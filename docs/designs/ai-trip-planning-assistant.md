## Relationship to existing work
`CONVERSATIONAL_ITINERARY_BUILDER_PLAN.md` (repo root) is a fully-speced, unimplemented plan that already covers this feature's Phase 1: a public, non-persisting `/packages/itinerary-chat` endpoint that turns free-text messages into `{destination, duration, travelers, budget, preferences}` slots, gated by a 30/15min gateway limiter (`itineraryChatLimiter`), then hands off to the existing `generate-itinerary-preview` pipeline once required slots are known. **This document does not replace that plan — it sequences after it and reuses its contracts, limiter pattern, and slot vocabulary.** Where this document's tool-call vocabulary below overlaps with that plan's `ItineraryChatSlots` (destination/duration/travelers/budget/preferences), it is the same data, exposed as discrete UI-driving tool calls instead of a single free-text turn. Implement the sibling plan first; this document is Phase 2 on top of it.

## Problem Statement
LushWare wants an AI layer over the existing travel CRM that helps a prospect plan a trip end-to-end (chat or voice), grounded in real company data (packages, pricing), tracks booking status, and can answer policy questions (refunds, etc.) — with the AI either carrying the full conversation or driving the UI step by step. Availability/date-constrained inventory checking is explicitly out of scope for this phase (see Open Questions) — packages are treated as available at the listed price unless a later phase adds live availability.

## Constraints
- Existing production system with paying customers (LushWare) — cannot regress the current booking/payment flow.
- `Services/package-service` already ships a one-shot Gemini itinerary generator (`generateItineraryPreview`) and, once the sibling plan lands, a conversational slot-filling endpoint (`itineraryChat`) — this phase builds on both, not a parallel LLM integration.
- `organizationSettings` (`Services/shared/contracts/src/organizationSettings.js`) already has a single `cancellationPolicy` string field (nullable, admin-editable via `PUT /admin/settings`) — this is the existing single-policy-text pattern to extend, not a from-scratch data model. There is still no *retrievable, multi-document, citable* company-docs store — that part is genuinely new.
- Gateway is the only entry point (JWT verification, rate limiting, CORS) — a new AI surface must route through it like every other service, and any new limiter must budget for a *session's* worth of model calls, not one call (see Success Criteria note on rate limiting).
- All services are ESM, Zod-validated at the boundary, structured pino logging with `requestId` — new code follows the same conventions.

## Premises
1. **Wedge is the itinerary-building flow for prospects (unauthenticated), not booking-status tracking or voice** — those are explicitly deferred to a later phase.
2. **Refund/policy answers must be RAG-retrieved verbatim from company docs with citation, never LLM-paraphrased from training data — and the citation itself must be server-verified, not model-written.** Non-negotiable: Air Canada's chatbot invented a bereavement-fare refund policy in 2024 and a tribunal held the airline to it (~US$800 payout). A model that writes its own "quote" next to a real `sourceDocId` reproduces this exact failure (fabricated text wearing a real citation) — the retrieval and quote-extraction must happen in server code, with the model only selecting among server-provided snippets or declining.
3. **Any tool call that touches money or booking state (cancel, refund, modify) requires a deterministic confirmation step** — the LLM proposes, a non-LLM code path executes only after explicit user confirmation. No such tool call exists in this phase (see Out of Scope), so this premise is not yet exercised by shipped code; it constrains the next phase.
4. User committed to watching 3-5 real prospect sessions on the current one-shot generator before further chat/voice engineering spend — this is an explicit process commitment, not yet executed (see Assignment).

## Landscape Findings
- Standard architecture for this category (Mindtrip, Layla, Turkish Airlines/Kiwi via MCP) is retrieval-augmented generation + typed tool-calling into real inventory/booking APIs — not a bare LLM. MIT researchers found standalone LLMs produce logistically viable itineraries only ~4% of the time without grounding.
- The dominant failure mode industry-wide is hallucination on policy/pricing specifics (fabricated refund terms, wrong dates, invented amenities) — directly informs Premise 2.
- Only ~30% of US travelers report being comfortable using AI travel tools (2025) — trust/transparency (showing sources, not overclaiming certainty) matters as much as capability.
- No eureka against conventional wisdom: the RAG + tool-calling + confirm-before-mutate pattern is sound and is what LushWare should build toward, just not all in one sprint.

## Approaches Considered

### Approach A: Conversational slot-filling chat (= the sibling plan, Phase 1)
Free-text chat turn → model extracts known slots (destination/duration/travelers/budget/preferences) → once destination+duration are known, hands off to the existing `generate-itinerary-preview` pipeline. Fully speced in `CONVERSATIONAL_ITINERARY_BUILDER_PLAN.md`, not yet implemented. Effort: S (already scoped down to a file-by-file plan). Risk: Low.
Not rejected — this is the prerequisite phase; ships first.

### Approach B: Ideal architecture — dedicated ai-service
New `ai-service` (port 3011, matches the existing 10-microservice pattern) owns conversation persistence (Postgres), a `docs` table with pgvector RAG for refund policy and future company docs, and typed tool-calling into `package-service` (search/pricing) and `booking-service` (status) via internal HTTP. Streaming endpoint architected so voice (speech-to-text) feeds the same tool-calling loop later.
Effort: L (~3-4 weeks). Risk: Medium (new service, new data model, cross-service auth).
Not rejected — this is the target end-state once booking-status tracking, voice, and multi-doc RAG are needed; out of scope for this document.

### Approach C: UI-driven wizard (voice-ready, low hallucination) — CHOSEN for this phase
Once Approach A's slots exist, the AI drives the **existing itinerary-builder UI components** step by step via a small fixed tool-call vocabulary ("set destination", "set dates", "propose packages from real inventory", "answer policy question with a server-verified citation") instead of leaving the visitor to parse free prose. Both text and voice reduce to the same tool-call vocabulary, so voice is a thin adapter later, and hallucination risk drops structurally because the model fills known slots and selects among server-provided doc snippets rather than generating free text a user has to trust blindly.
Effort: M (~1.5-2 weeks, reduced from the original estimate because Approach A already provides the slot-extraction and hand-off plumbing). Risk: Medium — the dependency is UX/interaction design (choreographing the step sequence and confirmation UI), not raw engineering difficulty.

## Recommended Approach
User chose **Approach C**, sequenced after Approach A. Rationale accepted: C is structurally the safest against the Air Canada-class hallucination risk, and makes voice nearly free later because voice and text collapse to the same tool-call interface. Traded off: slower time-to-first-observation than shipping Approach A alone, so the Assignment below (observe real usage) must happen on Approach A's chat before Phase 2/C work starts.

### Implementation shape (package-service + Client, no new service yet)

**Tool-call vocabulary (v1, fixed set):**
- `set_slot(name, value)` — mirrors Approach A's `ItineraryChatSlots` fields (destination, duration, travelers, budget, preferences); server re-validates against the same bounds `sanitizeSlots` already enforces in the sibling plan.
- `propose_packages(criteria)` — **the model emits search criteria only** (destination, budget range, preferences); the orchestrator queries `package-service`'s real inventory server-side and returns DB-validated package rows in the turn envelope. The model never emits a package ID directly, and the client never renders an ID that didn't come from this server-side query.
- `answer_policy_question(question)` — the orchestrator performs server-side retrieval against the policy store (see Data Model below) and returns the best-matching stored snippet(s) verbatim in the turn envelope; the model's job is limited to choosing which retrieved snippet(s) answer the question and phrasing a short lead-in sentence, never authoring the quoted text itself. If no snippet clears the match threshold, the orchestrator returns a fixed "I don't have a confirmed answer — here's how to reach a human" response (contact channel = existing `supportEmail`/`whatsappNumber` from `organizationSettings`), and the model cannot override this.
- `complete_wizard(selection)` — terminal action once a package is chosen from a `propose_packages` result. Because the wizard always terminates on a real, server-validated package (never a from-scratch manual itinerary), it navigates into `CustomizePackageContainer` (`/package/:id/customize`) pre-filled with the wizard's gathered slots (dates, travelers, preferences), landing the visitor at that flow's existing Contact step and submitting via its existing `submitCustomizationRequest` → `leadId` path. `PlanYourTripContainer`'s separate from-scratch Step 4 (`submitManualItineraryRequest`) is not part of this wizard's exit path — that remains Approach A's terminus for visitors who never select a proposed package. This phase does not add a new submission path in either container.
- Reserved, not implemented this phase: any tool call that mutates booking/payment state (cancel, refund, modify) — deferred to the phase that implements Premise 3's confirmation step against real mutating actions.

**Turn envelope (request/response shape):** each turn, the client posts `{ wizardState, messages: [...] }` (wizardState = the slots/selections gathered so far, same shape as Approach A's `slots`); the orchestrator calls `geminiClient.generateStructured` constrained to a JSON schema returning exactly one tool-call object `{ tool: <name>, args: {...} }` per turn, executes any server-side work that tool implies (inventory query, policy retrieval), and returns `{ toolCall, serverResult, updatedWizardState, uiComponent }` where `uiComponent` names which existing Client component to render next (date picker, package cards, policy answer card). A single free-text message naming multiple slots at once (e.g. "2 people, $3000, love hiking") is handled the same way Approach A already handles it: the model may return multiple `set_slot` updates merged in one turn via a `slots` object on the tool-call args, reusing Approach A's `sanitizeSlots` merge function rather than inventing a second merge path.

**Data model:** extend `organizationSettings`'s existing `cancellationPolicy` single-string pattern with a new `policyDocuments` table (id, title, body, updatedAt, updatedById) rather than one giant string — this is what makes citation-by-snippet possible. Owner of editing/populating these docs: the same admin role that already edits `cancellationPolicy` via `PUT /admin/settings` in Management; no new role. Retrieval at this doc count (a handful of policy documents) is keyword/substring matching against document sections, not embeddings — vector search is deferred to Approach B, when the doc count grows beyond what keyword matching handles well.

**Gateway rate limiting:** this phase's endpoint reuses (does not duplicate) Approach A's `itineraryChatLimiter` budget (30/15min/IP) — a full wizard walkthrough (slot-fill → propose → policy question → complete) is several turns, same order of magnitude as a chat conversation, so it shares the same ceiling rather than getting a separate, stricter one.

**AI-unavailable degradation:** if `generateStructured` returns the existing "AI generation is not configured"/503 error, the wizard surfaces the same fallback banner + manual-entry path the current one-shot generator already uses (`PlanYourTripContainer`'s existing manual Step 1-4 flow) — no new degradation UX to design.

**Explicitly out of scope for this phase:** booking-status tracking, voice input, authenticated/logged-in flows, live package availability by date, and any tool call that mutates booking or payment state.

## Open Questions
- Exact keyword-matching implementation for `policyDocuments` (simple substring/TF-IDF vs. a small library) — an engineering choice, not a product one; defer to `/plan-eng-review`.
- Conversation state lifetime (in-memory per session vs. short-lived Redis/DB row) — Approach A's plan keeps it client-side and stateless server-side; confirm this phase follows the same pattern before adding any server-side session store.
- Whether `propose_packages` needs date-based availability filtering before wider rollout, or whether "available at listed price" remains an acceptable phase-2 assumption — revisit once real usage data exists.

## Success Criteria
- A prospect can complete a full wizard build (destination/duration/travelers/budget via `set_slot` → `propose_packages` from real inventory → optional `answer_policy_question` → `complete_wizard`) within the existing 30/15min gateway budget, ending in `CustomizePackageContainer`'s existing `submitCustomizationRequest` → `leadId` submission for the selected package.
- Every `propose_packages` result traces to a real `package-service` row; zero invented package IDs or prices reach the client.
- Every `answer_policy_question` response either quotes a server-verified stored snippet with its document reference, or returns the fixed "I don't have a confirmed answer" fallback — never a model-authored quote.
- The 3-5 observation sessions on Approach A's chat (Assignment) are completed and their findings inform this phase's tool-call vocabulary and step choreography before broader rollout.

## Eng Review Addendum (/plan-eng-review)
- **[P1] Admin auth on `policyDocuments` CRUD (accepted):** the new admin routes for creating/editing/deleting `policyDocuments` MUST be registered behind the same JWT+admin-role middleware chain that already guards `PUT /admin/settings` (`organizationSettings`) — no new auth path invented. This is load-bearing: an unauthenticated write to policy content the wizard cites verbatim to prospects would be worse than the Air Canada failure Premise 2 exists to prevent.
- **[P2] Enum-constrained tool schema + turn latency UX (accepted):** the turn envelope's `tool` field must be a JSON-Schema enum over the fixed vocabulary passed to `generateStructured`'s `schema` param (unknown value → 502, mirroring Approach A's invalid-JSON handling), not a loosely-typed string. The Client must show a per-turn loading state and a defined timeout message, since a turn can take up to ~90s worst case (3 retries × 30s timeout, per `geminiClient.js`) plus a server-side inventory/policy query.
- **[P2] Reuse `serializePackageList`/`buildInclude` for `propose_packages` (accepted):** the inventory query and result shape must go through `package.service.js`'s existing `serializePackageList`/`buildInclude` helpers — no second, parallel package-serialization path for the wizard.
- **[P3] Policy-doc caching (declined, correctly):** an in-memory cache for `policyDocuments` reads was proposed and explicitly declined as premature at current doc count/traffic — revisit only if real latency data justifies it.
- **Test coverage (accepted in full):** 13 test requirements added covering `propose_packages` (happy/empty/DB-failure), `answer_policy_question` (match/no-match/model-authored-quote-discarded — this last one is the Premise-2 regression guard), `complete_wizard` (valid/removed-package), `policyDocuments` admin CRUD (401/403 + happy paths), the enum-constrained tool schema (unknown tool → 502), and one E2E full-walkthrough flow plus a slow-turn/no-duplicate-submit interaction test. All follow the project's existing vitest/supertest conventions (see `aiPackage.controller.test.js`).
