## Problem Statement

The lead copilot currently fails both functionally and visually. When no lead is selected, it still exposes the composer and sends `scope={}`; `leads.adapter.parseScope()` rejects the missing lead identifier with `Invalid input: expected string, received undefined`. Clearing a lead resets only loading and claims, leaving context, sources, suggestions, answers, and errors from the previous lead available to leak into the next interaction.

The UI is a fixed 320px card over the top-right of Lead Management. It covers work instead of joining the layout, reduces collapse to a floating top-right button, separates sources from claims, omits user turns and question/answer association, and gives agents no honest reason to reopen it.

The redesigned first slice serves a frontline travel agent working one selected lead. It must make the lead's situation, changed facts, risks, and next decision understandable before the agent writes a prompt.

Scope of that promise: the first release briefs only on what the existing allowlist supplies — lifecycle status, name, destination, budget, assignment, and the created/updated timestamps — plus whatever the `changed` window adds. The lead record also holds travel date, end date, traveler count, priority, and follow-up date, and those stay out of evidence in this slice, behind the same endpoint audit as the other related sources. Until they land, the briefing is a status, freshness, and attention brief, not a full trip-risk brief; do not let the UI's wording promise more than the evidence carries.

This is a reference implementation, not the product boundary. Once the specialized lead module proves the briefing, evidence, dock, and scope contracts, the same pattern expands to every protected Management workspace with page-specific data and behavior.

## What Makes This Cool

Opening a lead is the prompt. The dock immediately explains what changed, what needs attention, why it matters, and where each conclusion came from.

The distinctive interaction is the Evidence Lens: activating a briefing claim reveals and focuses the supporting allowlisted field in the lead record. Activity-level linking appears only after the server supplies activity evidence. Evidence is not a detached list of pills. The CRM record itself becomes the source view. A compact “Since you were here” strip provides a real return loop, while consequence ladders translate facts into operational stakes.

## Constraints

- First release completes one lead-detail flow end to end and establishes the reusable workspace-module contract; it does not fake product-wide coverage before a second specialized adapter exists.
- Keep the existing authenticated management turn endpoint, read-only CRM boundary, and two-phase deterministic/model briefing. Extend evidence granularity and add only the authenticated seen acknowledgement specified below.
- No request may be sent without a non-empty lead identifier.
- No previous lead content may survive deselection or lead switching.
- Follow `Management/DESIGN.md` Signal Console: functional teal accent, separate semantic status colors, Archivo/Public Sans/JetBrains Mono roles, 12px text floor, 4px spacing grid, 6–8px ordinary radii, both themes, no gradients, glass, decorative sparkles, or consumer chat bubbles.
- Reuse the current turn endpoint and installed UI primitives. The seen acknowledgement is the only new endpoint in this slice; do not add assistant/chat/layout dependencies unless an implementation probe proves a missing capability.
- The assistant never writes CRM business data in this scope; its only write is user-scoped Copilot metadata recording an acknowledged briefing view.
- Do not show a review inbox, unread count, or engagement badge until real review records and lifecycle semantics exist.
- **Landing decision:** implement the complete reviewed scope as one change set. The task order still establishes contracts and state before UI, but there is no reduced intermediate deliverable or separate PR boundary.
- **Comment maintenance:** the change updates the three comments it invalidates in the same edit — the `writeLastSeen` contract in `managementCopilot.controller.js`, the `loadEvidence` bundle interface in `adapters/registry.js`, and the evidence-granularity note at the top of `leads.adapter.js`. The registry comment is the documented deep interface every future page adapter copies, so it must describe the bundle shape that actually ships.

## Premises

1. A selected lead is required for briefing and conversation. No lead means no API calls and no enabled composer.
2. The assistant is briefing-first. Conversation inspects, challenges, and extends the briefing.
3. On the first eligible lead visit, auto-open the non-covering dock only at `xl` and wider. Below `xl`, keep the record visible and show one truthful “Lead briefing ready” cue on the Copilot trigger. Explicit open/collapsed and cue-dismissed choices persist; switching leads refreshes content without forcing visibility.
4. At `xl` widths and above, a non-covering desktop dock reflows the lead page. Below `xl`, the same session body uses an overlay drawer. A 40px rail restores a collapsed desktop dock.
5. Attention UI is derived from current data. The collapsed rail may show one semantic warning marker only when the active briefing contains a warning or critical claim.
6. Proactive review queue, action-taking, cross-page memory, and feedback-driven learning remain future extensions. The first release leaves room for them without shipping placeholders.

## Cross-Model Perspective

The independent Codex cold read agreed that the product should minimize time-to-understanding rather than lead with chat. It proposed three strong additions adopted here:

- Link each supported lead claim to the actual allowlisted field that grounds it; add activity linking only when activity evidence exists.
- Show a concise “Since you were here” change strip using the existing `last_visit` briefing window.
- Express attention as a consequence ladder when the existing server-authored claim text and audited evidence permit it, rather than inventing a client-side implication.

It also proposed replacing the existing chat stack with assistant-ui, Vercel AI SDK, CopilotKit, and a resizable-panel dependency. That prescription is rejected for this design: the repository already owns an Express assistant contract and UI primitives, and no verified missing capability justifies adding parallel runtime or panel abstractions.

## Approaches Considered

- **Focused Lead Dock:** smallest repair, rejected because its evidence remains inside a conventional panel and produces a weaker demo.
- **Contextual Copilot Workspace:** product-wide shell is the intended expansion path, but its generic layout ownership is sequenced after the first specialized lead module proves the contract.
- **Evidence Lens Dock:** selected because it makes instant, verifiable understanding the hero while retaining the safe dock behavior needed for future growth.

## Recommended Approach

### 1. Scope and session ownership

**Module split.** `ManagementContextCopilot.tsx` is already 310 lines and this change adds a rail, a drawer, briefing sections, evidence reveal, and conversation turns. Split it as part of the change:

- `useCopilotSession(scope, since)` — scope lifecycle, keyed reset, cancellation, two-phase load, acknowledgement, turn state;
- `CopilotDock` / `CopilotRail` / `CopilotDrawer` — shell, visibility, focus, responsive surfaces;
- `LeadBriefing` / `LeadConversation` — lead-specific content rendered inside the shell.

The shell receives page-specific sections as children/props so the next specialized workspace reuses it without copying lead UI. Keep the peer API narrow: the hook returns session state and actions, and sections receive data plus callbacks, never the transport layer.

Replace the loose `Record<string, unknown>` request scope with a nullable server scope, while keeping the display label client-only:

```ts
type LeadCopilotScope = {
  leadId: string;
} | null;
```

`LeadManagement.tsx` remains the owner of the selected lead and passes `scope={{ leadId }}` plus a separate `scopeLabel`, or `scope={null}`. Normalize the selected ID with `trim()`; blank or whitespace-only IDs become `null`. Only `{ leadId }` is serialized into `page.scope`; `null` is never sent. Tighten the server schema to `z.string().trim().min(1).max(255)` and keep the object strict. The client must never construct `{}` or `{ leadId: "" }` as a sentinel.

**Scope binds to the lead record, not to the documents dialog.** Today `sectionLead` is set only by `onSectionClick`, which opens `LeadSectionView` — a `Dialog` listing quotations, invoices, receipts, and vouchers that renders only `lead.name`. That is why the reported bug reads as it does: the copilot's scope exists only while a documents modal is open, and clearing it leaves the empty-object sentinel behind. This change adds a persistent lead-detail surface in `LeadManagement` that renders the adapter's allowlisted fields and publishes their `data-copilot-evidence-id` values, and binds the copilot scope to the selected row in that surface. Without this surface, the reflow premise, the anchor protocol, and the Evidence Lens reveal have no target and every claim falls through to the inline fallback.

Split panel state by lifetime:

- **Dock shell state:** `open | collapsed`, persisted independently of the selected lead.
- **Lead session state:** context, claims, sources, suggested questions, user/assistant turns, pending question, per-turn errors, briefing error, loading, and partial/no-access state.

Key the lead session body by `leadId`. Selecting lead B unmounts lead A's session before B loads. Clearing selection unmounts the session and renders the no-lead state. Abort or ignore every in-flight request from the prior key so a late response cannot repopulate stale content.

The deterministic request runs when the scope changes, because it is cheap and paints the instant skeleton. The model briefing request runs only while the dock or drawer is actually open for that scope, so a collapsed rail never spends a generation the agent cannot read, and the "AI checked this lead" timestamp never refers to unseen content. Opening a collapsed dock starts the briefing for the active scope; closing it does not cancel an in-flight generation, whose result is kept for the next open of the same scope.

Because a first open can therefore be cold, the dock shows grounded deterministic insights immediately and marks the model phase as explicitly pending rather than blank. The model claims swap in when they arrive, and no prefetch or idle warming is added, so generation cost stays tied to a dock the agent actually opened.

`copilotAPI.js` exposes an optional `AbortSignal` on `turn()` and all three exported calls. A scope change aborts the prior scope's in-flight requests so an abandoned briefing stops rather than completing invisibly, and the fetch path must distinguish an abort from a genuine failure so a cancelled request never renders as an error.

Every copilot request is also bounded by a client timeout above the server's 17s generation deadline. A timeout presents as a recoverable failure with Retry rather than an indefinite loading state, and the controller's comment about the client's latency budget is corrected to match what the Management client actually enforces.

Accepted cost: each phase loads its own evidence bundle, so an open performs the lead-service read twice. This is deliberate. No bundle cache is introduced, because a cached record could make a claim cite a value the lead no longer holds, and on Cloud Run without session affinity the two requests may not even share an instance.

The no-lead state:

- makes zero deterministic, briefing, or ask requests;
- clears every lead-scoped value, including input and errors;
- shows “Select a lead to generate its situation briefing” when the dock is open;
- removes the attention marker and disables/hides the composer.

### 1.1 Truthful last-seen acknowledgement

The current turn controller must stop calling `writeLastSeen` during deterministic, briefing, and ask requests. Both briefing phases read the same previously stored timestamp, so the deterministic request cannot advance the window before the model request computes it.

Add authenticated `POST /api/v1/assistant/management/seen` with a strict shared request schema containing `{ page: { key, scope } }`. The handler applies the same `copilotEnabled()` and `pageKeyAllowed()` gates as the turn route and returns the same generic 404 when either fails, so disabling the copilot closes every path into the feature and unallowlisted page keys stay undisclosed. It then authenticates the operator, resolves the existing page adapter, runs its strict scope parser, fingerprints the scope, and upserts the operator/page/scope `lastSeenAt`. It does not load evidence, call the model, or accept a client-authored timestamp. Repeated acknowledgements are idempotent and only move the timestamp forward.

The client acknowledges once, at presentation time, when all of these are true:

- a non-empty grounded briefing result has rendered for the active lead;
- the persistent dock or mobile drawer is actually open;
- the model phase has settled successfully, including a server-returned deterministic fallback;
- the session key still matches the lead being acknowledged.

A briefing that settles while the dock is collapsed is kept, not acknowledged. When the agent later opens the dock and the kept result is presented, that presentation is the acknowledgement moment: the conditions above are evaluated then, the header's timestamp is labeled as generation time rather than check time, and the window advances exactly once. A kept result is reused only within a short freshness bound; once it exceeds that bound the dock regenerates instead of presenting it, so the presented content is never arbitrarily old.

Do not acknowledge a no-scope, no-access, loading, total briefing failure, collapsed, background-only, or stale response. The seen handler must await the upsert and return a 5xx when it rejects, while the turn route's last-seen read stays best-effort so a storage problem never fails a briefing. If the acknowledgement fails, keep the briefing usable and retry once on the next genuine open; never display a blocking error because the failure affects future change-window accuracy, not current evidence.

**The window must have a consumer, or this machinery is dead weight.** Today `computeInsights(bundle, since)` never reads `since` — its `changed` insight is `daysBetween(lead.updatedAt, Date.now())` — and `buildManagementBriefingPrompt` receives only the literal `Change window: last_visit`. Both phases must use the resolved boundary:

- `computeInsights` compares against the resolved boundary so a `changed` insight means "changed since the agent last saw this", not "changed recently";
- `buildManagementBriefingPrompt` receives the resolved ISO boundary, not the window keyword, so model-authored `changed` claims describe the same window;
- T3's regression list changes from now-relative freshness thresholds to boundary-relative ones.

If the boundary is not consumed by both phases, delete the seen endpoint and keep turn-time writes instead of shipping a clock nothing reads. Also resolve the client-authored `page.lastSeenAt` hint in `ManagementAssistantTurnRequest`: the controller prefers it whenever no stored row exists, so either remove it or document it as a first-visit-only fallback.

### 2. Dock shell and visibility policy

At `xl` (1280px) and wider, Lead Management becomes a two-column work surface: `minmax(0, 1fr)` for the record and a dock column. The open dock is 360–400px, with 388px as the target at wider desktop sizes. It never uses `position: fixed` and never covers the lead record.

When collapsed, the dock column becomes a 40px rail with one labeled, keyboard-accessible Copilot control. The rail uses the primary token for focus/active state, not decoration.

| Viewport | Record and navigation | Copilot surface |
|---|---|---|
| 1440px+ | Existing app navigation plus a lead workspace that keeps its current content hierarchy | Persistent 388–400px dock; 40px collapsed rail |
| 1280–1439px | Existing navigation plus at least a practical two-column lead workspace; wide tables scroll in their own wrapper | Persistent 360px dock; 40px collapsed rail |
| 768–1279px | Lead workspace keeps the full content column | Dialog-based right drawer, `min(420px, 90vw)`; 44px trigger |
| 320–767px | Lead workspace stays behind a locked overlay and does not scroll while open | Full-width, `100dvh` drawer with safe-area padding; 44px trigger and close control |

Persist UI preference in local storage under the authenticated operator's stable internal ID, never their email or display name:

- `management-copilot:v1:<actorId>:visibility` is missing before discovery, then `open` or `collapsed`;
- `management-copilot:v1:<actorId>:mobile-cue-dismissed` is missing before the cue is handled, then `true`.

Wait for authenticated identity before reading or writing either key. Until identity resolves, render the non-intrusive collapsed rail/trigger and do not persist a fallback. Never read a browser-global key, so one operator cannot inherit another operator's discovery or visibility choice.

When the first valid lead appears and visibility preference is missing, auto-open the dock only at `xl` and wider and persist `open`. Once the user collapses it, lead changes and reloads must not reopen it. Manual reopening persists `open`. No-lead visits do not count as discovery.

Below `xl`, render the same session body inside an app-specific `CopilotDrawer` composed from `Management/src/components/ui/dialog.tsx`; no Drawer/Sheet primitive exists today. Reuse Dialog's portal, modal overlay, focus trap, Escape dismissal, scroll lock, and focus restoration, while the composite supplies right-edge placement and sizing. The trigger is at least 44px. Preserve the same visibility preference and session semantics. Opening moves focus to the drawer heading; closing restores focus to the trigger.

Below `xl`, never auto-open the modal surface. After the first valid briefing becomes ready, attach a one-time “Lead briefing ready” cue to the 44px Copilot trigger; this is status copy, not an unread count. Opening the drawer or explicitly dismissing the cue persists its dismissal. The cue does not return for later leads, and a warning marker appears only under the separate verified-severity rule.

### 3. Briefing-first hierarchy

The open dock is one continuous surface, not nested cards or tabs:

1. **Header:** a neutral 16px line icon and “Lead briefing” heading, lead name/ID, generated/checked timestamp, partial-data label when applicable, and collapse control. Do not place the icon in a filled tile or spend teal on assistant identity; accent remains reserved for active navigation, focus, evidence actions, and the primary composer action.
2. **Since you were here:** one compact change summary based on `since="last_visit"`; omit the block when no changes exist. Render it as a flat row with a 12px uppercase label, body copy, generous vertical spacing, and hairline separators. No rounded container, colored left border, teal fill, or decorative icon.
3. **Current state:** the smallest set of facts needed to understand the booking opportunity now.
4. **Needs attention:** warning/critical claims before informational advice. Each item renders the server-authored claim text and evidence action. If that text contains an audited consequence, present it as subordinate supporting copy; the client never generates or extrapolates one.
5. **Experienced view:** optional lower-priority interpretation from the existing claim contract.
6. **Suggested questions:** at most three record-aware actions, phrased as real agent questions.
7. **Conversation thread:** appears after the first question and preserves both user turns and their associated answer blocks.
8. **Composer:** sticky at the bottom, labeled with the active lead, secondary to the briefing.

Dock typography uses role-specific Signal Console faces and sizes:

- `Archivo` 18px/700 for the dock heading;
- `Public Sans` 16px with at least 24px line height for claim and answer prose;
- `Public Sans` 14px for question actions, controls, and short utility copy;
- `Public Sans` 12px/600 uppercase for section labels and 12px/400 for metadata;
- `JetBrains Mono` 12–14px with tabular figures for lead IDs, dates, amounts, and deltas.

The 16px prose role applies only to the copilot's sentence-length interpretation, not dense lead fields or tables. Keep claim text concise enough that the top-three briefing jobs remain visible; never reduce type to recover space.

The first dock viewport, before its internal scroll, reserves priority for exactly three content jobs:

1. what changed since the agent last saw this lead;
2. the minimum current-state summary;
3. the highest-severity item needing attention.

When no changes exist, omit that block and let current state and attention move up; do not fill the released space with chat. Suggested questions and the transcript never displace these jobs above the fold.

The lead record and dock scroll independently on desktop. The composer is sticky inside the dock, never fixed to the viewport. On mobile, the drawer owns its scroll while open; the obscured record does not scroll behind it.

Deterministic insights render first as a provisional list. A successful non-empty model briefing atomically replaces that list; it never clears the list before the replacement is ready. If model generation fails or returns no accepted claims, retain the deterministic list, label the briefing partial, and offer Retry. If keyboard focus is inside the provisional claims region when model claims arrive, queue the replacement until focus leaves. While queued, keep the header timestamp aligned with the rendered deterministic claims and announce “Updated briefing ready” through the polite live region. If evidence activation already moved focus to a record field, replacement may proceed because that target remains mounted.

If the initial deterministic request fails, render a full briefing-error state with a concise message and Retry action; keep the selected lead visible, disable the composer, and show no rail marker. Do not describe this as partial because no grounded briefing content exists.

### 3.1 Confidence storyboard

| Horizon / step | Agent does | Agent sees | Intended feeling | Failure signal |
|---|---|---|---|---|
| First 5 seconds | Opens a valid lead | Dock opens once with lead identity, freshness, changed context, current state, and one highest-risk item | Oriented: “I know what changed and where to look” | Agent closes the dock before reading, cannot identify why it opened, or the lead record feels obstructed |
| First verification | Activates evidence on a claim | Supporting field scrolls into view, receives focus, and matches the cited value | In control: “I can check this myself” | Agent hunts for the source, mistakes the highlight for an edit, or cannot return to the claim |
| First 5 minutes | Uses a suggested or typed question | Their question remains visible with a grounded answer and inline evidence | Productive: “This understands this lead, not generic travel” | Chat replaces the briefing, loses the question, or answers without a usable source |
| Repeated lead work | Collapses, switches leads, reloads, and reopens when useful | Visibility preference is respected; content changes to the active lead without stale text | Respected: “It helps without taking over” | The dock forces itself open again, keeps another lead's content, or shows a meaningless badge |
| Long-term / every workspace | Encounters the same shell in another protected page after that page has a specialized adapter | Familiar controls and state language with page-specific briefing content and evidence | Fluent: “I learned one copilot, and it understands each workspace” | Every page shows generic prompts, copied lead language, or inconsistent empty/error behavior |

The 5-second goal is zero-effort orientation. The 5-minute goal is verified, user-directed understanding. The long-term goal is one learned interaction model with specialized intelligence in every workspace, never one generic chat pasted everywhere.

### 4. Evidence Lens interaction

The current leads adapter emits one record-level evidence item, `lead:<id>`, and no `fieldPaths`; that is insufficient for field-level reveal. Extend the existing adapter without changing endpoints:

- emit one evidence item per allowlisted field that may ground a claim;
- use stable IDs such as `lead:<id>:lifecycleStatus`, `lead:<id>:destination`, and `lead:<id>:updatedAt`;
- use the existing evidence vocabulary: `{ id, type: "record", label, value, recordRef: { kind: "lead", id }, fieldPaths: [fieldName], updatedAt, asOf }`, with one scalar `value` per item;
- remove the legacy record-level `lead:<id>` item; the model briefing prompt receives the same field-level evidence IDs, and every deterministic or model claim must cite those IDs;
- update deterministic insights to cite the field-specific evidence ID;
- stop treating the evidence bundle as the record store: `computeInsights` and `defaultQuestions` must read the lead object fetched in `loadEvidence` (held on the bundle outside `evidence`, or captured in the adapter closure), never `bundle.evidence.find((e) => e.id.startsWith('lead:'))`. Field items are citation-only, so a scalar `value` must never be dereferenced as an object;
- extend `ManagementSourceSchema`, `buildSources`, and the client source type with `capturedValue: string | number | boolean | null`, copied only from the cited allowlisted field item, so an authorized client can render the fallback detail;
- keep the validator rule that every rendered claim cites an evidence ID present in the current bundle.

Do not create activity, payment, invoice, or communication evidence until those related service reads and allowlists pass the separate endpoint audit. The first Evidence Lens release links only fields the leads adapter actually supplies.

One shared `leadEvidenceId(leadId, field)` helper produces every field evidence ID. The adapter, the record markup, and the reveal resolver all consume it, so no call site reconstructs the string by hand. A test asserts that the IDs the adapter emits equal the IDs the record surface can publish. Do not infer targets from display labels, and do not let two independently maintained builders define the same identifier.

Each claim renders its evidence action inline. Field reveal is scoped to `xl` and above, where the dock and the record are both live. Below `xl` the drawer is modal, so content behind it is inert; there the evidence action opens the inline detail instead of moving focus into the record. On hover, focus, or activation at `xl` and above:

- resolve the first matching target that is rendered and not hidden by `display: none` or `visibility: hidden`; an off-screen target is valid and scrolls into view on activation;
- apply the accent wash and 2px primary outline from the target's already-visible neutral state; transition only `background-color` and `outline-color` for 140ms with an exponential ease-out curve, with no scale, pulse, glow, or opacity entrance;
- on activation, pin the highlight, call `focus({ preventScroll: true })`, then `scrollIntoView({ block: "center", behavior: "smooth" })`;
- when `prefers-reduced-motion: reduce` matches, remove the color transition and use immediate scrolling;
- announce the revealed field through an `aria-live="polite"` status;
- treat pointer hover/focus as a preview and activation as pinned: clear a preview on pointer leave when neither control nor target has focus; clear a pinned highlight when focus leaves the target or another claim is activated.

If no matching rendered target exists, keep the claim usable and open an inline evidence detail containing the source label, timestamp, field path, and captured value. Missing anchors are a graceful fallback, not an exception.

### 5. Conversation and trust

A submitted or suggested question creates a visible user turn before the request starts. The resulting answer is attached to that turn. Do not append anonymous answer blocks beneath the original briefing.

Use a restrained transcript with speaker labels and dividers, not speech bubbles. Every answer claim keeps its evidence action inline. A failed answer remains attached to its question with a concise error and Retry control.

Feedback controls do not ship in this slice because the authenticated management API has no feedback event or endpoint. They remain a future extension rather than writing into the anonymous site-assistant telemetry path.

No-access state replaces briefing and conversation with the existing access explanation, removes evidence values, and does not expose the composer.

### 6. Truthful attention and future AI reviews

The collapsed rail displays a single amber or destructive marker only when the current active lead session has at least one warning or critical claim. Its accessible label states “This lead has items needing attention.” It is not called unread and has no count.

The open header says “AI checked this lead” with the timestamp for the claims currently rendered. “Since you were here” and the semantic marker are the initial return mechanisms. No review inbox tab or teaser ships in this release.

Future extensions attach as follows:

- **Proactive review queue:** real review records may later open the same dock with a review scope and route into a lead session.
- **Action-taking:** confirmed actions attach beneath the claim that motivated them; the read-only boundary must be redesigned before enabling writes.
- **Cross-page memory:** dock shell state can move to the protected layout only when a second page has a real contextual briefing.
- **Feedback learning:** first add an authenticated management feedback schema, endpoint, and retention purpose; only then expose helpful/correction controls or use those signals for training or ranking.

Workspace expansion is deliberate, not a narrowing of the product vision. Each new Management workspace must supply six concrete pieces before it joins the copilot:

1. a typed, strict, nullable page scope;
2. an authenticated page adapter with audited allowlisted reads;
3. field-level evidence IDs and source targets;
4. page-specific deterministic insights and suggested questions;
5. rendered evidence anchors and complete empty/error/access states;
6. the same scope-switch, stale-response, responsive, and accessibility tests.

### 7. State and recovery matrix

| State | Record surface | Dock body | Composer | Rail marker |

| Briefing request failure | Selected lead remains usable | Error message + Retry; no claims | Disabled | None |
| Ready | Evidence targets available | Full briefing | Enabled | Derived from severity when collapsed |
| Partial model failure | Record unchanged | Deterministic content + partial label + Retry | Enabled if access permits | Derived from surviving claims |
| Ask failure | Record unchanged | Failed turn retains question + Retry | Re-enabled | Unchanged |
| No access | Redacted/authorized record behavior | Access explanation only | Hidden | None |
| Lead switch | New lead renders immediately | Prior session unmounted; new skeleton | Disabled until valid session | Recomputed only for new lead |

### 8. Accessibility and responsive requirements

- Every trigger, evidence action, suggestion, retry, and collapse control is keyboard reachable with a visible primary-token focus ring.
- Desktop dock and mobile drawer use a named heading and landmark.
- The 40px desktop rail control has an accessible hit target; mobile controls remain at least 44px.
- Semantic warnings are never color-only: pair color with icon/text and accessible labels.
- A model response never unmounts a focused provisional claim control; defer the atomic replacement until focus leaves that region. Evidence activation moves focus to the persistent record target before replacement.
- In both themes, normal text and metadata meet at least 4.5:1 contrast; large text, focus indicators, semantic icons, control boundaries, and meaningful non-text state meet at least 3:1 against adjacent colors.
- Real content never renders below 12px.
- At 200% browser zoom, the CSS viewport re-evaluates the same breakpoints, no page-level horizontal scroll is introduced by the copilot, and every briefing, transcript, evidence fallback, and control remains reachable.
- Focus is never obscured by the sticky composer, dock edge, or drawer chrome. The dock scroll container uses bottom scroll padding at least equal to the composer height, and focused controls scroll fully into view.
- Automated accessibility checks are a floor; keyboard-only traversal and screen-reader announcements must be exercised in both the persistent dock and mobile drawer.

## Success Criteria

1. Submitting without a lead is impossible; no assistant endpoint is called and the reported undefined-scope error cannot occur.
2. In select A → clear → select B, no label, claim, source, question, answer, input, loading result, or error from A appears in B.
3. A late response from A cannot update B after a scope switch.
4. First valid lead visit auto-opens once at `xl` and wider; below `xl`, a truthful one-time ready cue appears without opening the drawer. Collapse, manual reopening, and cue dismissal persist across reload and later lead changes.
5. At 1280px and wider, the dock never covers lead content. Below `xl`, it becomes a focus-managed drawer using the specified tablet and phone geometry.
6. The first viewport shows lead identity, freshness, changed context when present, current state, and the highest-severity attention item before chat.
7. At `xl` and above, every supported lead-field evidence action highlights and focuses the intended field; below `xl`, or whenever no target is rendered, the same action exposes the evidence through the inline detail with its source label, timestamp, field path, and captured value.
8. Suggested and typed questions render as user turns with their own loading, answer, citation, error, and retry states.
9. The rail marker appears only for real warning/critical claims and never claims unread/review counts.
10. Component coverage includes no scope, ready, partial, no access, request failure, ask failure, A→clear→B, stale response suppression, visibility persistence, truthful marker, evidence target, missing target, and keyboard focus behavior.
11. Light and dark visual verification passes at desktop and mobile breakpoints using realistic lead data.
12. No new UI or AI runtime dependency is added without a documented, reproduced gap in existing primitives.
13. The lead implementation leaves a documented six-part workspace-module seam so the next protected page can reuse the shell and protocol without copying lead-specific UI or weakening its own scope schema.
14. Accessibility verification demonstrates the specified 4.5:1/3:1 contrast thresholds, 200% zoom reflow, full keyboard traversal, correct live-region output, and no focused control hidden by sticky or modal UI.
15. Deterministic and briefing requests observe the same prior `lastSeenAt`; only an authenticated acknowledgement after grounded content is visibly rendered advances it, and acknowledgement failure never blocks the current briefing.
16. A fixture-based briefing evaluation in `Services/assistant-service/src/evaluation/` gates the landing: each claim's substance must follow from the field it cites, and every `changed` claim must fall inside the active window. It replays canned model output through the validator and insight rules, so it needs no live Gemini quota. Grounding alone is not the bar — a technically grounded but substantively empty briefing must fail.
