## Problem Statement

Operators stopped asking quantitative and cross-domain questions, and the copilot cannot answer them for four separate, fixable reasons.

**1. Grouping is not an askable operation.** `leadsCollection.adapter.js` already computes `groupedCount` by destination (threshold 3, section `experienced_view`, severity `info`) and its `questionTemplates` literally include "Where is demand clustering?". The data is owned and the panel does surface one fixed grouping on load. Asking is what fails: the page declares `tools: ['listLeads']`, and `listLeads` returns an ungrouped page of rows. Nothing groups by an arbitrary field, filters a group, or ranks groups. The operator sees a fixed insight they cannot interrogate or extend.

**2. The grounding gate deletes numeric answers.** `validateClaims` rejects an entire claim when its prose contains any digit: `RESIDUAL_VALUE_PATTERNS[0] = /\b\d[\d,.]*(\.\d+)?\b/` (`src/ai/groundingValidator.js`). Ask mode runs every answer block through it (`managementCopilot.controller.js`, `handleAsk`). A correct answer such as "12 leads want Bali, 8 Dubai" is generated, validated, discarded, and `CopilotConversation.tsx:119` renders "No grounded answer for that question." with a "Try again" button that resubmits the identical question.

The invariant is zero *unsupported* values. The implementation says zero *digits*. They differ, and the second makes every quantitative question unanswerable.

**3. The prompt forbids numbers too.** `managementBriefing.v1.js:68` instructs the model: "`text` is qualitative prose only. If a value appears in `text`, the claim is discarded." So the model is trained by its own prompt to avoid numbers. Fixing the validator alone changes nothing; the instruction has to change in lockstep or the model will keep producing prose the gate now accepts but the prompt still discourages.

**4. Derived numbers have no machine-readable form.** The rules that produce numbers emit inconsistent or absent facts:

| Rule | Prose | Fact emitted |
|---|---|---|
| `staleForDays`, `stuckInStatus` | "…62 days…" | `{ kind: 'date', value: <ISO timestamp> }` (the date, not the duration) |
| `groupedCount` | "…12 leads…Bali" | none |
| `groupedShare` | "…43% of the value…" | none |
| `ratioBelow` | "…43% of…" | `{ kind: 'percentage', value: '43' }`, which then fails `factGroundedIn` because the rounded value is not in the cited field |
| `thresholdExceeded`, `zeroOrLowCount` | "is above 3" / "at or below 0" | `{ kind: 'count', value }` for the field, but the descriptor constant in the prose is unrepresented |
| `overdueBy`, `expiringWithin` | qualitative | `{ kind: 'date' }`, grounded |

So a rule that accepts "numbers which trace to evidence" cannot work until the emitters carry the number.

**5. The panel is unranked.** `runRules()` returns insights in descriptor-declaration order and the deterministic handler ships them uncapped, so an `info` insight can outrank a `warning` on the same page (the leads page: the destination grouping is `info`, `Lead has no owner` is `warning`).

**Discovered while designing this, unrelated to the above:** a paged collection source is failed closed when its read is truncated (`collectionEngine.js:180-188`: if `total > rows.length`, the source lands in `unavailableSources`). `leadsCollection.adapter.js` pages at 200 with a `pagination.total` probe, so **the leads panel already reports "partially loaded" once the view holds more than 200 leads**. That is a live defect, and it blocks building the aggregate on the adapter read path.

## Demand Evidence

- Operators act on what the panel surfaces: a named operator changed a decision because of something it surfaced that they had not known (user-stated, this session).
- The sharper signal is the invisible one. For cross-page and quantitative questions, **operators stopped asking entirely** (user-stated). Abandonment is stronger evidence than a workaround, because the product already failed and nobody filed a ticket.
- **Telemetry gap that limits every claim above.** The public widget writes an `AssistantEvent` row per turn; the management copilot writes only `ManagementLastSeen`. There is no usage data, no dead-end rate, and no record of which tools ran. Every demand claim about this surface is currently an anecdote, including these. Instrumenting it is part of the work.

## Status Quo

- Row-level questions: answered in-app with list pages and filters.
- Quantitative and cross-domain questions: the panel offers one fixed grouping per page and cannot be asked to vary it. Above 200 leads even that page degrades. Operators stopped asking.
- The panel: deterministic insights render on load, a model briefing replaces them when it survives validation, and a chat sits below whose empty state is a refusal with a retry.

## Target User & Narrowest Wedge

**User:** the operator on a Management page who cannot ask a quantitative question today, and the owner who currently receives those questions out of band.

**Wedge:** make ask mode answer one quantitative question the operator chooses, on the page they are on, with every number traceable to cited evidence, inside the existing 17s budget. Concretely: ask "which destinations have the most leads?" on the leads page and get counts that survive the gate, each citing evidence.

That is one fact-shape change, one gate change, one prompt change, one aggregate primitive, and the role-derived catalogue that makes the primitive reachable. No new model calls, no new page, no transport changes. The rename, derived severity, ranking, suppression state, and streaming stay out (see Out of Scope).

## Constraints

- **Budgets:** 4 tool calls and one 17s deadline shared between generation and tool I/O (`src/ai/agentRunner.js`, `constants/managementCopilot.js`). The Management client aborts at 20s.
- **Compute:** Cloud Run 512Mi, 1 vCPU, `min_instances = 0`, `max_instances = 10`. Request timeout and concurrency are not declared in `infra/`.
- **Two different read paths with different failure modes:** the adapter/bundle path fails closed on truncation (`collectionEngine.js:180-188`) and pages at 200 for the leads descriptor; the tool path (`toolRegistry.js` `fetchJson`) reads up to 1000 rows, sets a `truncated` flag, and has no completeness probe.
- **Evidence shape is constrained by the substance judge:** `managementBriefingEvaluation.js:57-63` treats only evidence carrying `fieldPaths` as citation-capable, so any new evidence kind must carry `fieldPaths` plus a scalar `value`. Source baselines already do exactly this (`fieldPaths: ['recordCount']`).
- **Fact shape is constrained by the wire contract:** `managementBriefing.v1.js:34` requires `['kind', 'value', 'evidenceId']` on every fact, and `makeInsight` drops a fact whose single `evidenceId` is not among the insight's citations.
- **Transport:** single JSON response per call. No streaming anywhere in the stack.
- **Authorization:** gateway-only internal (`allow_unauthenticated = false`); JWT verified at the gateway, `x-user-*` forwarded, each domain service runs its own access check and returns 403/404 which surfaces as `notAuthorized`.
- **Invariants that do not move:** no unsupported value reaches an operator; no unauthorized evidence in a response; the model never authors server-owned prose or a route.
- **CI:** `microservices-ci.yml` runs `npm test` for assistant-service on PRs touching that service's paths, which includes `src/evaluation/__tests__` and `src/adapters/__tests__`. Unit fixtures do run in CI. The unwired suites are `Management/e2e/` (Playwright) and `Services/e2e-tests/`.

## Premises

1. **Identity is already the boundary.** Every tool runs under the caller's forwarded `x-user-*` and each domain service enforces its own access. Widening the tool vocabulary does not widen what a caller can see.
2. **Widening loses defense-in-depth.** Page-declared vocabularies also stopped the model enumerating which domains exist. That must be replaced deliberately by a server-side role filter, not left implicit.
3. **Two budgets still bound the answer.** A cross-domain question cannot be answered by loading several page bundles; it has to be one bounded query.
4. **The emitter fix, the gate fix and the prompt fix ship together.** Any one alone leaves the system in a state where the panel's own numeric insights, or the model's, are unreachable or deleted.

## Approaches Considered

**A. Role-authorized registry plus an aggregate primitive (chosen).** Capability derives from the question and the operator's permissions; the page keeps deciding only what is volunteered. One bounded `aggregate` tool covers any question shape expressible in the declared semantic layer.

**B. Multi-scope bundles, agent requests other pages' evidence.** Reuses the adapter machinery exactly, keeps the page as the gate, spends extra round trips inside a 17s budget so latency becomes the failure mode. Rejected for now; plausible later.

**C. Role-scoped vocabulary, page still narrows within the role.** Smallest fix for the worst asymmetry, but it does not make grouping askable, so it ships a partial fix that cannot be demonstrated.

**D. Reach-out tool that loads another page's bundle by key.** Fastest to implement and codifies the wrong model: the model picks pages, so authorization reasoning and latency both worsen.

## Recommended Approach

### 1. Give derived numbers a machine-readable form without breaking the fact contract

Extend the existing fact shape rather than replacing it (the wire contract and `makeInsight` both require the singular `evidenceId`, so a plural-only fact would be silently dropped):

```
fact: {
  kind: 'count' | 'duration' | 'percentage' | 'amount' | 'date',
  value: string,                 // canonical; compared by exact token equality
  evidenceId: string,            // unchanged: the primary citation, keeps makeInsight's guard satisfied
  unit?: 'days' | 'percent' | 'currency',
  derivation?: 'grouped-by' | 'elapsed-since' | 'ratio-of' | 'sum-of' | 'descriptor-constant',
  derivedFrom?: string[]         // supporting evidence ids; defaults to [evidenceId]
}
```

Every rule that puts a number in prose emits one. Concretely: `groupedCount` emits `{kind:'count', value:String(members.length), derivation:'grouped-by', evidenceId: <the byKey evidence of the first flagged member>, derivedFrom: <byKey evidence of all members>}`; `groupedShare` emits `{kind:'percentage', unit:'percent', derivation:'ratio-of'}`; `staleForDays` and `stuckInStatus` keep the `date` fact and add a `{kind:'duration', unit:'days', derivation:'elapsed-since'}` fact; `ratioBelow`'s percentage becomes a derivation fact instead of a bare value that fails groundedness; `thresholdExceeded` and `zeroOrLowCount` emit `{kind:'count', derivation:'descriptor-constant', value:String(decl.threshold)}` so the constant in their prose is representable.

**Validation branch required.** `factGroundedIn` checks that a fact's value appears inside a cited evidence value's serialization. A derivation fact cannot satisfy that (12 leads are not inside one lead record), so `validateClaims` must validate derivation facts by their own rule (every id in `derivedFrom` is cited by the claim, and `value` is consistent with the declared `derivation`), and must not route them through `factGroundedIn`. Without this branch the new facts are pruned before the resolution rule can see them.

### 2. Reshape the gate so supported numbers survive

Replace "any digit rejects the claim" with a resolution rule: every numeric token in a claim's prose must resolve, by **exact token equality against a canonical scalar value** (not substring containment, which would let "3" match inside a date or an amount), to one of:

- (a) a canonical scalar value of a cited evidence item,
- (b) the `value` of one of the claim's grounded facts, or
- (c) the `value` of a derivation fact whose `derivedFrom` ids are all cited by the same claim, matched with its `unit`.

**Canonicalization is defined, not implied:** scalar extraction from an evidence item's `value` — strings and numbers as themselves, booleans as `'true'`/`'false'`, arrays and objects flattened to their scalar leaves, formatted the same way for comparison and for rendering. Object-valued tool evidence (`{ tool, result }` envelopes) contributes its scalar leaves, so a token can resolve against a row field inside a tool result.

Unresolved numbers still reject the claim. The invariant (zero unsupported values) is preserved; digits in prose stop being a proxy for unsupported values.

**Paths covered:** the two paths that already call `validateClaims` (model briefing claims, and ask answer blocks in `handleAsk`). Deterministic insights and the fallback path (`insightsToClaims`, `respondWithFallback`) stay ungated on purpose, because they are server-computed and the server trusts its own arithmetic. That asymmetry is written down here so a later change does not extend the gate to those paths without first auditing every rule that emits a number.

### 3. Change the prompts, as versioned files

Prompts are one of the cheapest levers in this plan, and four edits are load-bearing:

| File | Change | Why it is required |
|---|---|---|
| `managementBriefing.v1.js:68` | "`text` is qualitative prose only" becomes: text may carry a value only when the claim also emits it as a grounded or derived fact citing its evidence | Otherwise the model self-censors exactly the numbers the new gate is ready to accept |
| `managementAnswer.v1.js` `GROUNDING_RULES` | the same relaxation (bullet 2 currently forbids any count, amount, percentage or duration in prose) | Same reason, on the ask path |
| `managementAnswer.v1.js` tool-mode block | add: "If the question asks for a count, ranking or grouping, call `aggregate`; do not answer such a question from the initial evidence" | This is the instruction that makes the model pick the tool instead of concluding the page has nothing to say |
| `managementAnswer.v1.js` evidence block | label the bundle as the page's *insight evidence*, not the dataset, and include the per-source row counts already present as baselines | Fixes the likeliest cause of today's empty answer: the model treating the evidence block as the whole answer space and returning `claims: []` |

Two more prompt-level requirements that cost nothing and buy honesty:

- tell the model how many rows were examined, using the baselines already in the evidence, so it can say "200 leads examined" rather than implying the whole book was read;
- for a counting question, require the claim to cite the aggregate evidence id, so the number resolves by exact token equality instead of by luck.

**Discipline, so prompt work does not become vibes:**

- **Version the file, do not edit v1.** The repo already conventions this (`assistantTurn.v1.js`, `managementAnswer.v1.js`, `MANAGEMENT_ANSWER_VERSION`). Telemetry stamps the version and eval attribution depends on it surviving, so a prompt change is `managementAnswer.v2.js` plus a version constant, never an in-place edit of v1.
- **A prompt change and its validator change ship in the same release.** Either alone leaves the system disagreeing with itself: a model told to avoid numbers while the gate accepts them, or a relaxed gate while the prompt still forbids them.
- **Every prompt change gets a fixture.** `assistantTurnPrompt.test.js` is the existing pattern; a management answer-prompt test asserting the aggregate instruction and the relaxation stops a later edit silently reverting the behaviour.

What prompts **cannot** fix, and must not be asked to: the missing grouping tool (no wording makes an operation exist), the evidence subset (the model cannot see rows nobody fetched), ranking decisions (deterministic, server-side), or the absence of telemetry. If a proposed fix is "tell the model to try harder", it is not a fix.

### 4. Separate volunteered from askable

The adapter keeps `parseScope`, `loadEvidence`, `computeInsights`, `defaultQuestions`, and gains a declaration of **what can be asked about**: per source, groupable fields, aggregable metrics, bounds. The ask vocabulary is generated from those declarations plus a `tool -> permission` map, filtered server-side by `req.user.permissions`; `isSuperAdmin` (`middleware/auth.js`) grants the full catalogue. The client never supplies vocabulary. `adapter.askTools(scope)` stops being the authorization gate for the ask path; the page still bounds what is volunteered unprompted.

### 5. Add the aggregate primitive

`aggregate({ source, groupBy, metric, filters, limit })` over the declared layer.

- **Read path: the tool layer, not the bundle path.** The bundle path fails a source closed on truncation, which would make the leads aggregate unusable the moment the view exceeds the page size. The aggregate reads through `fetchJson` with the tool bounds (≤1000 rows, byte budget) and returns `truncated` explicitly, so a partial grouping is reported instead of asserted.
- **Bounds:** the three declarations every tool carries (projection, `rowCap`, `resultByteBudget`), plus a scan bound and `redirect: 'error'`.
- **Minimum group size: 3.** Below-minimum groups are dropped and counted in `suppressedGroups`, so a zero is never asserted over data that was examined. Matches the existing precedent (`groupedCount` thresholds 3 and 5).
- **Evidence shape:** each group emits an evidence item with `fieldPaths: ['count']` (and `['share']` where a metric is summed) plus a scalar `value`, mirroring the source-baseline precedent, so group claims pass the substance judge in `managementBriefingEvaluation.js`.
- **Group identity:** `entityRef = { kind: 'group', id: '<source>:<groupBy>:<key>' }`.
- `searchManagementKnowledge` stays a separate retrieval tool and is **new work**; `toolRegistry.js` currently registers only `getLead`, `listLeads`, `listInvoices`.

### 6. Logging that makes the next session cheap

- Per-step trace events: `{step, tool, argsShape, rowCount, resultBytes, latencyMs, outcome}`. `history` is in-memory and discarded today, so a 4-step ask leaves no record of which tools ran.
- Decision rows for the aggregate path: groups emitted, suppressed, or ranked out, with reason codes.
- `x-request-id` propagation on outbound fetches. `forwardActorHeaders` sends only `x-user-*`, so evidence and tool reads reach the domain service with a fresh id and cannot be joined to the turn that made them.
- Management-surface usage telemetry: reuse `AssistantEvent` with additional `eventType` values rather than a new table.

| Ranking, diversity, suppression state, retention, scheduler | The companion design's own phases. The wedge ships only the trace emit and decision rows it needs for telemetry. |

## Open Questions

1. **Which fields become groupable, per source.** The semantic layer's real work; needs a per-domain review, not inferable from descriptors.
2. **Minimum group size per source.** 3 everywhere, or lower for a low-volume source, and who signs that off.
3. **Sources that cannot group in-process.** Which need a new endpoint plus an IAM `run.invoker` grant and a deploy order. `lead-service` already exposes `GET /api/v1/leads/stats` (`lead.routes.js:48`) for fixed aggregates.
4. **Whether the 200-row truncation fail-closed behaviour should change**, or whether the aggregate path simply routes around it permanently. Changing it alters panel semantics for every paged source, so it is a separate decision.
5. **Decision-row retention window**, and whether it needs a scheduler that does not exist yet.

## Success Criteria

- A fixture proves the wedge question ("which destinations have the most leads?") returns at least one count-bearing claim citing evidence, on the leads page, where ask mode declares no grouping tool today.
- A second fixture proves the same shape on a different source, so the primitive is not special-cased to leads.
- A fixture proves an **unsupported** number still rejects the claim, and that a substring match does not pass (the "3 inside a date" case).
- A fixture proves a below-minimum group is omitted and reported as `suppressedGroups`, never rendered as a zero.
- A fixture proves a derivation fact survives validation while a bare ungrounded number in the same shape does not.
- A fixture proves a group claim passes `judgeBriefingSubstance`, which pins the `fieldPaths` requirement.
- Zero unauthorized evidence in any answer payload, asserted through the aggregate path.
- **Latency mechanism:** the fixture asserts the wedge question completes within one tool call. Wall-clock is sampled manually at demo time (the suite has no timing baseline today), and p95 becomes computable from the trace rows once they land, which is the point of shipping them.
- **Post-deploy smoke check passes** (mandatory under the lockstep rollout decision): on the released build, the copilot on `/leads` answers one counting question with a count-bearing, evidence-citing answer, and the panel renders ranked insights. This is the replacement for the build-time drift guard, so a release that ships without it is unverified.
- **No critical is ever hidden by the new ordering:** a fixture asserts that a `critical` insight is never out-ranked by an `info`, and that the critical band is not budgeted (it is bounded by `CRITICAL_CEILING` with overflow reported as `suppressedCriticals`).

## Distribution Plan

Web service; the existing pipeline covers it (`microservices-ci.yml` builds and tests on PRs touching the service, `deploy.yml` deploys to Cloud Run). No new distribution channel.

**Rollout decision (approved 2026-09-12): lockstep, with downtime tolerated.** The contract rename and the reshaped response ship together, across both halves, in one release. The two halves do not share deploy machinery (Management ships via Firebase Hosting, the service via Cloud Run), so no ordering guard is imposed and a short window of a broken panel is accepted. Two consequences carried deliberately:

## Reviewer Concerns

Recorded after three adversarial review rounds on 2026-09-12 ("if you had 48 hours", no; this is an independent reviewer that saw only the document). These are unresolved implementation details, not disagreements about direction. Each needs an answer before code, and each was found by checking the draft against the repository rather than by reading it.

1. **Tool results do not reach the evidence set with citations.** `historyToEvidence` (`agentRunner.js`) wraps each tool result as one `computed` item with no `fieldPaths`, and `judgeBriefingSubstance` only accepts items carrying `fieldPaths`. So every aggregate or group claim fails the substance judge until either the runner emits per-group evidence items or the judge accepts a declared tool-evidence contract.
2. **Derivation facts need a plural home.** `makeInsight` sets a single `insight.fact`, and the wire fact schema requires `kind`, `value`, `evidenceId`. Adding a duration fact beside the existing date fact requires pluralizing the insight fact to `facts[]` across `makeInsight`, `insightsToClaims`, and the deterministic schema.
3. **`derivedFrom` must not be the member list.** Citing every member's evidence to justify a grouped count collides with the per-claim citation rule and with the 200-item evidence budget and its second-pass pruning. The count should ride one aggregate evidence id instead.
4. **`truncated` needs an upstream total.** `fetchJson` discards `pagination.total` and `boundResult` flags only local overflow, so a capped read can present a partial count as complete. Reading the upstream total, where the endpoint provides one, is required for the aggregate's honesty claim.
5. **Derivation checks are not yet predicates.** "Value consistent with the declared derivation" needs one concrete check per kind (`ratio-of`, `elapsed-since`, `sum-of`, `descriptor-constant`), or the unverifiable kinds should be dropped.
6. **Prose token extraction and number formatting are undefined.** Canonicalization was specified for evidence values only. The prose side needs an extractor plus a shared formatter so `₹1,500` resolves against a canonical `1500`.
7. **Ordering must be in scope.** The wedge question ("most leads") is an ordering question, but ordering and tie-breaks were deferred along with ranking and the `limit` parameter. Without a specified deterministic order, the fixture is nondeterministic.
8. **The generation schemas cannot express the new fact fields.** Both flat schemas expose only `kind`, `value`, `evidenceId`, so the model cannot emit `unit`, `derivation`, or `derivedFrom` until those properties are added to `managementBriefing.v1.js` and `managementAnswer.v1.js`.

## NOT in scope

- **Streaming answers.** A transport change across the gateway and both clients; every schema in the stack is one JSON body. Separate re-platform decision.
- **Proactive or background agents.** There is no scheduler, worker or queue, and instances scale to zero. The scheduler this plan adds is for decision-log retention only, not for background work.
- **Executing write actions.** Action descriptors are declarative; phase 3 designs preview and confirm, and it is not in this plan.
- **Cross-page reach** (role-derived catalogue plus semantic layer). Train 2's own changes 4 and 5; this review covers the contract and the numeric rule, not the vocabulary model.
- **Changing the 200-row fail-closed truncation itself.** The aggregate routes around it (PERF-1A groups over loaded rows and threads the upstream total). Changing panel semantics for every paged source is a separate decision.
- **Derived criticality bands (§6.5).** Deferred per page until a rubric owner signs the bands.
- **Multi-provider routing and agent frameworks.** Rejected with named revisit triggers in the ranking doc §11.

## What already exists (reuse, do not rebuild)

- **Grouping.** `groupedCount` and `groupedShare` in `adapters/rules.js` already group in process over `bundle.records`. The aggregate reuses them rather than introducing a query layer.
- **Gate layers L1 and L2, partly.** `makeInsight` already drops uncited insights, and the bundle already classifies sources into `unavailableSources` / `notAuthorizedSources`.
- **Bounded reads.** `engineLimits()` (rows, bytes, evidence), `boundResult` (projection, row cap, byte budget), `fetchJson` (redirect refusal, per-target ID token) all exist.
- **Citation-capable evidence precedent.** Source baselines already carry `fieldPaths: ['recordCount']` with a scalar value, exactly the shape group evidence needs.
- **Client-side severity ordering.** `claimsIn` already sorts the attention section critical → warning → info; the server change makes band ordering global rather than section-local.
- **Validation on both paths.** `handleAsk` already routes `answerBlocks` through `validateClaims`, so §9.9.3 is a parameter change, not new plumbing.
- **Prompt versioning and the eval harness.** `*.v1.js` modules, `managementBriefingEvaluation.js` with canned fixtures, and `npm test` running in CI for this service.

## Failure modes

| Path | Failure | Tested? | Handled? | Operator sees |
|---|---|---|---|---|
| Scorer | malformed insight (missing `severity`) | T1 | must default, never throw | nothing, if it defaults correctly |
| Suppression read | DB blip on the `InsightState` read | T2 | **must fail open** — show everything | everything, briefly over-shown. Failing closed would blank the panel on a blip, strictly worse |
| Acknowledgement write | DB error on `/seen` | exists | awaited, surfaces as 5xx | a failed acknowledgement the operator retries |
| Decision-row write | DB error | T2 | fire-and-forget, never fails the response | nothing |
| Trace emit | logger/DB error | T2 | fire-and-forget | nothing |
| Aggregate precompute | domain service slow or down | T1/T3 | bounded slice of the 17s, then answer with what arrived, labelled | a partial or labelled partial answer |
| Aggregate read | truncated upstream | T1 | `truncated` from the upstream total | a labelled partial count, never a confident wrong one |
| Numeric resolution | model emits an unsupported number | T1 | claim rejected | no answer, never a fabricated number |
| Model-claim gate | L3 would demote every claim | T1 | `origin` discriminator skips L3/L4 for model claims | a normal answer |
| Role catalogue | role resolves to an empty vocabulary | T1 | explicit "not available for your role" state | a clear message, not a silent no-tools panel |
| `x-user-permissions` | malformed header JSON | T1 | Zod validation, fail closed to `[]` | a permission-shaped failure, not a 500 |
