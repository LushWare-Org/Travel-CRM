# Design: Granular AI Itinerary Generation — Per-Day and Partial Trip Controls

## Problem Statement
Both `CustomizePackageContainer` and `PlanYourTripContainer` offer only whole-trip AI generation: one "Regenerate with AI" button that replaces *all* itinerary days at once, plus an "Add Day" button that creates a blank day the user fills manually. There's no middle ground. A user who likes 4 out of 7 AI-generated days but wants to regenerate day 3, or who manually added 3 days and wants AI to fill in only the remaining 4, has to either accept the whole AI output and manually fix the parts they don't like, or build the entire trip by hand. The current UX forces an all-or-nothing choice between AI and manual.

## Demand Evidence
This is a product-intuition call informed by the existing shipped AI workflow. The whole-trip "Regenerate with AI" button already works and is exposed to prospects. The gap is observable: a user who adjusts day content after AI generation and then clicks "Regenerate" loses all manual edits. That's a friction pattern the current UI creates but doesn't solve.

## Status Quo
Today, the user's options for each day are:
1. Click "Regenerate with AI" to replace ALL days (loses any manual edits).
2. Click "Add Day" to add a blank day and fill it entirely by hand.
3. Manually edit individual fields (title, activities, locations) within an AI-generated or hand-built day.

There is no "regenerate just this day" or "fill in this blank day with AI" or "add N more days with AI" capability.

## Target User & Narrowest Wedge
The prospect on `PlanYourTripContainer` or the admin customizing on `CustomizePackageContainer` who has a partial itinerary (some days done, some blank or unsatisfying) and wants AI to fill or improve specific days without touching the rest.

The narrowest wedge: a single "Regenerate this day with AI" button per day card, calling a new endpoint that generates exactly 1 day given the trip context plus that day's position.

## Constraints
- The existing `generateItineraryPreview` endpoint generates a full N-day array. A per-day endpoint is a new backend route.
- The `generateDaysArray` helper already handles single-day generation (it pads shortfall), but the prompt and schema are designed for multi-day output. A per-day prompt should be cheaper (fewer tokens) and more focused.
- Both `PlanYourTripContainer` and `CustomizePackageContainer` share the `useAIItineraryGenerator` hook, which currently replaces all days on completion. Per-day generation needs either a second hook or extending the existing one.
- Rate limiting: per-day generation will make more frequent, smaller API calls. The existing `generate-itinerary-preview` uses its own `aiItineraryPreviewLimiter` (5/15min/IP), while `itinerary-chat` and `wizard-turn` share `itineraryChatLimiter` (30/15min/IP). The new per-day and range endpoints should get their own limiter or share one of these. A 7-day trip with per-day regeneration = 7 calls; a 14-day trip = 14 calls. Either limiter ceiling accommodates this, but sharing the chat limiter (30/15min) is safer to avoid starving the whole-trip preview's tighter budget.
- Both containers are already large files (~1000+ lines each). New UI should minimize additions.

## Premises
1. **Users will commonly want to regenerate or AI-fill individual days, not just whole trips.** The current whole-trip regeneration destroys manual edits; per-day generation preserves them. This is a standard pattern in itinerary tools (Google Trips, Wanderlog both allow per-day editing/regeneration).
2. **A single-day AI call should be aware of the other days in the trip** to avoid duplicate locations/activities and maintain narrative flow (e.g., don't suggest the same museum on day 3 that's already on day 1).
3. **The existing gateway rate limits are sufficient** for per-day calls. The new endpoints should share `itineraryChatLimiter` (30/15min/IP) rather than `aiItineraryPreviewLimiter` (5/15min/IP), since a user regenerating several days in a session needs headroom. Even an aggressive user regenerating every day of a 14-day trip = 14 calls, well under 30.
4. **Per-day generation and "add days with AI" are the two operations needed.** "Regenerate a range of days" (e.g., days 3-5) is a nice-to-have that can be expressed as sequential single-day calls without a dedicated endpoint.

## Approaches Considered

### Approach A: Per-Day Endpoint (Minimal Viable)
**Summary:** Add a single new endpoint `POST /packages/generate-day-preview` that generates exactly 1 itinerary day, given destination, day number, total duration, travelers, preferences, and an array of existing days (so the AI avoids duplication). Client gets a new `useAIDayGenerator` hook that replaces/fills a single day in place. Each day card gets a small sparkle button.

**Effort:** S (1 new endpoint, 1 new prompt file, 1 new hook, button additions in 2 containers)
**Risk:** Low
**Pros:**
- Simplest backend change: one endpoint, one prompt, one schema
- Preserves user edits on all other days
- Reuses existing `generateStructured` and `geminiClient` infrastructure
- Each call is cheap (single day = ~200 output tokens vs ~800+ for a full trip)

**Cons:**
- No "add 4 days at once with AI" in this approach (user would add blank days then regenerate each one)
- Sequential per-day calls for bulk operations (not a UX problem, just slightly slower)

**Reuses:** `generateStructured`, `geminiClient`, `normalizeAIDays`, `buildDayState`/`buildItineraryDayFromAIDay` mappers, gateway `itineraryChatLimiter`

### Approach B: Per-Day + Bulk Add (Ideal Architecture)
**Summary:** Everything in Approach A, plus a second endpoint `POST /packages/generate-days-preview` that generates N days (a sub-range) in one call. Client gets both per-day regeneration buttons AND a "Generate N days with AI" button that appears when there are unfilled day slots (e.g., trip is 7 days but only 3 are planned). The bulk endpoint receives the existing days so the AI fills gaps coherently.

**Effort:** M (2 new endpoints, 2 new prompts, 2 new hooks, UI additions in 2 containers)
**Risk:** Low-Medium
**Pros:**
- Covers both use cases: "fix this one day" and "fill in the rest with AI"
- Bulk generation is a single API call (faster UX for adding multiple days)
- The "Generate remaining days" button is a natural progression from the current "Add Day" button
- Context-aware: AI sees existing planned days and fills gaps without duplication

**Cons:**
- Two new endpoints instead of one
- Bulk endpoint's prompt needs to handle variable-length input (existing days) and output (new days only)
- Slightly more complex hook logic (single vs batch mode)

**Reuses:** Same as Approach A. Note: `generateDaysArray` is NOT safe to reuse directly for sub-ranges because its shortfall-padding logic numbers placeholders from `days.length + 1` (head-anchored), which corrupts non-head-anchored ranges (e.g., filling days 4-7 when the model returns only 3 days would produce a placeholder numbered 4, duplicating it). The range controller must call `generateStructured` directly and map returned days positionally onto the requested dayNumbers.

### Approach C: Extend Existing Endpoint with Day Filter
**Summary:** Add an optional `dayNumbers` filter to the existing `generate-itinerary-preview` endpoint. When present, only the specified days are regenerated; existing days are passed as context. No new endpoint, just a request schema extension.

**Effort:** S
**Risk:** Medium
**Pros:**
- No new routes or controllers
- Single endpoint handles whole-trip, per-day, and range generation

**Cons:**
- Overloads the existing endpoint's contract; callers that expect N-day output now get variable output
- Harder to test: the same endpoint behaves differently with vs without the filter
- Existing E2E contract specs (`wizardTurn.test.ts`, `itineraryChat.test.ts`) cover the current shape; changing it risks regressions
- Prompt complexity: one prompt must handle "generate all days" and "generate day 3 given days 1,2,4-7" modes

## Recommended Approach
**Approach B (Per-Day + Bulk Add)** because it covers both real use cases (regenerate one day, fill in remaining days) with clean separation. The incremental cost over Approach A is one additional endpoint and prompt file, which is cheap relative to the UX gain. Approach C was rejected: overloading a working endpoint with mode-switching is the kind of hidden complexity that produces regressions.

### Implementation shape

**Backend (package-service):**

1. **New prompt file:** `ai/prompts/generateDayPreview.v1.js`
   - `buildGenerateDayPreviewPrompt({ destination, dayNumber, totalDuration, travelers, preferences, existingDays })` — generates a single day, receives the existing days array as context so the AI avoids repeating locations/activities.
   - `generateDayPreviewResponseSchema` — same shape as one element of `generateItineraryPreviewResponseSchema.days.items` (dayNumber, title, locations, activities, meals, transport).

2. **New prompt file:** `ai/prompts/generateDaysRange.v1.js`
   - `buildGenerateDaysRangePrompt({ destination, dayNumbers, totalDuration, travelers, preferences, existingDays })` — generates N specified days, given existing days as context.
   - `generateDaysRangeResponseSchema` — `{ days: [...] }` matching the existing preview schema.

3. **New controller functions** in `aiPackage.controller.js`:
   - `generateDayPreview` — validates input with Zod, calls `generateStructured` with the single-day prompt, forces `dayNumber` to the requested value (ignoring model output), returns `{ day: {...} }`.
   - `generateDaysRangePreview` — validates input with Zod, calls `generateStructured` directly (NOT `generateDaysArray`, whose head-anchored padding corrupts sub-ranges), maps returned days positionally onto the requested `dayNumbers` array (forcing each `dayNumber` to the corresponding requested slot), returns `{ days: [...] }`. On shortfall, unfilled slots are omitted from the response (the client re-shows the CTA) rather than padded with blank placeholders.

4. **New routes** in `package.routes.js`:
   - `POST /packages/generate-day-preview` — public, rate-limited at gateway via `itineraryChatLimiter`.
   - `POST /packages/generate-days-preview` — public, rate-limited at gateway via `itineraryChatLimiter`.

5. **Gateway allowlist** in `Services/gateway/src/index.js`:
   - Both `POST /api/v1/packages/generate-day-preview` and `POST /api/v1/packages/generate-days-preview` must be added to `PUBLIC_PATTERNS` (POST) alongside the existing `generate-itinerary-preview`, `itinerary-chat`, and `wizard-turn` entries. Without this, unauthenticated prospects on `PlanYourTripContainer` get 401s.

6. **Shared contract** in `Services/shared/contracts/src/`:
   - `GenerateDayPreviewRequest` / `GenerateDayPreviewResult` Zod schemas
   - `GenerateDaysRangePreviewRequest` / `GenerateDaysRangePreviewResult` Zod schemas

**Frontend (Client):**

1. **New API client:** `services/api/aiDayGeneration.ts`
   - `generateDayPreview(params)` — single day
   - `generateDaysRangePreview(params)` — day range/batch

2. **New hook:** `features/planner/hooks/useAIDayGenerator.ts`
   - `generateDay(dayNumber)` — regenerate or fill a single day in place. Merge contract: the returned day is applied positionally, forcing `dayNumber` to the requested slot value regardless of what the model returned. Other days and their edits are untouched.
   - `generateDays(dayNumbers)` — generate multiple days at once (for "fill remaining" button). Same positional merge: each returned day is matched to the corresponding requested dayNumber.
   - Returns `{ isGenerating, generatingDayNumber, error, generateDay, generateDays }`
   - `generatingDayNumber` tracks which specific day is loading (for per-day spinner)

3. **UI additions in `PlanYourTripContainer`:**
   - Per-day: small sparkle button in each day card header (next to the delete button), calls `generateDay(dayNumber)` for that day
   - Bulk: "Generate remaining days with AI" button appears when `itineraryDays.length < duration` and there are unfilled slots. Requested dayNumbers are computed as `{1..duration} \ {existing dayNumbers}` (set difference).
   - Per-day loading state: the specific day card shows a spinner overlay while its day is being generated; other days remain interactive

4. **UI additions in `CustomizePackageContainer`:**
   - Same per-day sparkle button in each day override card
   - "Generate remaining days with AI" button when `dayOverrides.length < (pkg?.duration_days ?? 0)`. Note: `CustomizePackageContainer`'s `handleRemoveDay` removes by array index without renumbering, so after deleting a middle day the state can have non-contiguous dayNumbers. The remaining-days computation must use set difference `{1..duration} \ {existing dayNumbers}`, not a naive tail computation.
   - Same per-day loading state pattern

**Prompt design for context-awareness (Premise 2):**
The single-day prompt receives `existingDays` as a JSON summary (day number, title, locations, activities) so the model knows what's already planned and avoids duplication. **The target day being regenerated is excluded from `existingDays`** (server defensively filters it out even if the client sends it) to prevent the model from echoing the old content back. Example:
```
Generate Day 3 of a 7-day trip to Bali. Travelers: 2. Preferences: adventure, local food.

Already planned days — excluding Day 3 (do NOT repeat these locations or activities):
- Day 1: Arrival in Ubud — locations: Ubud Palace, Tegallalang Rice Terrace; activities: temple visit, rice terrace walk
- Day 2: Ubud Waterfalls — locations: Tegenungan Waterfall, Tibumana Waterfall; activities: waterfall hike, lunch at warung
- Day 4: Beach Day — locations: Seminyak Beach; activities: surfing lesson, sunset dinner

Generate a complete day 3 that flows naturally between Day 2 and Day 4.
```

## Open Questions
- Should per-day regeneration show a confirmation dialog ("Replace this day's content?") like the whole-trip regeneration does, or just replace silently since it's a single day and easy to undo by re-editing? Lean toward silent replacement with a brief toast notification.
- Should the "Generate remaining days" button appear as a prominent CTA or a subtle secondary action? Depends on whether the user flow is "add days manually then optionally AI-fill" or "AI-fill first then manually adjust."

## Success Criteria
- A user can regenerate any single day without affecting other days.
- A user can add blank days and then AI-fill them individually or in batch.
- The AI-generated day content avoids duplicating locations/activities from existing days.
- Per-day generation completes in under 5 seconds (single day is ~200 output tokens).
- All new endpoints are rate-limited under the existing gateway budget.

## Dependencies
- No new service dependencies. All work is in `package-service` (backend) and `Client` (frontend).
- Reuses existing `geminiClient`, `generateStructured`, `normalizeAIDays` infrastructure.
- **Gateway:** both new POST routes must be added to `PUBLIC_PATTERNS` in `Services/gateway/src/index.js` (same as existing `generate-itinerary-preview`, `itinerary-chat`, `wizard-turn`), plus the limiter-proxy mounts. Without the allowlist entry, unauthenticated prospects get 401s.

## The Assignment
Before building this, use the existing "Regenerate with AI" button on a real 5+ day itinerary in the live Client app. Manually edit 2-3 days after generation, then hit "Regenerate" and watch your edits disappear. That's the pain this feature solves. Write down which days you wanted to keep and which you wanted to regenerate. That list is the acceptance test for the per-day feature.

## UI/UX Specifications

Added by /plan-design-review on 2026-09-04 (design completeness 4/10 → 8/10).

### Information architecture
- Per-day: sparkle button (`Sparkles` icon + tooltip/aria-label "Regenerate day N") in the day-card header, left of the delete button.
- Bulk: "Generate remaining days with AI" is a subtle secondary/ghost button below the day list (not in the header), shown only when unfilled slots exist.

### Interaction states
| Feature | Loading | Empty | Error | Success | Partial |
|---------|---------|-------|-------|---------|---------|
| Per-day regenerate | full-card dim overlay + centered spinner (target day blocked, others interactive) | n/a (button always present) | inline error near the button, day content untouched | toast with Undo | n/a |
| Bulk fill remaining | spinner on the CTA; filling cards show per-day overlay | CTA hidden when no unfilled slots | inline error near CTA | toast with Undo | unfilled slots omitted; CTA re-shows; inline note "N of M days generated" |

### Responsive & accessibility
- Both new buttons are real `<button>` elements, 44px minimum touch target.
- Sparkle button: `aria-label="Regenerate day N"`; tooltip on hover/focus.
- Spinner overlay: `aria-busy="true"` + screen-reader announcement on the regenerating card.
- Undo toast: `role="status"` `aria-live="polite"`.
- Contrast: body text >= 16px / 4.5:1 (already enforced by existing tokens).

### User journey (storyboard)
1. User regenerates the full trip, likes 4 of 7 days, dislikes day 3 → feels stuck under the current all-or-nothing UI.
2. Clicks the sparkle on day 3 → day 3 dims with a spinner, other days stay interactive → feels in control.
3. New day 3 arrives → toast "Day 3 regenerated — Undo" → feels reversible.
4. If worse, clicks Undo → prior content restored → feels trusted.
