## Problem Statement
Today's AI chatbot (`wizard-turn`/`itinerary-chat`) only exists inside one tab of the trip-planner. Everywhere else on the public Client site, visitors browse unassisted — no navigation help, no instant policy/FAQ answers, no way to search packages without manually clicking through. The ask: a floating button present on every public page that can navigate, fetch package details, and eventually do "almost everything," built on a deterministic, future-proof tool-calling architecture, not a one-off widget.

## Demand Evidence
Not measured. User confirmed this is a forward bet, not a reaction to observed pain: no funnel data, no support-ticket volume, no direct observation of a visitor hitting this specific wall. Phase 1 must be instrumented to prove the bet before phase 2/3 get built (Premise 1a).

## Status Quo
Visitors browse manually with no assistance outside the planner tab. No measured drop-off number exists yet.

## Target User & Narrowest Wedge
Target: anonymous visitors on public browsing pages (`/`, `/packages`, `/package/:id`, `/destinations-international`, `/about`, `/contact`, `/career`) — not the auth-adjacent pages (`/login`, `/my-account`), not `/planner` (see Constraints' coexistence rule — that's where `TripWizardPanel`/`ItineraryChatPanel` actually mount), and not `/package/:id/customize` (a separate, conservative exclusion: it's a `PAGE_CONFIG.planner`-gated conversion-form funnel page with no chat surface of its own — the widget is excluded here to avoid competing with that funnel, not because of a chat-surface collision).

Wedge (after one round of pushback — see Premises #2): visitor initially wanted nav + package search + lead capture + policy Q&A + extensible future actions shipped together in one release ("full autonomous everything"). Revised to a phased build on one architecture: **Phase 1 — navigation + FAQ/policy Q&A** ships first and alone; Phase 2 adds package search/detail fetch; Phase 3 wires in lead-capture (reusing the already-shipped `POST /leads/internal/intake` pipeline). Each phase is independently shippable and used to gate the next.

## Constraints
- Must reuse `wizard-turn`'s existing deterministic tool-calling pattern (model selects from a fixed, server-executed, Zod-validated tool vocabulary; model never authors prices/policy text, never produces an executed action directly) — this is both the existing convention and what 2026 industry practice recommends over trusting a model's raw output.
- Site-wide surface is a materially larger attack surface than the closed wizard-turn conversation: an assistant reachable from package-detail pages will eventually read user-generated content (package descriptions, reviews) once phase 2 lands, making it a live indirect-prompt-injection target. Hardening (instruction/content separation, tool-output allowlisting, never rendering raw HTML/links from model output) is required from phase 1, not deferred.
- Navigation must be client-side only: the model requests a named route from a fixed allowlist; the client's own router executes it. No server-side redirects, no raw URLs/HTML from model output ever become an executed action.
- **Nav allowlist is derived from `Client/src/config/pages.ts`'s `PAGE_CONFIG`, not hardcoded separately.** `PAGE_CONFIG` today only holds `enabled` booleans per feature — the logical-name→path mapping the model needs (e.g. "destinations" → `/destinations-international`) currently lives hardcoded in `App.tsx`'s `handleNavigate` and the Header/Footer nav configs. This design adds one shared table (name, path, `enabled` flag sourced from `PAGE_CONFIG`) that both `App.tsx`'s route registration and the assistant's tool-vocabulary/allowlist read from — real net-new work, not a lookup into something that already exists in that shape. A route whose `enabled` flag is false is excluded from both the model's tool-vocabulary prompt and the client's executable allowlist — otherwise the assistant can confidently "navigate" a visitor to a page that silently bounces them to the homepage, which reads as broken.
- **Launcher placement vs. the existing floating-action stack.** `MainLayout` already renders `FloatingActionStack` (WhatsApp/Call/scroll-to-top, fixed bottom-right) on every public page. The new launcher must stack above/beside it without covering WhatsApp — the primary existing conversion surface — not simply mount at the same fixed corner. Concrete offset/z-order is implementation detail for `/plan-eng-review`, but the constraint (never obscure the WhatsApp button) is a phase-1 design requirement, not a nice-to-have.
- **Coexistence with the existing `/planner` in-tab wizard:** the floating widget does not mount on `/planner` — that page already has its own wizard/chat surface (`TripWizardPanel`/`ItineraryChatPanel`). Two independent chat surfaces on one page is a UX and a policy-answer-drift risk (see Consistency note below). The widget's own nav allowlist may still include `/planner` as a *destination* other pages can route to.
- No new AI framework/SDK — "state of the art, future-proof" is satisfied at the tool-contract layer (versioned, additive Zod tool vocabulary), not by adopting a trendy agent framework that will churn.
- Gateway remains the single public entry point; the assistant's backend must sit behind it like every other service, mirroring the existing `/api/v1/packages/wizard-turn` mount shape (own path prefix, added to gateway's `PUBLIC_PATTERNS`). Rate limiting: shares the existing `itineraryChatLimiter` instance (30 req/15min/IP) rather than a new one — see Turn Protocol below for the accepted consequence (a visitor's assistant use and planner-tab use draw from the same per-IP budget).
- Existing lead-intake pipeline (`POST /leads/internal/intake`, `internalTokenAuth` / `INTERNAL_EVENTS_TOKEN`, `PENDING_VERIFICATION` status) is reused as-is in phase 3 — not rebuilt.
- **Two internal-token conventions already exist in this codebase and must not be conflated:** `INTERNAL_SERVICE_KEY` gates user-service's `/internal/policy-documents` (checked via `x-internal-token` in `admin.routes.js`) — this is the convention `answer_faq_policy` calls into. `INTERNAL_EVENTS_TOKEN` gates lead-service's `/internal/events`, `/internal/facebook-lead`, `/internal/communication-logs`, `/internal/intake` — this is the convention phase 3's lead-capture call uses. `assistant-service` is a client to both, using whichever token matches whichever downstream service it's calling.

## Premises
1. This is a forward bet — validated by usage data after each phase ships, not a reaction to measured pain.
   1a. **Revised per Codex challenge:** the decisive unknown is entry (will anyone on a random page even open a site-wide widget), which is testable at the placement layer independent of the AI layer. Phase 1 therefore ships with the Telemetry Contract below and a go/no-go bar resolved to a concrete number *before* shipping, so phase 2 is gated by real data, not informal impression.
2. "State of the art, future-proof" means keeping the existing deterministic tool-calling pattern, not chasing an agent framework — matches 2026 best practice (neurosymbolic/tool-call guardrails over pure-prompt trust).
3. Site-wide surface is newly exposed to indirect prompt injection (reads UGC in phase 2+, can trigger navigation) — hardening is first-class from day one.
4. The floating widget is a thin client over new/extended backend tool endpoints reusing wizard-turn's existing model/tool-execution pattern — no rewrite. ("Reused" means the *pattern* — Gemini client, Zod-validated structured-output schema, tool-execution dispatch shape — is ported into `assistant-service`; each tool's actual downstream integration is spec'd per-tool below, since not every wizard-turn tool has an existing internal HTTP endpoint to call as-is.)
5. Navigation is client-side only, executed by the client router against a named-route allowlist derived from `PAGE_CONFIG` — never a server-side redirect or raw model-output execution.

**Scope override note:** user's initial choice was "full autonomous everything in one release." Pushed back once (platform-vision trap, bigger diff, slower first feedback, future-proofing capabilities nobody asked for yet); user revised to a phased build on one architecture. Logged as an accepted scope call.

**Service-boundary re-validation (added post-review):** Approach B's payoff (calling other services as an internal HTTP client per tool) only materializes once phase 2/3 add tools with genuine cross-service targets — phase 1's only tool with a backend call (`answer_faq_policy`) calls user-service directly, a single-hop internal client any service could make. If phase 1's go/no-go bar fails, `assistant-service` becomes a stranded deployable (health checks, CI, gateway route, Terraform) for two tools. This is an accepted, logged risk (see Recommended Approach) — re-check the service-boundary choice at the phase-1→2 gate, not after phase 3 ships.

## Approaches Considered

### Approach A: Extend package-service (minimal)
New `/assistant-turn` endpoint in `package-service`, sibling to `wizard-turn`, sharing its Gemini client/tool-execution helpers directly.
**Effort:** S-M | **Risk:** Low
**Pros:** fastest to ship, reuses proven code paths directly, smallest diff, easiest rollback; phase 1's actual dependency (user-service's `/internal/policy-documents`) is called exactly the same way whether the caller is package-service or a new service, so A loses none of phase 1's real capability.
**Cons:** `package-service` becomes the catch-all AI brain even as phase 2/3 add tools that logically belong to other domains (lead-service, booking-service); a second migration is likely once cross-service tools arrive — mitigated by the additive Zod tool-vocabulary contract making that extraction mechanical, not a rewrite.
**Reuses:** wizard-turn's Gemini client, tool-execution helpers, Zod tool-vocabulary pattern, and its existing `INTERNAL_SERVICE_KEY` call into user-service's policy-documents endpoint (`fetchPolicyDocuments`) plus its local `retrieveSnippets` matcher — both ported as-is, not reinvented.

### Approach B: New assistant-service (chosen, with re-validation gate)
A new microservice, `assistant-service` (:3011), owns the tool-calling harness generically — holds the model client and fixed Zod tool vocabulary, calls other services (user-service, package-service, lead-service) as an internal HTTP client per tool, the same way gateway routes CRUD per service but for AI turns instead.
**Effort:** M-L | **Risk:** Medium (new deploy target, new gateway route, new internal-auth wiring on day one)
**Pros:** matches how the rest of this codebase is already organized (one thing per service); scales cleanly across service boundaries as tools grow in phase 2/3; doesn't retrofit package-service into an AI-orchestration role it wasn't designed for.
**Cons:** bigger phase-1 diff than A; a new deployable adds real ops overhead (health checks, CI, gateway route) for just 2 tools on day one; if phase 1's go/no-go bar fails, this deployable is a total loss where A would only strand one endpoint (see Service-boundary re-validation note in Premises).
**Reuses:** wizard-turn's Gemini client/tool-execution pattern (ported, not rewritten); `INTERNAL_SERVICE_KEY` convention to call user-service's `/internal/policy-documents` for `answer_faq_policy`; `INTERNAL_EVENTS_TOKEN` convention (phase 3) to call lead-service's `/internal/intake`; gateway's per-service routing precedent.

### Approach C: Static widget first, zero AI (entry-test — rejected)
Floating button + panel with hardcoded nav links and client-side fuzzy FAQ search, no model call, pure entry/placement validation.
**Rejected because:** doesn't test the actual value prop (AI understanding intent); a null result would be ambiguous (bad placement vs. no interest in AI help); user chose to keep the model live in phase 1 and validate via telemetry instead (Premise 1a) rather than via a throwaway placebo widget.

## Recommended Approach
**Approach B (assistant-service)**, phased, with the service-boundary re-validation gate from Premises:

- **Phase 1:** `assistant-service` ships with 2 tools:
  - `navigate(route)` — client-router-executed, allowlist derived from `PAGE_CONFIG` (excludes disabled routes, `/login`, `/my-account`, `/planner`'s wizard surface per the coexistence constraint, though `/planner` itself is a valid navigation *destination*).
  - `answer_faq_policy(question)` — `assistant-service` calls user-service's existing `GET /internal/policy-documents` (`x-internal-token = INTERNAL_SERVICE_KEY`, the actual existing convention — corrected from an earlier draft that misattributed this to a non-existent package-service endpoint), then runs the same `retrieveSnippets()` matcher wizard-turn already uses (ported into `assistant-service` verbatim, or exposed as a shared package if duplication becomes a problem — not blocking for phase 1). **No-match fallback (ported from wizard-turn verbatim, not optional):** when `retrieveSnippets()` returns `[]`, the server overrides the model with wizard-turn's exact existing `FALLBACK_POLICY_MESSAGE` constant — "I don't have a confirmed answer to that — please reach out and our team will help." (plus its structured `supportEmail`/`whatsappNumber` fields) — instead of letting the model compose policy prose from parametric memory. Reusing the identical string (not a paraphrase) matters here specifically because the coexistence constraint above flags policy-answer drift risk between the two surfaces — they must say the same thing when they don't know the answer.
  - **Turn protocol:** one structured model call per user message, same envelope shape as wizard-turn (single `tool` + `args` + assistant `message` per turn — no multi-tool-per-turn, no server-side loop). If a user's message plausibly needs both an answer and a navigation ("take me to the refund page and summarize it"), phase 1 handles this as two sequential turns, not one — the model is instructed to pick the single most useful action per turn, and the client always allows sending a follow-up message immediately. Rate limit: shares `itineraryChatLimiter` (30 req/15min/IP) with `wizard-turn`/`itinerary-chat` — a visitor deep in a planner-tab conversation who also opens the floating assistant draws from the same ceiling; accepted for phase 1, revisit if Telemetry Contract data shows real contention.
  - Client gets a new `AssistantWidget` (floating launcher + panel) mounted once in Client's root layout on public browsing routes only (see Target User).
  - **Degraded-state UX:** on a 503 from `assistant-service` or a 429 from the shared `itineraryChatLimiter`, the panel shows an inline error using the same pattern `wizard-turn`'s client already uses for this case (`useTripWizard.ts`/`useItineraryChat.ts`'s existing fallback string, "Failed to reach the trip-planning assistant. Please try again." — reused verbatim or a phase-1-specific variant, not the invented copy from an earlier draft); nav chips already rendered from a prior successful turn remain clickable (they're static client-side links by that point, not live model output).
  - **Telemetry Contract:** events sink to a new public ingest endpoint on `assistant-service` itself (`POST /assistant-turn/events` or similar, gateway-mounted, `PUBLIC_PATTERNS`), which writes to `analytics-service`'s existing database via an internal service-to-service call — `analytics-service`'s current routes are all `requireAuth`/`authorize('admin','salesRep')` dashboard queries with no public ingest path, so this is net-new plumbing on both ends, not a "no new sink" reuse as an earlier draft claimed. Events: `assistant_impression` (widget rendered on page load), `assistant_opened` (panel opened), `assistant_turn` (message sent), `assistant_response` (assistant successfully replied — the completed-turn signal, distinct from `assistant_turn` so a 503/429/malformed-tool-output mid-turn does not silently count as a completed turn), `assistant_nav_click` (a nav chip clicked), `assistant_error` (503/429/malformed-tool-output). Session identity: client-generated `sessionId` (`crypto.randomUUID()`, `localStorage`-persisted, same pattern as `wizard-turn`'s existing session handling), attached to every event. Funnel/drop-off = sessions with an `assistant_opened` event that never reach a subsequent `assistant_response` or `assistant_nav_click`.
  - **Go/no-go bar (resolved, not left open):** phase 2 work starts only if, over a 2-week window post-launch, **≥8% of sessions that render an impression open the widget**, AND **≥30% of sessions that open it reach at least one `assistant_response`** (a real completed round-trip, not merely sending a message that then errors). Both numbers are a starting bar, not a permanent target — revisit after the first real 2-week sample if either metric proves miscalibrated (e.g., traffic volume too low for a meaningful sample), but do not start phase 2 work without a fresh sample clearing whatever bar is current at that time.
- **Phase 2 (gated on phase-1 telemetry clearing the bar above):** add a `search_packages`/`get_package_detail` tool calling package-service; re-validate the service-boundary choice at this gate (confirm `assistant-service` remains the right home now that a genuine cross-service tool exists, per the Service-boundary re-validation note). This is where indirect-prompt-injection hardening becomes load-bearing (package descriptions/reviews are UGC) — retrieved content must be explicitly labeled as data, not instructions, in the model context (spotlighting), and tool output stays inside the same fixed-vocabulary/allowlist discipline as phase 1.
- **Phase 3 (gated on phase-2 telemetry):** wire durable-signal detection into the existing `POST /leads/internal/intake` pipeline (`INTERNAL_EVENTS_TOKEN` convention), exactly as `wizard-turn` already does — no new lead-creation path.

Rationale for Approach B over A, net of the re-validation risk: the user's own stated scope (nav → search → lead-capture, explicitly future-proof) is the second-caller problem `wizard-turn`'s original design doc already flagged — package-service was never meant to be the AI-orchestration home for cross-service tools. Building the harness in its own service now avoids a second migration once phase 2/3 need to call both package-service and lead-service tools from the same conversation, at the accepted cost of a stranded deployable if phase 1 fails its own bar.

## Eng Review Decisions (resolved 2026-09-05, `/plan-eng-review`)
- **Persistence:** `assistant-service` is fully stateless for phase 1, matching `wizard-turn` — no Postgres schema. Client resends the sliding message window each turn; telemetry events go to the new ingest endpoint (below), never a conversation table.
- **Gemini 429 quota fix folded into this work:** `Services/package-service/src/ai/geminiClient.js`'s retry loop (TODOS.md, P2) ignores Gemini's `RetryInfo.retryDelay` and uses a fixed backoff that can't survive real quota exhaustion — today shared by 2 callers (`wizard-turn`, `itinerary-chat`), and `assistant-service` becomes a 3rd, more publicly-visible caller of the same client. Fix `geminiClient.js` to parse `RetryInfo.retryDelay` (capped ~60s) as part of this PR, before `assistant-service` ships, rather than widening exposure to a known-broken retry path.
- **Nav allowlist single source of truth:** client-owned, sent per request. A new `Client/src/config/` table (name → path → `enabled`, replacing the `PAGE_CONFIG` + `handleNavigate` duplication) is included in every `/assistant-turn` request; `assistant-service` builds the model's tool-vocabulary prompt from what the client just sent, never a server-held copy — correct by construction, no drift between the executable allowlist and the model's prompt.
- **DRY: policy-retrieval matcher extracted, not forked.** `retrieveSnippets()`/`fetchPolicyDocuments()` move into a shared package (`Services/shared/`, alongside the existing `@travel-crm/contracts` precedent) and both `wizard-turn` and `assistant-service` import it — one bugfix location, no risk of the two surfaces' policy answers drifting apart.
- **Performance:** the shared `retrieveSnippets()`/`fetchPolicyDocuments()` package (see above) adds a 60s in-memory TTL cache around the user-service fetch — policy documents change rarely (admin-edited), and this cuts a redundant internal HTTP round-trip on every turn for both `wizard-turn` and `assistant-service`, which now share the implementation.

## Open Questions
- Exact gateway path/limiter config for `/assistant-turn` — mirrors `wizard-turn`'s mount shape per Constraints (shares `itineraryChatLimiter`); concrete route string (`/api/v1/assistant/turn`, `/api/v1/assistant/events`) to be finalized at implementation time, not blocking.

## Success Criteria
- Phase 1 measurable, per the Telemetry Contract: ≥8% impression→open rate and ≥30% open→completed-turn rate over a 2-week post-launch window (see Recommended Approach's resolved go/no-go bar).
- No measurable increase in support/agent load, cross-checked against existing support-ticket volume as a baseline (this is additive help, not a replacement for existing wizard/lead flows).
- Zero incidents of the model outputting an unallowlisted route or raw HTML/link that gets executed (verifies hardening from Constraints).
- Zero visitor-visible "broken navigation" incidents from the assistant targeting a `PAGE_CONFIG`-disabled route.

## Distribution Plan
Web service with existing deployment pipeline (Cloud Run via the existing Terraform modules) — `assistant-service` follows the exact same deploy pattern as the other 10 Prisma/Express microservices already in `infra/terraform/modules/deployment/`. No new distribution channel needed.
