## Problem Statement
The site needs a customer-facing chatbot that answers company-policy questions, helps visitors search/discover packages, and — the part that actually reduces agent headcount pressure — turns a real conversation into a qualified Lead a human agent verifies in Management, instead of an agent manually re-keying it. The broader ask (personalized recommendations, travel history, chat-driven editing of an existing package) is real but layers on top of this core capability, not a substitute for it.

## Demand Evidence
Not measured — the user confirmed this is a reasonable inference from the codebase, not a hard number. `wizard-turn`'s `complete_wizard` case finds a matching package and returns it to the client but has zero write path into `lead-service` (`createLead` is `authorize('admin', 'salesRep')`-only). Every wizard conversation that reaches a real outcome today requires an agent to manually re-type it into Management. The user has watched agents work real leads and confirmed two things a bot can't shortcut: (1) judgment calls on pricing/bundling for vague requests, (2) leads that resolve across multiple sessions/channels (WhatsApp, calls) rather than one conversation.

**Assignment before/while building:** get the real number — instrument current lead creation with a `source` breakdown and time agents spent per manually-keyed lead for one week. This is the success-metric baseline; building this without it means shipping blind on the one number that proves it worked.

## Status Quo
1. A prospect completes the public, anonymous `wizard-turn` flow (`Services/package-service/src/controllers/wizard.controller.js`) — slot-filling, package proposals, policy Q&A via `answer_policy_question` (deterministic retrieval over `policyDocuments`, model only selects among server-retrieved candidates, never authors quotes) — and reaches `complete_wizard`.
2. The client receives the selected package. Nothing is persisted.
3. An agent — via phone, WhatsApp, or the client handing off contact info some other way — manually creates the Lead in Management (`POST /api/v1/leads`, admin/salesRep-only), re-typing what the bot conversation already extracted.
4. Leads that don't cleanly resolve in one wizard pass (customer says "let me think" and comes back next week via WhatsApp) leave no trace at all — the second conversation starts from zero context.

## Target User & Narrowest Wedge
The agent who currently re-keys a completed wizard (or WhatsApp/call) conversation into Management by hand. The narrowest wedge: any channel that captures a durable signal — real contact info plus meaningful trip intent (destination/dates), not just idle browsing — persists a Lead automatically, tagged so it's unmistakably unverified.

## Constraints
- `wizard-turn` is deliberately public/anonymous. It is stateless server-side, but the client does NOT resend full history or a session id today: `useTripWizard`/`useItineraryChat` hold state in React `useState` (lost on reload) and send only a sliding window of the last 20 messages (`MAX_SENT_MESSAGES = 20`), with no message `id`/`at` and no session identifier anywhere in `WizardTurnRequest`. A session id, full-transcript capture, and localStorage persistence are all NET-NEW client + contract work this design must build, not reuse.
- `lead-service`'s user-facing `createLead` is authenticated `admin`/`salesRep`-only, but `lead-service` already has a second, separate auth path for machine writes: `internalTokenAuth` (`x-internal-token` header checked against `INTERNAL_EVENTS_TOKEN`) already gates `/internal/events`, `/internal/facebook-lead`, and `/internal/communication-logs`, and `notification-service`/`package-service` already call it via `lead.client.js`. The intake endpoint reuses this convention — it is not a new auth mechanism.
- `Lead.lifecycleStatus` today has no state meaning "machine-created, unverified" in the sense this design needs, but two existing machine-created paths (`createWebsiteContactLead`, `handleFacebookLeadEvent`) already write directly to `NEW` (auto-assigned only if `AssignmentSettings.mode` is `auto`; otherwise unassigned-but-still-`NEW`). This design intentionally does NOT reuse that pattern: those sources are structured, human-typed form/ad fields, while a wizard conversation's slots are LLM-extracted from free text and materially more error-prone (wrong destination parse, duplicate/garbled entries) — the extra `PENDING_VERIFICATION` quarantine step exists specifically to gate LLM-authored records before they're agent-actionable, a risk website/Facebook leads don't carry. This is a deliberate inconsistency with existing machine leads, not an oversight.
- Lead access today is ownership-gated for `salesRep`: `getLeads`/`getLeadsByStatus` filter to `assignedToId: user.id`, `getLead`/`updateLead` 403 when `lead.assignedToId !== user.id` (unless `admin`/`manage_leads`), and `assignLead` requires `manage_leads`/`admin`. An unassigned `PENDING_VERIFICATION` lead is invisible and unclaimable to a plain salesRep through every existing endpoint — the claim flow needs new capability, not just a new status value (see Implementation shape).
- The model must never author pricing, policy text, or a confirmed booking — this already holds architecturally in `wizard-turn` (fixed tool vocabulary, server executes deterministic logic per tool) and must hold identically for whatever writes the Lead.
- Chat-driven editing of an already-quoted/booked package is explicitly out of scope for this design (mutates priced state, materially higher risk) — the schema must not block it later. Concretely: once a lead leaves `PENDING_VERIFICATION`, further intake calls for that session must never mutate its scalar fields (destination, dates, traveler count) — only append to the communication log — so intake can't bypass `validateTravelerUpdate`/`validateTravelDatesUpdate`/pricing gatekeepers on a lead an agent is actively working.
- Authenticated personalization + travel history is explicitly out of scope for this design (wizard-turn today is anonymous) — same non-blocking requirement.

## Premises
1. **Persist on durable signal, not wizard completion.** Revised during this session: the original premise (persist a Lead only when `complete_wizard` fires) is too narrow given that real leads resolve across sessions/channels. The trigger is contact info + meaningful trip intent, whichever turn it appears on — an abandoned-but-contactable conversation is not nothing.
2. **Chatbot-originated leads get a distinct, unmistakable status.** Never conflate a chat-created Lead with one an agent already worked. A new `PENDING_VERIFICATION` lifecycle status (transitions only to `NEW` on agent claim, or `CLOSED_LOST` on agent reject) is the literal enforcement of this — not a tag or a note field an agent could miss.
3. **The bot proposes, an agent verifies — always.** No auto-confirmed booking or price change ships from a chat write, ever. Matches both the existing tool-call architecture and 2026 industry guidance (ground in real data, escalate instead of guess, human verifies before any transaction) confirmed via landscape search.
4. **Lead-quality judgment stays human in v1.** Spam triage and pricing/bundling judgment calls the user watched agents make are not replicated by AI — the persisted Lead carries the full transcript + extracted slots (see Implementation shape for the concrete storage model) so the agent still applies that judgment, not an auto-score/auto-reject.
5. **Duplicate leads are dedupe'd by contact, not just by session.** The motivating scenario is a conversation resuming on a new device/browser (fresh session id) or a different channel entirely — session-id idempotency alone would fork a new Lead in exactly the case this design exists to fix. Intake must also dedupe by contact (email/phone/whatsapp) against existing unclaimed `PENDING_VERIFICATION` leads, following the precedent `handleFacebookLeadEvent` already sets.
6. **This closes as reusable infra, not a one-off script.** Policy retrieval, wizard tool-calling, and (per the chosen approach below) a channel-agnostic intake path are all durable plumbing other features build on, independent of any one person maintaining it.

## Approaches Considered

### Approach A: Minimal contact-capture (wizard-only, no new tables)
**Summary:** Add one new internal route, `POST /leads/internal/intake`, gated by the existing `internalTokenAuth` convention (not a new auth mechanism); `Lead` gains `intakeChannel`/`intakeSessionId` columns and the `PENDING_VERIFICATION` status. The client must be extended to generate and persist a session id and send full-conversation contact/slot state (today it sends neither — see Constraints) — `package-service` calls the new route whenever slots + contact look meaningful, idempotent upsert by `(channel, sessionId)`.
**Effort:** S | **Risk:** Low
**Pros:** zero new tables/services, ships in days; reuses the wizard's existing stateless-client pattern exactly.
**Cons:** no durable transcript if the client loses its session id; no Management queue UI — agents find these via existing lead search/filter; wizard-specific, doesn't generalize to WhatsApp/contact-form intake later.
**Reuses:** `wizard-turn`'s existing stateless message-history pattern, `sanitizeSlots`, `Lead` model, `ALLOWED_TRANSITIONS`.

### Approach B: Wizard + server-held ChatSession + Management queue
**Summary:** Everything in A, plus `package-service` persists a `ChatSession` (transcript, slots, channel, status) so history survives client-side loss; Management gets a `source=chatbot` / `PENDING_VERIFICATION` queue view with a transcript link.
**Effort:** M | **Risk:** Low-Medium
**Pros:** resilient to client state loss; agents get a real queue instead of hunting the general lead list; sets up the editing/personalization phases cleanly.
**Cons:** new table, new service-to-service contract, new Management screen — bigger diff; still wizard-specific.
**Reuses:** everything in A, plus existing Management list/filter patterns for the new queue view.

### Approach C: Generalized inbound-intake API (chosen)
**Summary:** Build one channel-agnostic `POST /leads/internal/intake` in `lead-service` that any inbound channel — the chat wizard today, a future WhatsApp bot or contact-form widget — calls identically, gated by the existing `internalTokenAuth` convention. `wizard-turn` becomes its first caller, not a special case. Carries `channel`, `sessionId` (idempotency key alongside `channel`), `contact`, `slots`, `transcript` (with per-message `id`/`at`), and writes `Lead` with `source` derived from `channel`, always at `PENDING_VERIFICATION`.
**Effort:** M-L | **Risk:** Medium
**Pros:** every future channel plugs into the same pipe instead of repeating a one-off integration; the `PENDING_VERIFICATION`/queue/verification UX is built once and applies everywhere, not re-litigated per channel; matches Premise 5 (durable infra).
**Cons:** built ahead of a second real caller — the standard YAGNI risk on an internal tool; slightly larger v1 surface (a generic contract has to be designed carefully, not just wired for one caller) and a wider security surface on day one (see Recommended Approach below).
**Reuses:** `wizard-turn`'s existing tool-calling architecture and stateless pattern as the first caller; `Lead` model, `ALLOWED_TRANSITIONS`; the existing WhatsApp webhook pattern in `notification-service` as the shape a second caller will eventually follow.

## Recommended Approach
**Approach C**, per the user's explicit choice overriding the minimal-first recommendation. Rationale for building the abstraction now rather than after a second caller exists: `notification-service` already receives inbound WhatsApp webhooks and the product ask explicitly named WhatsApp-style follow-up conversations as part of "leads that resolve over multiple sessions" — a second caller is not hypothetical, it is the next thing this same conversation described. Building `POST /leads/internal/intake` as the shared contract avoids `wizard-turn` and a future WhatsApp integration each inventing their own lead-creation path with different idempotency and status semantics.

### Implementation shape

**lead-service (schema + intake endpoint):**
1. `LeadSource` enum: add `chatbot`. `LeadPlatform` enum: add `Chatbot_Wizard` (and leave room for `WhatsApp_Bot` later without a migration surprise — the enum is additive).
2. `LeadLifecycleStatus`: add `PENDING_VERIFICATION`. `ALLOWED_TRANSITIONS['PENDING_VERIFICATION'] = ['NEW', 'CLOSED_LOST']` (agent claims → `NEW`; agent rejects as spam/junk → `CLOSED_LOST`, still requiring `lostReason` per the existing gatekeeper). No other status transitions INTO `PENDING_VERIFICATION` — it is a machine-only entry state. This deliberately does NOT match how `createWebsiteContactLead`/`handleFacebookLeadEvent` write straight to `NEW` — see Constraints for why LLM-extracted slots get the extra quarantine step.
3. `Lead` model: add `intakeChannel String?` and `intakeSessionId String?`, with `@@unique([intakeChannel, intakeSessionId])` (a single-column unique on session id alone would let two different channels' session ids collide in one namespace). This composite key is the idempotency mechanism for a *repeat call on the same session* — it does NOT catch a resumed conversation on a new device/session, which is why dedupe-by-contact (Premise 5) is a separate, required check, not a nice-to-have. `LeadCommunicationLog` also gets a new `externalMessageId String?` column with `@@unique([leadId, externalMessageId])` — it has no field today to record which client-side transcript message a row came from, which per-message dedupe (#6/#7) requires. Also add `@@index([email])`, `@@index([phone])`, `@@index([whatsapp])` to `Lead` in the same migration — none exist today, and Premise 5's contact dedupe runs an OR-matched lookup across all three on every intake call, which would otherwise table-scan `crm_leads.Lead` on a hot path that only grows busier as the table grows.
4. New route `POST /leads/internal/intake`, mounted before `router.use(requireAuth)` alongside the existing `/internal/events`, `/internal/facebook-lead`, `/internal/communication-logs` routes, reusing the same `internalTokenAuth` middleware (`x-internal-token` vs `INTERNAL_EVENTS_TOKEN`) rather than inventing a second internal-auth convention. **Not** exposed through the gateway's public allowlist — only `package-service` (and later `notification-service`) call it, service-to-service, inside the private network.
5. Request contract: `{ channel: 'chatbot' | future values, sessionId: string, contact: { name?, email?, phone?, whatsapp? }, slots: { destination?, duration?, travelers?, budget?, preferences? }, transcript: [{ role, content, at, id }], selectedPackageId? }`. `id`/`at` on each transcript message are required specifically so the server can diff a resent sliding window against what it already stored (see #6) — the client's existing 20-message window has neither today and must be extended to carry them. Validated with Zod, same conventions as every other lead-service input.
6. Controller, first call for a `(channel, sessionId)` pair: dedupe first by contact (email/phone/whatsapp) against ANY existing lead with that contact, not only unclaimed `PENDING_VERIFICATION` ones (precedent: `handleFacebookLeadEvent`'s dedupe) — a returning visitor who already has a claimed, in-progress lead must still merge into it (Success Criteria), just through the append-only path in #7, not by forking a second lead. If no match, use `tx.lead.upsert` on `@@unique([intakeChannel, intakeSessionId])` rather than a bare `create` — two wizard turns close enough together can both pass the "no existing lead for this session" check before either write commits, and a bare `create` would throw a `P2002` unique-violation on the loser instead of safely converging on one lead. Set `lifecycleStatus: 'PENDING_VERIFICATION'` (create branch only — never reset on the update branch), `source` derived from `channel`, no auto-assignment (assignment happens on agent claim — a `PENDING_VERIFICATION` lead is not yet "in" the round-robin). `destination`/`numberOfTravelers`/`budget`/`message` map directly to existing `Lead` columns; `duration` has no `Lead` column and is derived into `travelDate`/`endDate` only when both a start date and duration are known, otherwise stored in `message` alongside `preferences` (no dedicated column exists for either — flagged as a real schema gap the migration should close if this proves valuable, not silently dropped). Every transcript message becomes one `LeadCommunicationLog` row (`type: 'message'`, `externalMessageId` = the client's message `id`) — the unique constraint on `(leadId, externalMessageId)` makes re-inserting a message already logged from a prior overlapping window a safe no-op.
7. Controller, repeat call on an existing lead: **if** `lifecycleStatus` is still `PENDING_VERIFICATION`, append new (by `id`) transcript messages and merge new/changed slots into the Lead's scalar fields. **If** the lead has already left `PENDING_VERIFICATION` (an agent claimed it), append transcript messages only — never touch scalar fields, so a live conversation can't bypass `validateTravelerUpdate`/`validateTravelDatesUpdate`/pricing gatekeepers on a lead an agent is actively working (Constraints).
8. Claim capability: a plain `salesRep` cannot list, open, view, or claim an unassigned `PENDING_VERIFICATION` lead through any existing endpoint (`getLeads`/`getLead`/`assignLead` are all ownership- or admin-gated — verified against `lead.controller.js`: `getLead` 403s a salesRep whenever `lead.assignedToId !== user.id`, unassigned included). This design adds THREE carve-outs, not one: (a) `GET /leads?lifecycleStatus=PENDING_VERIFICATION` as an explicit branch in `getLeads`'s `where` construction, visible to any `salesRep`, not filtered to `assignedToId`; (b) the same carve-out in `getLead`'s authorization check — a salesRep may view a specific lead when its `lifecycleStatus` is `PENDING_VERIFICATION`, regardless of `assignedToId`; (c) a new `POST /leads/:id/claim` that sets `assignedToId = req.user.id`, `assignmentMode: 'manual'`, and runs the `PENDING_VERIFICATION → NEW` transition through `validateTransition`. Rejecting a `PENDING_VERIFICATION` lead as spam (`CLOSED_LOST`) stays admin/`manage_leads`-only, matching every other `CLOSED_LOST` transition today — salesReps only get the claim path, not the reject path.

**package-service (first caller):**
1. In `wizard.controller.js`, after computing `mergedSlots`/`serverResult` for any tool, check whether contact info (name + email or phone/whatsapp) is present in `wizardState` alongside meaningful intent (`destination` and either `duration` or a `selectedPackageId`). The client must be extended to actually collect contact info as a wizard step (today's `wizardTurnResponseSchema` tool vocabulary has no `capture_contact` tool) — add `capture_contact` as a fifth tool the model can call when the conversation naturally reaches "how do we reach you," server-validated the same deterministic way `set_slot` is.
2. When the durable-signal condition is met (on any turn, not only `complete_wizard`), call `POST /leads/internal/intake` on `lead-service`, awaited with a strict short timeout (e.g. 2s) wrapped in try/catch that never throws past it. This bounds worst-case wizard-turn latency to a known constant instead of an undefined "fire-and-forget but awaited" hang, while keeping the synchronous-log guarantee: a timeout or error is logged with full turn context before the handler continues to respond, rather than firing detached and losing correlation to the turn that triggered it. `package-service` has no existing lead-service client to reuse for this — `lead.client.js`'s `internalTokenAuth` pattern exists today only in `notification-service`; `package-service` needs its own small client module following the same convention (env-configured `LEAD_SERVICE_URL` + `x-internal-token` header), not a reuse of an existing cross-service call.
3. This design requires client changes beyond the wizard tool: extend `WizardTurnRequest`/`WizardStateSchema` and `useTripWizard` to (a) generate a `sessionId` (`crypto.randomUUID()`) on first wizard load and persist it in `localStorage` so a page reload resumes the same session, and (b) give every message a stable `id`/`at` so the intake payload's transcript diffing (Implementation shape #6/#7) works — the current `{ role, content }`-only, no-id, last-20-messages shape is insufficient as-is and must change for both `wizard-turn` and this intake call.

**Shared contract:**
- `Services/shared/contracts/src/leadIntake.js`: `LeadIntakeRequest`/`LeadIntakeResult` Zod schemas, consumed by both `package-service` (as a client) and `lead-service` (as the server), same pattern as `itineraryChat.js`.

**Management (minimum viable surface for this design — full queue UI is a fast follow):**
- `getLeads` needs a new carve-out `where` branch for `lifecycleStatus=PENDING_VERIFICATION` (visible to any `salesRep`, bypassing the normal `assignedToId` filter — see Implementation shape #8) plus new `source`/`platform` query params (today `getLeads` only supports `status`/`search`; Management's platform filter is client-side over already-loaded rows, which won't scale to a real PENDING_VERIFICATION queue).
- Client-side, `PENDING_VERIFICATION` must be added everywhere `LeadLifecycleStatus` is already enumerated: `StatusChangeDialog`'s transition map (currently duplicates `ALLOWED_TRANSITIONS`; an unknown status yields an empty option list and silently blocks claim/reject in the UI), `LeadStatusBadge`'s label/color map, and `LeadFilters`'/`LeadTable`'s hardcoded status tabs. This is real, non-optional v1 work, not a "just make the filter reachable" afterthought.
- A dedicated queue view (vs. reusing the filtered list) is the natural next iteration once agents are actually using this filter.

## Open Questions
- Should `capture_contact` be a wizard tool the model chooses to call, or a fixed step the client always asks after N turns regardless of what the model does? Model-chosen risks the bot never asking; a fixed client-side step is simpler and matches the "never trust the model with the important thing" pattern already used for pricing/policy. Lean toward the fixed client-side step.
- What's the actual demand number (agent-hours/week spent re-keying)? Flagged in Demand Evidence — needed before/while building to have a real before/after metric.
- Does a `PENDING_VERIFICATION` lead notify anyone, or does it just sit until an agent checks the filter? `Lead.notifNewLead` exists only as a schema column — no service code reads it today, so it is dead, not "likely reuse it." A team-wide notification for an unassigned `PENDING_VERIFICATION` lead (no `assignedToId` to route a per-rep notification to) is net-new plumbing this design does not scope; flagged as a fast-follow, not a blocker.

## Success Criteria
- A wizard conversation that provides contact info + real trip intent produces a `PENDING_VERIFICATION` Lead in `lead-service` with zero agent re-keying, verifiable by comparing wizard completion count to intake-created lead count over a week.
- A visitor who abandons mid-wizard after giving contact info still produces a Lead an agent can follow up on — not lost, unlike today.
- A returning visitor merges into the same Lead whether they resume the same session (`(channel, sessionId)` match) or return via a new session with the same contact info (contact-based dedupe, Premise 5) — neither path forks a duplicate.
- No `PENDING_VERIFICATION` lead is ever auto-assigned, auto-confirmed, or auto-priced — every one requires an explicit agent claim before entering the normal `NEW` → `DRAFTING` → ... flow.
- `POST /leads/internal/intake` is unreachable from the public internet (gateway allowlist excludes it; `internalTokenAuth` required) — verified by a live E2E check against the gateway, same pattern as the existing "genuinely public" contract specs verify public routes.

## Dependencies
- No new services. Work spans `package-service` (wizard tool, session id + transcript-id client changes, intake call), `lead-service` (schema migration, new intake + claim endpoints, state machine edge), `Services/shared/contracts` (new schema pair), and `Management` (new `PENDING_VERIFICATION` handling across `StatusChangeDialog`/`LeadStatusBadge`/`LeadFilters`/`LeadTable`, plus new `getLeads` query support — not just filter reachability).

## Implementation Notes (post-ship, security-driven revision)
- **Premise 5 revised again, this time down:** the shipped `intakeLead` does NOT dedupe by contact (email/phone/whatsapp) across sessions. `/ship`'s security specialist review found the original contact-dedupe design (persist-on-durable-signal from a PUBLIC, unauthenticated `wizard-turn` endpoint, matched against ANY existing Lead by contact) was an IDOR: an anonymous caller could type a stranger's email into a fresh session and merge into or overwrite that stranger's Lead, or append attacker-authored transcript text into an already-claimed lead's communication log. Shipped behavior: dedupe is scoped to the caller's own `(channel, sessionId)` key only — safe because `sessionId` is a non-guessable client-generated UUID the caller already owns. A returning visitor on a new device without their original session id now forks a second Lead instead of merging; restoring the merge safely requires a verified-ownership mechanism (email confirmation link, OTP) — tracked as a P1 TODO, not silently dropped.
- **Migration split for zero-downtime index builds:** the five new indexes (composite unique on `Lead.intakeChannel`/`intakeSessionId`, three single-column on `Lead.email`/`phone`/`whatsapp`, unique on `LeadCommunicationLog.leadId`/`externalMessageId`) ship as five separate single-statement migrations using `CREATE INDEX CONCURRENTLY`, not bundled into the schema/enum migration. `CREATE INDEX CONCURRENTLY` cannot run inside a transaction, and Prisma wraps any multi-statement migration in one — a non-concurrent build on the shared, live `crm_leads.Lead`/`LeadCommunicationLog` tables would hold a write-blocking lock for the full index build.
- **`POST /leads/:id/claim` is an atomic conditional update** (`updateMany` with `WHERE lifecycleStatus = 'PENDING_VERIFICATION'`, checking `count`), not a plain `findUnique` + `update` — two salesReps claiming the same lead concurrently now has exactly one winner instead of last-write-wins.
- **`getLeads`'s new `source`/`platform` query params filter on the Prisma enum's schema identifier** (e.g. `Chatbot_Wizard`, `Walk_in`), not the `@map`-mapped display string (`Chatbot Wizard`, `Walk-in`) — Management's `PLATFORM_OPTIONS` values were corrected to match (this was a latent bug in the pre-existing platform filter chips too, exposed once the backend actually started reading the param).
