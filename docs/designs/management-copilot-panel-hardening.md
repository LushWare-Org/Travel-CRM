## Problem Statement

Three defects in the shipped Management Context Copilot, reported from real operator use:

1. **The panel scrolls sideways.** When a copilot output is longer than the panel's width it becomes horizontally scrollable instead of wrapping. It should just wrap onto another line.
2. **Desktop has no labeled copilot control.** The labeled, attention-dotted trigger exists only below `xl`. At `xl` and wider, a collapsed panel leaves an icon-only 40px rail pinned to the far right edge.
3. **The chat is not where the operator is.** The panel should offer a chatbot with context and the ability to call tools, acting as a real agent copilot — on the scopes the operator actually works in.

Each is verified in the current tree, not inferred from the report:

- `CopilotDock.tsx:29` and `CopilotDrawer.tsx:86` scroll with `overflow-y-auto`. CSS computes the unset `overflow-x: visible` to `auto` whenever the other axis is not `visible`, so the panel's own scroll container silently becomes a horizontal scroller. Nothing in `Management/src/features/copilot/` sets `overflow-wrap`, and every text-bearing flex child (`ClaimItem`'s facts row, `EvidenceAction`'s `<dd>` value rows, `LeadBriefing`'s meta line) keeps the default `min-width: auto`. One unbreakable token — a 24-character lead id, a URL inside model prose, a long captured value — widens the scroll area by its full length.
- `CopilotRail.tsx:21` is `size="icon"` with `aria-label="Open copilot"` and no visible text; `CopilotDrawer.tsx:53` renders the labeled `h-11` pill with the attention dot, inside a wrapper that is `xl:hidden`.
- `LeadConversation` is imported by exactly one module, `LeadBriefing.tsx:6`. `CollectionBriefing.tsx` renders claims and nothing else — no transcript, no composer, and no suggested questions. So on nine of the ten page keys, and on `/leads` with no row selected, the panel has no chat at all. The ask path itself works end to end (`useCopilotSession.ts:436` reads `result.answerBlocks`; `managementCopilot.controller.js:288` runs `runAgentLoop`), but its whole tool vocabulary is one tool — `getLead` in `toolRegistry.js` — and `handleAsk` passes no page key and no tool list, so every page shares that one lead-bound tool.

## What Makes This Cool

The panel stops being a briefing with a chat bolted underneath it and becomes a surface that is correct by construction: it cannot scroll sideways, it cannot lose its own affordance at any breakpoint, and it cannot have a scope where the assistant is missing.

The one structural idea worth the refactor: **the conversation belongs to the shell, not to the record briefing.** Today the record briefing hosts the chat because it was written first, which is why nine pages lost it. Moving the conversation up one level is a few lines and it makes the missing-chat class of bug unrepresentable rather than fixed.

## Constraints

- Read-only stays. No tool in this slice may write CRM business data; every new tool is a `GET` executed under the caller's forwarded identity with the adapter's existing allowlist.
- Reuse what shipped: the dock/rail/drawer shell, `useCopilotSession`, the two-phase deterministic/model contract, the `agentRunner` loop, `groundingValidator`, the adapter registry, and the owned UI primitives. No new chat, AI, panel, or animation dependency.
- The panel stays **one continuous surface**. Tabs and nested cards remain out.
- Every grounded claim keeps its inline evidence action; the briefing keeps its hierarchy and its `xl` record-reveal behaviour.
- No new upstream endpoints. Tools are built from reads the adapters already perform under an existing audit.
- The nine existing page mounts must inherit the fixes without being edited.

## Premises

Agreed in session:

1. Horizontal overflow is a defect, not a preference. The fix belongs in the shared panel primitives, not per-claim patches. It violates the shipped criterion "no page-level horizontal scroll is introduced by the copilot" (`docs/designs/management-context-copilot-evidence-lens.md:362`, restated in the acceptance-test assertions at `:487`).
2. The collapsed desktop affordance is the discoverability defect. Desktop needs a labeled control equivalent to the mobile trigger.
3. The chatbot is not missing; it is scope-gated. The vocabulary is one tool, and it is not page-scoped at all.
4. Read-only stays. Chat grows read tools only; writes stay behind the deferred action-taking contract.
5. No new chat/AI/panel dependency.

**Correction to premise 3 recorded during this session:** the descriptor `tools` field described in `management-copilot-all-pages.md` §4/§6 and in the "Per-page ask-mode tool vocabulary" TODO was never implemented. `grep -rn "tools"` over `assistant-service/src` returns only the agentRunner, prompt, and controller references; `createPageAdapter` produces `parseScope` / `loadEvidence` / `computeInsights` / `defaultQuestions` and nothing else. The seam is net-new work, and its absence is the root cause of the one-tool vocabulary.

## Cross-Model Perspective

Codex cold read (`deepseek-v4-pro`, high reasoning; `gpt-6-astra` was rejected by the configured provider, so this is a stronger sibling of the session model in a different harness — not an outside family). It received a structured summary and never saw this conversation.

It reached the same diagnosis independently from the same files: do not add a chat tab; the chat is already built and the defect is that it is scope-gated. It named the overflow fix and the "one shared rule, not per-claim patches" discipline. It named `@modelcontextprotocol/sdk` as the tool-layer shape donor — tool discovery, execution, and typed-schema registry — while agreeing it must not become a runtime dependency.

Where it differed, in two places worth keeping:

- **Scope of the tool work.** It recommends skipping per-page tool vocabularies and adding a single collection read tool (`listLeads`). This design keeps the descriptor seam and ships two tools instead, because the missing seam is precisely why nine pages share a lead-bound tool; adding tools without it re-creates the same hole one tool later.
- **What the chat should be.** Its "coolest version" is Codex's strongest contribution: make the briefing's own rows promptable (`Ask why this`, `What changed since I left`), and carry the originating claim's evidence ids into the turn so the agent answers against evidence already on screen. That idea is deferred here as the natural next slice rather than folded in — it is a new interaction, not a fix, and it must not crowd the briefing hierarchy that the previous review deliberately ranked first.

It also read the user's emphasis correctly: the stated want is agency and tool use, not tab UI.

## Approaches Considered

- **A — Cowpath repair (rejected).** Patch the exact spots: `overflow-x-hidden` and `[overflow-wrap:anywhere]` on both scrollers, a labeled trigger, and `LeadConversation` plus suggested questions added to `CollectionBriefing`. Smallest diff, but the wrap contract stays unowned and the next page mount repeats the bug.
- **B — Shared-primitive hardening (chosen).** Fix the contract once in a shared surface primitive; share one trigger across both breakpoints; move the conversation into the shell so it is scope-agnostic by construction; implement the descriptor `tools` seam and ship two read tools.
- **C — Interrogable briefing (deferred).** B's structure plus promptable claim rows carrying evidence ids into the turn. The best product idea on the table and a new interaction surface with no usage data behind it; needs its own review.
- **D — Tabbed Briefing | Chat (rejected).** Gives chat a permanent home but contradicts the merged decision that the dock is one continuous surface rather than tabs, and leaves the briefing-versus-chat priority and the collection-scope hole unresolved underneath it.

## Recommended Approach

### 1. The panel's wrap contract, owned in one place

Add `Management/src/features/copilot/CopilotSurface.tsx`: the panel's single scroll container, consumed by both `CopilotDock` and `CopilotDrawer`. It applies `min-h-0 flex-1 overflow-y-auto overflow-x-hidden overscroll-contain` plus `[overflow-wrap:anywhere]`.

Two properties make this the correct fix rather than a cosmetic one:

- **`overflow-wrap: anywhere` is the load-bearing choice, and it must be `anywhere`, not `break-word`.** Per CSS Text 3, only `anywhere` makes the soft-wrap opportunities count toward the element's **min-content intrinsic size**. That is what lets a flex child shrink below the length of its longest token. `break-word` breaks the line without changing min-content, so it fixes the visual overflow and leaves the scroll axis alive. `overflow-wrap` is inherited, so declaring it once on the surface covers claim prose, questions, fact values, source labels, and evidence detail.
- **`overflow-x-hidden` is the assertion, not the fix.** It states that panel width is a layout invariant. Wrap alone leaves the axis available for the next unanticipated child; clip alone hides content. The pair is required.

`CopilotSurface` renders the scroll element itself. It applies `relative` on that element, because `relative` is only load-bearing where the clipping happens: `CopilotDock.tsx:20-28` records that without a positioning context on the scroller, the absolutely positioned `sr-only` labels resolve against the sticky `<aside>` and stretch the app shell's scrollable area by ~1900px. It accepts a `className` for the caller's own padding and `scroll-pb-24`, so both callers keep their current spacing. `CopilotDock` and `CopilotDrawer` keep their positioning wrappers and stop declaring their own `overflow-y-auto`.

`Management/DESIGN.md` gains a line under the copilot primitives naming `copilot-surface` as the owner of the wrap contract, so the next workspace module inherits the rule instead of rediscovering it.

Known and accepted: `Badge` is `whitespace-nowrap overflow-hidden` by design, so a long source label clips inside its chip. That is a chip, not prose; the full text stays available through the action's `aria-label`.

### 2. One trigger, both breakpoints, labeled

Extract `Management/src/features/copilot/CopilotTrigger.tsx` from the `DialogTrigger` render in `CopilotDrawer.tsx:53`: the `h-11` outline pill with `ClipboardList`, the visible `Copilot` label, `aria-label="Open copilot"`, and a forwarded `ref` so focus restoration keeps working. The attention state moves out of the button into the sibling element specified below, so the dot is no longer a button child and the `sr-only` sentence is no longer needed.

- **Below `xl`:** `CopilotDrawer` keeps its `fixed right-4 bottom-…` wrapper and renders `CopilotTrigger`. The one below-`xl` visual change is the attention dot moving out of the pill to sit immediately beside it, for the accessibility reason in the next bullet.
- **At `xl` and wider when collapsed, the rail stays and the trigger is added.** `CopilotRail` keeps its 40px column as the page's layout edge, and the same `CopilotTrigger` is added at the same floating position (`fixed right-4 bottom-[max(1rem,env(safe-area-inset-bottom))]`) at the same 44px target. Both collapse states therefore remain reachable: the rail is the edge-anchored control, the floating trigger is the discoverable one. Accepted cost, and it is a real one: two controls now perform the same action, so they carry **distinct accessible names** — the floating trigger keeps `Open copilot` (matching the below-`xl` trigger) and the rail's control becomes `Expand copilot panel`, because the existing e2e helper resolves `getByRole('button', { name: /open copilot/i })` and must not match two elements at `xl`.
- **The floating trigger's position was designed for a below-`xl` overlay, not for a desktop column, so the page's content-column scroller reserves a bottom exclusion no smaller than the trigger's height plus its offset (72px).** No interactive row action or tab control may sit under the trigger at 1280, 1366 or 1439px. This closes Open Question 1 by decision rather than by later verification.
- **The attention glyph is decided here, not left to the implementer.** The two surfaces differ today: the rail's marker is an `AlertTriangle` inside a `text-warning` span (`CopilotRail.tsx:26-34`), the drawer's is a `bg-warning` dot (`CopilotDrawer.tsx:60`). One shared component cannot keep both, so `CopilotTrigger` renders the dot — it sits beside a visible "Copilot" label, where a dot is the right weight — and the rail keeps its own `AlertTriangle`, because the rail stays. The desktop marker's visual therefore does change, from triangle to dot; only the accessible contract is preserved. Severity handling is unchanged: neither shipped surface distinguishes warning from critical (`DESIGN.md:351` says "or destructive", but both use warning unconditionally), so the dot stays `bg-warning` and that stale DESIGN.md clause is reconciled in the same documentation edit rather than being silently implemented here. **The dot is also paired with a visible non-colour mark** — a small `AlertTriangle`, `aria-hidden`, sitting beside the trigger label — because `DESIGN.md:351` requires that the attention marker never be colour-only, and a lone amber dot is exactly that for a sighted operator. Colour vision deficiency affects roughly one in twelve men, and this marker carries the one state in the panel that says a human should look. The accessible name stays on the sibling `role="img"` element and the visible glyph is hidden from assistive tech, so the state is announced once rather than twice.
- **Activating the desktop trigger moves focus into the panel**, exactly as the drawer does today (`CopilotDrawer.tsx:76` moves focus to the briefing heading and `:77` returns it to the trigger on close). One control, one rule, both breakpoints: the same component cannot behave differently on desktop for the same action, and without the rule a keyboard operator presses the trigger, the panel appears elsewhere in the tab order, and they must traverse the rest of the page to reach what they just opened. The panel is `aria-labelledby` the briefing heading already, so focus lands on the element that names the region and the screen reader announces what opened.
- **The attention marker is a sibling of the button, not a child, and that placement is the requirement.** The rail gets this right: a sibling `role="img"` span carrying `aria-label="This lead has items needing attention."` and `data-copilot-attention-marker="true"` (`CopilotRail.tsx:26-34`), which `ManagementContextCopilot.test.tsx:263` matches. The drawer gets it wrong today: its dot and its `sr-only` span are both children of a button that carries its own `aria-label="Open copilot"`, and a button's contents are presentational in the accessibility tree, so neither the dot's role nor the `sr-only` sentence is exposed — the drawer's attention state is currently invisible to assistive technology, and the shell test passes anyway because `getByLabelText` computes a name for the span in isolation. `CopilotTrigger` therefore renders the button and, when there is attention, a sibling `role="img"` span with that label and that data attribute. The dot glyph stays; the semantics become real; the dead `sr-only` span is deleted. This is why the below-`xl` dot moves out of the pill.

The dock's geometry is unaffected: when open, the dock still occupies its own grid column and the content column keeps its paired height.

**Verification this needs, because it is the one eyeball-dependent decision:** confirm at 1280, 1366, and 1439px that a bottom-right floating control does not occlude the leads table's row actions or the billing tab strip. If it does, fall back to a labeled vertical control that keeps the 40px column and stacks the icon above the label.

### 3. The conversation belongs to the shell

- Rename `LeadConversation.tsx` to `CopilotConversation.tsx`. It takes `session` and `scopeLabel` and is already scope-neutral; the name is what encoded "record only" and is the reason this bug class existed. One import site (`LeadBriefing.tsx:6`, used at `:255`) plus the colocated tests.

```text
-- CopilotSurface (the panel's only scroller) --------+
|  briefing children(api)                              |
|    record:     header > changed > current state >    |
|                attention > experienced view >        |
|                suggested questions                   |
|    collection: attention > changed > current state > |
|                suggested questions                   |
|  ---- one hairline (border-t), no card, no tab ----  |
|  CopilotConversation: transcript, oldest first       |
|    > composer  (sticky bottom-0 to THIS scroller,    |
|       never position: fixed)                         |
------------------------------------------------------+
```

  **The composer's horizontal offset is re-derived for its new parent.** Its form is `sticky bottom-0 -mx-1 ... px-1` (`LeadConversation.tsx:79`), a negative margin tuned to the briefing's own padding. Inside `CopilotSurface`'s `px-4` that leaves a 12px gap on each side, so scrolling text shows through beside the composer's `bg-card` instead of being masked. It becomes `-mx-4 px-4` so the background spans the full width of the scroll surface. The composer sticks to `CopilotSurface`'s scrollport and to nothing else, and `scroll-pb-24` stays on that scroller so a focused control is never hidden behind it. The two children are separated by a single hairline, never a card or a tab, per the dock's one-continuous-surface rule. Below `xl` the same stack renders inside the drawer, which owns its own scroller and padding.
- **State contract for the shell's two children.** One table, both scope kinds, so nine newly chat-enabled pages cannot answer the same four states differently. Every cell describes what the operator SEES.

| Surface | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| Briefing | stable line skeletons, then deterministic claims | "No verified insights for this lead yet" (record) or the collection page's examined-count line | full briefing error + Retry, no stale claims | claims in scope order, evidence actions inline | deterministic claims kept + partial label + Retry |
| Conversation | the pending copy on the submitted turn | no transcript region at all before the first question; the composer is still present | the turn keeps its question, shows a concise failure, and offers Retry | paired user turn + grounded answer blocks | verified answer blocks, no invented text |
| Collection-scope ask (new) | same pending copy, scope-neutral; single-shot on a page declaring no tools | an empty list is still askable: the composer stays enabled and the transcript stays empty until asked | the same per-turn error + Retry as the record scope | same paired turn shape as the record scope | same |
| Composer | present but disabled until the deterministic phase is ready | present (an empty scope is not a no-access scope) | disabled | enabled | enabled |
- **An empty answer is a recoverable state, not a dead end.** Today Retry renders only when a turn's status is `error` (`LeadConversation.tsx:51`). A turn that returns `answerBlocks: []` arrives as `answered` with nothing in it, so after the loop-budget change the operator would read the honest not-in-view copy and find no control to press, with retyping as the only move. An empty answer therefore renders the same way as a failed one from the operator's seat: the question stays visible, the copy states that the panel could not ground an answer for it, and a Try again control re-submits the same question through the existing per-turn retry path. The only case that keeps no retry is a scope the operator cannot read, where asking again cannot help.
- **The pending copy is record-specific and must go neutral in the same edit.** `LeadConversation.tsx:43` renders "Checking this lead…". Once the shell hosts this component on all ten page keys, a question asked on `/billing` or `/users` would say "this lead" while no lead is in scope — wrong copy on nine of ten pages. Derive it from the scope instead (for example "Checking {scopeLabel}…"), and assert the neutral string in the collection-scope test step 3 adds.
- **Extract the briefing logic the two sections already duplicate, and leave the copy alone.** `LeadBriefing.tsx:33` and `CollectionBriefing.tsx:31` declare byte-identical `claimsIn` helpers with the same `{ critical: 0, warning: 1, info: 2 }` rank, and adding suggested questions to the collection briefing would make a third copy. `claimsIn` and the suggested-questions block therefore become one shared module both briefings import. **The section ORDER stays local to each briefing**, for the same reason the labels do: `LeadBriefing` renders `changed → current state → attention → experienced view` (`:156-195`) while `CollectionBriefing` maps `SECTION_ORDER = [attention, changed, current_state, experienced_view]` (`:22`). One shared order array would silently swap the shipped rendering hierarchy on one panel, and the all-pages design made that order scope-dependent on purpose. **The heading text stays per briefing**: they are not the same and were never meant to be — the record panel reads "Since you were here" (`LeadBriefing.tsx:20`) while the collection panel reads "Changed" (`CollectionBriefing.tsx:17`), the distinction the all-pages design introduced when it made section order scope-dependent (a record is read, a list is scanned). Sharing one label map would ship a silent, user-visible wording change inside a refactor.
- `LeadBriefing` drops its `LeadConversation` import and its trailing `<Separator />`.
- `CollectionBriefing` gains the suggested-questions block (at most three, the same `session.submit(question)` wiring the record briefing uses). The conversation now arrives from the shell for free.

The composer's guards already handle the states that matter, and this slice changes none of them: `showComposer` is `session.hasScope && !session.noAccess` (`LeadConversation.tsx:23`), and `composerDisabled` is `session.asking || Boolean(session.error) || !session.canAsk` (`:22`). A collection scope therefore renders briefing, suggested questions, and a composer that is present-but-disabled until the deterministic phase reports ready and no turn is in flight. Criteria 4 and 6 are restated below to name that full condition instead of the partial one this design first wrote down.

### 4. Page-declared tool vocabulary

Server, `assistant-service`:

- Descriptors gain an optional `tools: [name]` list, and every adapter exposes **`askTools(scope)`** — the tool names available for that scope. `createPageAdapter` returns its descriptor's list; the registry decides nothing.
- **Tool resolution is per scope, not per page key.** `/leads` is the one key carrying two genuinely different scopes, and `leadsPageAdapter` already branches on `isRecordScope(scope)` for `loadEvidence` (`adapters/pages/leads.adapter.js:45-49`). `askTools` joins that same discriminated branch rather than inventing a second discriminator: a record scope resolves the record vocabulary (`getLead`, `listLeads`), a collection scope resolves the collection vocabulary (`listLeads`). Resolving by `page.key` alone would either leave `getLead` live on the collection scope — the exact defect this section exists to remove — or, because `leadsPageAdapter` is a hand-written composition with no `descriptor` property, resolve to no tools at all and silently force every `/leads` question down the single-shot path. The registry's deep-interface comment gains `askTools` in the same edit, the way the previous slice established for `loadEvidence`.
- `managementCopilotTurn` passes the **parsed scope** into `handleAsk` as a new parameter, and `handleAsk` resolves `adapter.askTools(scope)` for `runAgentLoop({ ctx, scopeLabel, question, evidence, tools, generateStructured })`. The parsed scope lives only in the turn handler today and `handleAsk`'s signature has no `scope`, so this is a real threading change. Do not source it from `bundle.scope`: only the collection engine sets that field (`collectionEngine.js:287`), and the record bundle built by `leadsAdapter.loadEvidence` does not, so the record branch would resolve the collection vocabulary and lose `getLead` silently. This is the page-awareness the TODO names.
- `agentRunner` builds its prompt tool block from the **passed** list, and `executeTool` resolves against it. A tool name outside the resolved list returns the existing named error and is fed back to the model, never executed.
- **A page declaring no tools runs single-shot.** No tool loop: one structured call whose schema is `final_answer` only (no `tool` field) and whose prompt carries no tool block, over the evidence already in the bundle. The shipped prompt cannot be reused as-is here, because `buildManagementAnswerPrompt` always instructs the model to gather data via "the available tools" and requires a `{ tool, args }` response — self-contradictory against an empty tool list.
- **An ask never returns a briefing-shaped payload.** `respondWithFallback` returns `claims`, while the ask client reads only `result.answerBlocks` (`useCopilotSession.ts:436`), so today an exhausted loop or a fully rejected claim set reaches the operator as the briefing's claims being dropped and `"No grounded answer for that question."` rendered (`LeadConversation.tsx:68`) — the right message, bought with a model round-trip and, on every collection page, a wasted `getLead` fetch. Two call sites change, not one: the loop-failure path inside `handleAsk`, and the `!isAIConfigured()` gate at `:172-175`, which returns `respondWithFallback` **before** the `mode === 'ask'` branch at `:179`. Left as is, an ask request in a deployment with no provider credentials still receives a briefing-shaped payload. The `mode === 'ask'` branch therefore moves ahead of the provider gate, and an ask with no provider configured returns `answerBlocks: []`. The briefing path's own provider gate is unchanged.
- Two tools ship, both built from reads the adapters already perform. `listLeads` (`GET /api/v1/leads`, declared on both branches of `leadsPageAdapter`) takes `{ limit?: number }`, bounded by the engine's own cap, and projects the leads adapter's allowlist. `listInvoices` (`GET /api/v1/billing/invoices`, declared by the `billing` descriptor) takes `{ limit?: number }` too, **does the filtering and ordering itself, because no billing endpoint can supply it**: `getAllInvoices` hardcodes `orderBy: { createdAt: 'desc' }` and accepts no sort parameter (`invoice.controller.js:48`), and the one dueDate-ascending query, `getOverdueInvoices` (`:218-225`), gates on the document `status` field which the billing descriptor's field trap 1 records as never receiving `partial`/`overdue`. So the tool fetches a capped page, filters `paymentStatus ∈ {unpaid, partial}`, sorts by `dueDate` ascending, and returns the derived overdue flag per row. That keeps ranking server-side and deterministic, which is the boundary the answer prompt draws: the model narrates a decision it was handed and never counts, ranks, or derives. Neither tool takes a customer or lead filter: the billing scope is `z.object({}).strict()` and billing-service's `getAllInvoices` accepts only `page`/`limit`/`status`/`startDate`/`endDate`, with the lead filter applied server-side from the caller's role. Both keep the existing posture: Zod-validated args, allowlisted projection, `ctx.headers` identity forwarding, `403/404 → notAuthorized`, `5xx/timeout → unavailable`.
- **Every tool declares a projection and a row cap, and only the projected, capped result leaves the tool.** `serializeToolResult` stringifies whatever it is handed (`managementAnswer.v1.js:49-51`) and `buildManagementAnswerPrompt` splices every history entry into the prompt, so a list-returning tool is the first thing in this system that can put an unbounded payload in front of the model. The engine's own ceiling for such reads is `maxFetchRows: 1000` (`collectionEngine.js:68`). Each tool therefore declares its projection fields and its cap next to its schema, and `historyToEvidence` and the prompt both consume the projected array, not the raw response. A test asserts the serialized result stays under a stated byte budget when the upstream returns a full page.
- **The agent loop gets one overall budget.** `MAX_TOOL_CALLS` is 4 and each iteration passes `timeoutMs: GENERATION_DEADLINE_MS` (17s) to `generateStructured` (`agentRunner.js:6-7`), while the client aborts at `COPILOT_CLIENT_TIMEOUT_MS = 20_000`. With one bounded tool the multi-step path is effectively unreachable; the two list tools make it reachable, and a two- or three-step ask would let the client time out while the server keeps generating and billing. The loop takes a single total budget no greater than the server's existing generation deadline, derives each iteration's timeout from what remains, and on exhaustion stops with the answer-shaped empty payload instead of a third or fourth call. A test proves the derived per-call timeout cannot reach zero on the final iteration.
- **The shared fetch helper must take its token audience from the target service, not from a constant.** `fetchJson` today mints `domainAuthHeader(LEAD_SERVICE_URL)` and then fetches whatever URL it is handed (`toolRegistry.js:28-38`). A `listInvoices` built on it would present a lead-service-audience ID token to billing-service, and `domainAuthHeader` returns `{}` whenever `K_SERVICE` is unset (`cloudRunAuth.js:25`) — so local runs and the unit tests pass while every deployed call is rejected at the Cloud Run edge with 403, surfacing as `notAuthorized`. That failure is invisible off Cloud Run and would take out the one tool the Assignment depends on. Change the helper to `fetchJson(baseUrl, path, ctx)` so the base supplies both the request URL and the token audience, with `listLeads` passing `LEAD_SERVICE_URL` and `listInvoices` passing `BILLING_SERVICE_URL`, and add a test asserting the audience handed to `domainAuthHeader`.
- No change to `groundingValidator`: tool results already become turn-local evidence via `historyToEvidence`, and `handleAsk` already validates against `[...bundle.evidence, ...toolEvidence]`.

## Open Questions

1. **Does the floating desktop trigger occlude content at 1280–1439px?** RESOLVED in §2: it keeps the `right-4 bottom-…` position at a 44px target, the content column's scroller reserves a 72px bottom exclusion, and nothing interactive may sit under it at 1280, 1366 or 1439px. The labeled-vertical fallback is no longer needed.
2. **"like in small size screen in the large size screen also" — instead of, or in addition to?** This design reads it as *instead of* the icon-only rail, so desktop gets one labeled control. If the intent was to keep the 40px rail **and** add a floating trigger, say so before implementation; the change is small but it is a different panel geometry.

## Success Criteria

1. With a fixture containing a 120-character unbroken token, the dock and drawer scroll containers satisfy `scrollWidth <= clientWidth + 1` at 375, 768, 1280, 1440, and 1920px, in both themes, with no horizontal scrollbar rendered.
2. `CopilotDock` and `CopilotDrawer` declare no independent vertical scroll container; the wrap contract is applied by `CopilotSurface` and named in `Management/DESIGN.md`.
3. At `xl` and wider collapsed, a floating labeled control carries the visible text "Copilot" and the accessible name "Open copilot", and the rail keeps its column with its own control named "Expand copilot panel". The two names are distinct, and both controls reach the same panel. No scoped element carries an ambiguous name.
4. `CopilotConversation` renders on all ten page keys, including `/leads` with no row selected, and the composer is enabled exactly when `canAsk` is true and no turn is in flight — not while `session.asking` is true and not while an error is set.
5. `CollectionBriefing` renders up to three server-supplied suggested questions and submits them through the same session action as the record briefing.
6. The composer renders only when `session.hasScope && !session.noAccess`, and is disabled while `session.asking` is true, while an error is set, or while `canAsk` is false (where `canAsk` covers has-scope, access allowed, and the deterministic phase ready). During load it is present-but-disabled, which is the shipped behaviour and is deliberately unchanged.
7. `runAgentLoop` receives `adapter.askTools(scope)`, with the parsed scope threaded from `managementCopilotTurn` into `handleAsk`. On `/leads`, a record scope resolves the record vocabulary and a collection scope resolves the collection vocabulary. A tool outside the resolved list is rejected and fed back, never executed. A page declaring no tools takes the single-shot `final_answer`-only path. No ask outcome — loop failure, empty claims, zero declared tools, or an unconfigured provider — returns a briefing-shaped `claims` payload; all of them return `answerBlocks`.
8. Every claim citing a `tool:<name>:<n>` evidence id still passes `groundingValidator`.
9. No non-`GET` tool exists in `toolRegistry`; the read-only boundary is unchanged.
10. The nine existing page mounts are not edited and inherit criteria 1–6.
11. Every ask-mode tool declares a projection and a row cap, and the serialized tool result stays under the stated byte budget when the upstream returns a full page.
12. The agent loop enforces one overall budget no greater than the server's generation deadline; an ask that exhausts it returns `answerBlocks` rather than a transport timeout, and the derived per-call timeout stays positive on the final iteration.
13. `claimsIn` and the suggested-questions block have exactly one definition, imported by both briefings. Each briefing keeps its own section ORDER and its own heading text: both differ on purpose (a record is read with `changed` first, a list is scanned with `attention` first), and collapsing either would change shipped behaviour or shipped copy.
