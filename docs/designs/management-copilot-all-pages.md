## Problem Statement

The Management Context Copilot works on `/leads`, and only while exactly one lead is selected. `ManagementContextCopilot` is mounted once, from `Management/src/pages/LeadManagement.tsx:561`, with `scope = { leadId } | null`, and `createSession` initializes the deterministic phase as `leadId ? "loading" : "ready"` (`Management/src/features/copilot/useCopilotSession.ts:77`) — so `null` means *zero requests*. The collection view, which is the screen an operator actually starts their day on, has no assistant. The other nine protected pages have no assistant at all.

Requested: the assistant on every other part of the product, and on the general leads page it should surface general things, stats, and suggestions, generated per page.

## What Makes This Cool

Open `/billing` cold, before typing anything, and be told what is off-pattern and what to inspect next — with every sentence clickable back to the field it came from. That is a shift handover, not a chatbot.

The part that makes the claim true rather than marketing: **the analyst's judgment is deterministic.** Each page declares rules; the engine runs them server-side over an allowlisted evidence bundle; the model is only permitted to narrate. "It understands our data" becomes checkable in one click, on any page, because the ground truth was computed before the model was called.

## Constraints

- **Read-only.** The assistant cannot change status, send messages, edit records, or issue documents.
- **The model narrates; it never counts, ranks, or decides what is unusual.** Off-pattern findings are produced by deterministic rules, never by the model and never by statistical inference.
- Adapter fetches run under the caller's forwarded `x-user-*` identity. Downstream service authorization is the ceiling; the copilot cannot broaden access.
- **Field allowlists, never blacklists.** Passport data, credentials, payment instruments, bank details, and unrelated contact fields stay out of the bundle by construction.
- **One shell, ten registrations.** Per-page cost is a descriptor plus a mount, not a bespoke panel.
- **Per-page rollback requires a fix, not an assumption.** `pageKeyAllowed` (`Services/assistant-service/src/controllers/managementCopilot.controller.js:30-36`) currently returns `allowlist.length === 0 || allowlist.includes(key)` — fail-**open**, and three checked-in files document that contract (`Services/assistant-service/.env.example:35`; `infra/terraform/modules/deployment/variables.tf:406-409`; `infra/terraform/deployments/dev/terraform.tfvars.example:27-32`, all "empty = all registered pages"). With `MANAGEMENT_COPILOT_PAGE_KEYS` unset, registering nine descriptors would enable all ten keys at once and per-key rollback would be a no-op. **This change makes the gate fail closed** and therefore flips that documented contract: **every environment with `MANAGEMENT_COPILOT_ENABLED=true` must set `MANAGEMENT_COPILOT_PAGE_KEYS` (including `leads`) in the same release**, or the shipped `/leads` copilot starts answering `404`. That migration is a prerequisite, not a follow-up.
- The underlying page stays fully usable while the briefing loads, when a source 403s, when a source 5xxs, and when the model times out.
- The panel follows `Management/DESIGN.md`: token-only colors, one teal interactive accent, Archivo/Public Sans/JetBrains Mono, both themes, no gradients or chat bubbles.

## Premises

1. The existing adapter interface (`loadEvidence` / `computeInsights` / `defaultQuestions`) fits all ten page keys. No new abstraction layer and no second registry. A collection scope is simply a scope object with no record id.
2. "Off-pattern" is deterministic rules, not statistics and not the model. Each page's rules evaluate predicates over a server-fetched snapshot.
3. Collection mode is first-class on every page, never a fallback. Leads gains `{}` → collection analyst alongside `{ leadId }` → record briefing; the other nine pages are collection-only in v1.
4. On the nine non-lead pages, evidence reveal resolves to the **existing inline evidence-detail region** inside `EvidenceAction` (`Management/src/features/copilot/EvidenceAction.tsx:66-69` opens it, `:114-119` renders it), not to a highlighted field, because no page outside leads publishes `data-copilot-evidence-id` anchors.
5. One shell, ten registrations. `ManagementContextCopilot`'s `children(api)` seam already supports this; it is the *types*, not the component, that are lead-specific.
6. Rollback is per-page-key, and making that true requires the fail-closed gate fix plus the environment migration in Constraints.

All six confirmed by the user before alternatives were generated.

## Approaches Considered

- **Approach A — shared collection engine + per-page rule modules (ideal architecture).** Ten hand-written rule modules over a shared fetch/evidence/insight engine. Best per-page fidelity; largest diff, and the engine seam is only proven around page four. **Not chosen.**
- **Approach C — leads collection + three deep pages (narrow).** Fastest to a demo that cannot fail on grounding, but explicitly defers breadth, which is the thing that was asked for. **Not chosen.**
- **Approach B — one engine, ten declarative descriptors. CHOSEN.** See below.

## Recommended Approach

**Approach B**, with one addition that removes its main risk: an escape hatch. A descriptor covers nine pages as pure data. Any page whose rules outgrow the shared vocabulary contributes a rule *function* instead of a rule *spec* — same engine, same evidence contract, no fork. This keeps the minimal viable shape without the "ten pages, one template voice" failure that was the stated reason to prefer A.

### 1. The rule vocabulary (`Services/assistant-service/src/adapters/rules.js`, new)

Eleven shared predicates, each returning `DeterministicInsight[]` whose `evidenceIds` point at real bundle items:

| Rule | Predicate |
|---|---|
| `staleForDays` | `record[field]` older than N days |
| `expiringWithin` | date field within N days of now |
| `overdueBy` | date field past now, gated on a status field being in a set |
| `stuckInStatus` | status field in a set and unchanged for more than N days |
| `unassigned` | field is null/empty |
| `missingField` | field required by config but absent |
| `ratioBelow` | numerator/denominator under a threshold |
| `thresholdExceeded` | numeric field above a value |
| `zeroOrLowCount` | a computed count at or below a floor |
| `groupedCount` | records sharing a value of `byKey` counted together, at or above a threshold |
| `groupedShare` | one `byKey` group's share of a summed field at or above a percentage |

**Why the last two exist.** Running the Assignment against the real `billing` fields showed the original nine predicates cover *per-record triage* — "which single record is bad, by one field plus a status gate" — and fail on anything relating records to each other. All three of the five constructed overdue invoices that escaped shared one root cause: no predicate can group, compare, or aggregate across records, so "this customer has three overdue invoices" and "two customers are most of what we're owed" were unwritable. An independent adversarial pass over a separate set of ten billing sentences reached the same conclusion from the other direction (3 expressible, 4 awkward, 3 escape) and named a keyed aggregate as the smallest addition, converting roughly four of ten. Grouping is structural, not page-specific: leaving it to the per-page escape hatch would mean every page re-implementing the same aggregation. Both predicates read `bundle.records` (already fetched) and cite through the existing aggregate-evidence producer, so they add no source and no endpoint. `byKey` must be an allowlisted field per descriptor, or a grouping could cross records the caller cannot see.

**Field traps found by the Assignment (verified against `Services/billing-service/prisma/schema.prisma`).** These matter more than they look; each one silently produces a wrong briefing rather than an error.

- **`Invoice.status` and `Invoice.paymentStatus` are different fields, and payment truth lives in `paymentStatus`.** `status` is the document lifecycle and never receives `paid`/`partial`/`paidDate` writes (`invoice.controller.js` writes only `sent`, `viewed`, `cancelled`); receipts update `paymentStatus`, `paidAmount`, `outstandingAmount` (`paymentReceipt.controller.js:137-140`). Any payment-state rule must read `paymentStatus`. The Management client's `Invoice` type exposes `status` with `'paid' | 'partial' | 'overdue' | 'refunded'` in it, and those values never occur there.
- **`overdue` is derived, not stored.** `getOverdueInvoices` filters `status IN ('sent','partial','overdue') AND dueDate < now` (`invoice.controller.js:218`). The endpoint is correct; the `'overdue'` member is simply redundant. Rules should derive overdue from `dueDate`, matching the endpoint, rather than trusting a status value.
- **`unassigned` is dead on every billing document.** There is no owner column; assignment is `crm_leads.Lead.assignedToId`, reachable only through a raw cross-schema join (`invoice.controller.js:20-23`). Do not declare it on the billing descriptor.
- **`stuckInStatus` has no status timestamp.** It can only use `updatedAt`, so any edit — a note, a resend, a PDF regeneration — resets the clock. State the proxy in the insight text ("unedited for N days") rather than claiming the status is stuck.
- **`CreditNote` is unmodelled in the plan.** billing-service has it, with `voucherExpiryDate`, and it was missing from §4's billing descriptor.

**The Assignment's limits.** The five invoices in the worked example (§ worked example in `docs/designs/management-copilot-billing-scenarios.md`) are constructed, not real records; real rows contain messier combinations than any synthetic set. The result is directional evidence that the vocabulary had a structural blind spot, not a measurement. The full scenario catalogue (18 travel-specific AR exceptions, with sources) is the more durable artifact — it is the natural first evaluation corpus for the billing descriptor.

### 2. The engine (`Services/assistant-service/src/adapters/collectionEngine.js`, new)

`createPageAdapter(descriptor)` returns an object implementing the frozen adapter interface.

**Descriptor interface:**

```js
{
  key,                     // one of ManagementPageKeys
  parseScope(input),       // strict, per page; throws AppError(400) before any fetch
  scopeLabel(scope),       // non-empty display string for bundle.context.scopeLabel
  sources: [ { name, shape, url(base), listPath, fields[], recordKind, window?, when?, paging?, maxFetchBytes? }],
  rules: [ spec | fn ],    // spec = shared predicate; fn = escape hatch
  tools: [ toolName ],    // optional; ask-mode tools this page may use
  questionTemplates: [ fn | string ],
}
```

`shape` is `'collection'` (records land on `bundle.records`) or `'singleton'` (the one record lands on `bundle.record`). This is what lets the `settings` page — one document, no list — fit the engine without a special case, and it keeps the descriptor model as the only extension point.

`when(ctx)` gates whether a source is fetched at all. It is the single conditional-source mechanism: analytics uses it for the active tab, and role-scoped sources use it so an admin-only endpoint is never declared for a salesRep. Two separate filters would drift.
`paging` declares how the endpoint pages: `{ param, defaultLimit, totalPath? }`. This is not optional decoration. Three endpoints the plan reads paginate by default and answer `200` over a single page — `GET /leads` (`lead.controller.js:140`, `limit = 10`, and it returns `pagination.total`), `GET /packages` (`package.controller.js:19`, `limit = 12`), `GET /users?role=customer` (`user.controller.js:52`, `limit = 10`). Without a declared `paging`, no truncation probe fires, the mandated `recordCount` baseline reports the page size as the total, and every count-derived rule evaluates only the first page — on `/leads` itself. The engine reads `paging.totalPath` when the endpoint returns a total, and otherwise requests `defaultLimit + 1` and treats the extra row as truncation.

`tools` lists the ask-mode tools this page may use. Where a page declares none, `ask` runs single-shot over the same evidence bundle instead of entering the tool loop — see §6. Today the vocabulary is one lead-bound tool (`Services/assistant-service/src/tools/toolRegistry.js`), so without this the ask box on nine pages would fall through to the deterministic list rather than answer the question.

**Authorization ceiling — one source breaks it today.** The career descriptor reads `GET /vacancies/admin/all`, and that route is registered *above* the admin gate: `Services/career-service/src/routes/vacancy.routes.js:12` registers it, and `router.use(requireAuth, authorize('admin', 'superAdmin'))` only lands at `:15`. With forwarded `x-user-*` headers any authenticated caller reaches it, so the plan's claim that the copilot can never see more than its caller can is false for that page until the ordering is fixed. This change fixes the ordering and gates `/career` in `Management/src/App.jsx:87` to match, because that page is currently registered without role gating.

`loadEvidence(ctx, scope)`:
- For each declared source, fetch through the owning service's internal URL (the existing `*_SERVICE_URL` convention), forwarding the gateway-verified `x-user-*` headers already on `ctx`, **and minting a Google-signed ID token per call via `domainAuthHeader(base)` exactly as `leads.adapter.js:53-56` does.** Domain services run with `allow_unauthenticated = false`, so Cloud Run rejects the call at the platform edge without it. Never the user bearer, never `x-internal-token`.
- **Sources are fetched concurrently, each with its own timeout, and a timeout is a partial, never a failure.** Every eligible source goes through `Promise.allSettled` against two declared budgets: a short one for `mode='deterministic'` (so that phase keeps its ~1s target) and a longer one for `mode='briefing'`. A source that misses its budget lands in `unavailableSources` and renders as a named partial state. This is what makes `unavailableSources` real rather than aspirational, and it is the only thing standing between one degraded domain service and a copilot that looks broken on all ten pages at once.
- **Byte caps as well as row caps.** `maxFetchRows` (default 1 000) bounds rows, but rows are not payload: flight bookings expand into segments and travelers (`flight.controller.js:145`), so a row count does not bound the response body. Each source therefore also declares `maxFetchBytes`, sharing the same truncation rule — over either cap, the source is marked unavailable and no count is derived from it.
- Classify the response: `403`/`404` → `notAuthorizedSources`; network error / `5xx` → `unavailableSources`; `200` → allowlisted projection.
- **Never pre-check ownership** — lead-service lets any salesRep open an unclaimed `PENDING_VERIFICATION` lead, so adapters propagate the domain service's decision verbatim.
- Record every source **attempted** in `bundle.attemptedSources` — the engine's collection path and the leads record path alike (§5). Record projected records on `bundle.records`, aggregates on `bundle.aggregates`.
- **`window` is a post-fetch projection, not an upstream query.** Flight and hotel `listBookings` read only `status` and apply no `take` (`Services/package-service/src/hotels/controllers/hotelBooking.controller.js:82-91`; `Services/flight-service/src/controllers/flight.controller.js:136-147`, which also `include`s segments and travelers). So the engine would pull whole tables into `assistant-service` on every page view and could only slice afterwards, inside the 17s deadline. That is not acceptable for two of the ten pages, so **v1 adds `limit` to both list query schemas and controllers** and the descriptors register last (§8). The `limit` bounds the upstream row count on these two pages; `window` remains the post-fetch projection it is on every other source. Until that lands, no descriptor is registered for either page.
- **A bounded fetch must detect its own truncation.** `maxFetchRows` (default 1 000) and `maxFetchBytes` guard sources that return everything, but neither can fire on an endpoint that quietly pages: it returns a tidy `200` over a truncated slice, and the mandated per-source `recordCount` baseline plus any `zeroOrLowCount`/`ratioBelow` rule would then report a partial count as ground truth. Three of the ten descriptors read implicit-paging endpoints, so truncation detection is driven by the declared `paging` (above), not only by an explicit `limit`. When a source is truncated — by the probe, by either cap, or by a total the endpoint reports — it contributes to `unavailableSources`, and no count-derived evidence or count rule is emitted for it. Open Question 5 covers sizing; this rule is what keeps a wrong number off the screen either way.

`computeInsights(bundle, since)`: runs each declared rule. A spec runs the shared predicate; a function runs page-specific logic. Both receive the same bundle and the same resolved `since` boundary, so `changed` always means "changed since the operator last acknowledged this scope".

`defaultQuestions(bundle)`: filled from `questionTemplates`. The three suggested questions keep exactly one producer, and the model never authors them.

**Evidence bounding is load-bearing.** Do not emit one evidence item per field per record: 500 invoices would produce thousands of items before the model call. Instead:
- emit per-record field evidence only for records a rule flagged, capped (`maxFlaggedRecords`, default 20);
- emit one `computed` aggregate item per count or ratio a rule cites;
- **emit one baseline `computed` item per successfully-attempted source regardless of rule firing** (`recordCount`). Without this, a quiet page produces an empty evidence array, which `isNoAccess` (`managementCopilot.controller.js:60-62`) then misreports as a denial. An empty collection must render as empty, never as forbidden.
- **Every emitted ID goes through the one producer** — baseline `pageEvidenceId(pageKey, 'source', name, 'recordCount')`, aggregate `pageEvidenceId(pageKey, 'aggregate', aggregateName, 'value')`. Never a hand-built ID, and never a three-segment one: the client resolver parses four-or-more-segment IDs only (§3).
- `maxEvidence` default **200**, which must not exceed the briefing prompt's own cap: `serializeEvidence` slices to 200 (`Services/assistant-service/src/ai/prompts/managementBriefing.v1.js:54`). Items beyond the prompt slice are valid citation targets the model cannot see, so a higher bundle cap silently desynchronizes the two budgets.
- **Budget precedence is specified, not incidental.** A busy page can want more evidence than `maxEvidence` allows. When the cap is hit: per-source baseline items and aggregate items are protected; flagged-record evidence truncates first; any insight or claim left citing dropped evidence is pruned. This reuses the pruning rule the grounding validator already applies to unknown IDs rather than inventing a second one, and it protects the baselines the empty-versus-forbidden fix depends on.

`isNoAccess` becomes: **at least one source was attempted, and every attempted source was denied.** Not "any source denied and no evidence", and not the vacuous case: `[].every(...)` is `true`, so without the explicit attempt check a page or analytics tab whose sources are all filtered out by `when(ctx)` would render "you do not have access" when it should render empty.

`attemptedSources` is a cross-cutting contract change: the leads record path (§5) must populate it too, or the shared `isNoAccess` misfires on the shipped `/leads` record page.
**The two phases share one fetch.** The client issues `deterministic` and then `briefing` seconds apart, and each request would independently run the whole fan-out — with eight sources that is sixteen internal calls per page view per operator. A short-TTL server-side cache keyed by `{actorId, pageKey, scopeFingerprint}` (the helper the controller already computes at `managementCopilot.controller.js:100`) serves the second phase from the first. Staleness is bounded in seconds on read-only briefing data, and the TTL is short enough that a mutation is visible on the next page view. On Cloud Run each instance caches independently, so cross-instance staleness is bounded by the TTL rather than eliminated — accepted for v1.

### 3. Evidence-ID producer (`Services/shared/contracts/src/managementCopilot.js`)

Add, beside the existing `leadEvidenceId`:

```js
export function pageEvidenceId(pageKey, recordKind, recordId, field) {
  return `${pageKey}:${recordKind}:${recordId}:${field}`;
}
```

One producer, called by the engine and by the reveal resolver. The existing `leadEvidenceId` stays as-is so the shipped leads drift test keeps passing; migrating leads onto the shared producer is optional and separate.

**The deterministic phase must ship `sources`, not only cited IDs.** The briefing path builds `sources` server-side from its accepted claims, but the deterministic path returns insights only, and `EvidenceAction` renders its inline detail from the `sources` entry — `captured` and `timestamp` are both `null` without one (`EvidenceAction.tsx:54-56`), rendering "not captured" / "not recorded". So a fix confined to the ID parser and the label would make the button exist and open an empty panel in the exact phase the trust claim rests on. The two phases should return the same shape:
- `ManagementDeterministicResult` gains `sources`, built from the deterministic insights through the same helper the briefing path already uses (`Services/assistant-service/src/ai/groundingValidator.js`).
- The client merges deterministic sources the way it already merges briefing and turn sources.
- Because items carry their own `label` and `updatedAt`, no client-side field derivation is needed: the `evidenceFieldPath` generalization and the `Lead ${fieldPath}` label fallback stop being load-bearing and are left alone, which removes three work items from this plan.
- `EvidenceAction`'s `activate()` announce string must also stop saying "Revealed … in the lead record" (`EvidenceAction.tsx:71`) — wrong on nine pages.
- A drift test asserts every evidence ID the engine emits resolves to a `sources` entry in whichever phase produced it.

### 4. The nine new descriptors (ten page keys including leads)

`Services/assistant-service/src/adapters/pages/*.adapter.js`. Each declares `key`, `parseScope`, `scopeLabel`, `sources` (with `window`), `rules`, `tools`, `questionTemplates`.

| pageKey | Sources | v1 scope | Example rules |
|---|---|---|---|
| `overview` | `/analytics/leads/overview`, `/analytics/billing/overview`, `/analytics/salesreps/performance` | `{}` | `thresholdExceeded` on outstanding, `ratioBelow` on conversion |
| `analytics` | the **five** `/analytics/*/overview` routes, plus `/analytics/salesreps/me/performance`, each tagged with `when` | `{ tab }` | `ratioBelow` on conversion, `missingField` on a sample-size caveat |
| `packages` | `GET /packages/stats/all`, `GET /packages` | `{}` | `zeroOrLowCount` on published-with-no-bookings, `staleForDays` on last update |
| `billing` | `GET /billing/{quotations,invoices}/stats`, `GET /billing/invoices/overdue` | `{}` | `overdueBy`, `ratioBelow` on paid/total, `expiringWithin` on quotation validity |
| `users` | `GET /sales-reps/stats`, `GET /users?role=customer` | `{}` | `unassigned` on role gaps, `zeroOrLowCount` on inactive reps |
| `career` | `GET /careers/stats`, `GET /vacancies/admin/all` (see the authorization-ceiling note above) | `{}` | `stuckInStatus` on unreviewed applications, `expiringWithin` on close date |
| `settings` | `GET /admin/settings` | `{}` | `missingField` — escape-hatch case, see below |
| `flights` | `GET /flights/bookings`, ordered by ticketing deadline (not the endpoint's `createdAt desc`) | `{}` | `expiringWithin` on ticketing deadline, `missingField` on traveler data |
| `hotels` | `GET /hotels/bookings`, ordered by cancellation/check-in deadline | `{}` | `expiringWithin` on cancellation window, `overdueBy` on unpaid |

**Conditional sources.** Each source declaration carries a `when(ctx)` predicate, and the engine fetches only the sources whose predicate passes (a source with no `when` is always fetched). Analytics uses it to select the active tab — valid tab ids come from `Management/src/pages/Analytics.tsx:44-50`: `leads`, `billing`, `users`, `itineraries`, `website`, `my-performance`. Without it, a literal implementation fetches all six endpoints on every tab and briefs the billing tab with package and website data. The same predicate covers role scoping: `/analytics/salesreps/performance` is admin-only (`analytics.routes.js:25`), so on `overview` it is declared with a role predicate and a salesRep never fetches it, instead of seeing it permanently denied on the busiest page.

**Role-scoped sources are real and must degrade, not fail.** `/analytics/packages|users|website/overview` and `/analytics/salesreps/performance` are admin-only (`Services/analytics-service/src/routes/analytics.routes.js:15,18,21,25`); `/analytics/salesreps/me/performance` is salesRep-only (`:24`). A descriptor whose sources mix roles will always have some denied for some callers. The engine records those in `notAuthorizedSources` and keeps going — the denial is a partial state on that source, never a no-access state for the page, as long as at least one source succeeded.

**`settings` is the escape-hatch case.** It has one document and no collection. Two options, and the recommendation is the second: skip it, or treat it as a document descriptor whose rules are `missingField` checks (no support email, no street address, no logo). The second is worth doing — `TODOS.md` already records "Contact renders no street address when its environment value is absent", so the settings analyst surfaces a real known defect.

### 5. Leads: collection scope (`Services/assistant-service/src/adapters/leads.adapter.js`)

`parseScope` becomes a union, and `{}` stops being a `400`:

```js
const leadScopeSchema = z.union([
  z.object({ leadId: z.string().trim().min(1).max(255) }).strict(),
  z.object({}).strict(),          // collection
]);
```

`{ leadId: '' }` matches neither branch, so malformed input still rejects before any fetch.

**Filter inheritance is explicitly deferred.** A `{ filters }` scope would fail both strict branches above. v1 collection scope is `{}` — the page's default view. §7's mounts pass `{}`, and `{ tab }` only on `analytics`, whose `parseScope` declares it. Filter-scoped briefings are Open Question 1 and must not be partially wired: a scope the adapter rejects produces exactly the `400 Invalid leads scope` this change exists to remove.

`loadEvidence` branches: `scope.leadId` → the existing record path; otherwise → `GET /leads/stats` plus a windowed `GET /leads`. `computeInsights` branches the same way — record rules stay as they are; collection rules cover unclaimed-queue depth, leads stale beyond a threshold, and unassigned ownership.

**The record path must also push its source name into `attemptedSources`** (`fetchLead` today pushes only to `unavailableSources`/`notAuthorizedSources`). `isNoAccess` is shared and evaluated for both modes, so without this the shipped `/leads` record page either throws on `undefined` or silently loses its "You do not have access to this record." state.

### 6. Client generalization

- `Management/src/features/copilot/types.ts` — replace `LeadCopilotScope` with an opaque `CopilotScope = Record<string, unknown>`, and drop `COPILOT_PAGE_KEY` as a module constant (it is only a default at `useCopilotSession.ts:127`).
- `Management/src/features/copilot/useCopilotSession.ts` — **thread the scope object itself through all four request sites**, which today hand-build `scope: { leadId: capturedKey }` (`:197` deterministic, `:282` briefing, `:363` seen, `:402` ask). The fingerprint (`JSON.stringify(scope)`) is used *only* for session identity and the last-seen key; substituting it into those literals would send `{ leadId: '{}' }` and 400 every phase on every collection page.
- **Replace `normalizeLeadId` (`useCopilotSession.ts:67-72`) with a scope-key derivation, or the collection feature silently does nothing.** That function returns `null` for any scope lacking a non-empty string `leadId` — including `{}` — and the deterministic effect early-returns on a null key (`:190`, `if (!leadId) return undefined;`), so a literal reading of this section still fires zero requests for `{}`. Required derivation: `null` → dormant; any non-null scope with no record key (including `{}`) → collection key; non-empty `leadId` → record key; blank/whitespace `leadId` → dormant, matching the existing client rule that `{ leadId: '' }` and `{ leadId: '   ' }` send no request (`__tests__/useCopilotSession.test.tsx:147-155`). The server still rejects a blank `leadId` with `400` if one is ever sent; the client simply never sends one. That null-vs-`{}` distinction is the whole collection feature, and conflating them silently restores the bug.
- Rename the internal `Session.leadId` to `scopeKey`. The **exported** `CopilotSession.leadId` (`types.ts:66`) is kept as a derived alias — `scopeKey` when the scope is a record, `null` otherwise — so `useCopilotSession.ts:499`, `copilotTestUtils.tsx:53`, and `useCopilotSession.test.tsx:72` keep compiling; changing its meaning is what would break the null/dormant contract.
- **`hasScope` must derive from the scope key, never from that alias.** It is `const hasScope = session.leadId != null` (`useCopilotSession.ts:496`) and it gates three behaviours: `loading` (`:501`), `canAsk` (`:523`), and the dock's auto-open discovery effect (`ManagementContextCopilot.tsx:78-80`) — the last being what makes a collection scope open the panel at all. Implemented literally off a record-only alias, collection scopes get `hasScope === false`: no spinner, a permanently disabled ask box, and no auto-open, so the feature fires its requests and renders nothing. Same trap class as `normalizeLeadId` above, so fix both in one sweep.
- `useCopilotSession.ts:217` hardcodes `partial: false` and reads only `result.context?.noAccess`; the deterministic result's `unavailableSources`/`notAuthorizedSources` (`@travel-crm/contracts` `:197-210`) are discarded, and no component consumes them today. **They must feed the partial/denied presentation**, or a page whose flights source 5xxs renders a full-looking briefing with no partial marker.
- `ManagementContextCopilot.tsx` — `scope: CopilotScope | null`. Keep `pageKey: string` (`:23`).

### 6a. Collection briefing state contract

Nine reachable states. Each one gets copy and treatment, so nine pages cannot invent it three different ways. Tokens are `signal-console` paths.

| State | Trigger | What the user sees |
|---|---|---|
| Deterministic loading | scope changed, first phase in flight | The context stamp paints immediately — page, scope label, `as of` time in `{mono}` — plus one quiet line: "Reading the page…". The stamp is never covered by a skeleton; it is the answer to "what am I looking at". |
| Model pending | deterministic claims painted | Claims stay on screen. A thin progress line sits under the first section heading and the rail marker stays unlit. Appending claims must not shift layout. |
| Empty collection | a source returned 200 with zero records and no rule fired | "Nothing needs you on this page." Plus one line of context with the real count in `{mono}` — e.g. `0 leads in the current view`. Plus a primary action returning to the page's default view. Never a bare "No items found." |
| Partial | ≥1 source 5xx or timed out, ≥1 succeeded | Surviving claims render normally. One inline row under the stamp: `{colors.warning}` dot + "Partially loaded — N sources unavailable", expanding to name them. |
| Denied | ≥1 source 403/404, ≥1 succeeded | Surviving claims render normally. Same row position, deliberately different treatment: no warning colour, wording "Some data is outside your role". A permission boundary is not a fault, and making it look like one trains people to ignore warnings. |
| No-access | all attempted sources denied | Panel body replaced by one sentence: "You don't have access to this page's data." No claims, no suggested questions, no ask box. The stamp still renders. |
| Error / fallback | provider failure or the 20s client timeout | Deterministic claims remain. Inline row: "The summary couldn't be generated." with "Retry" as the only affordance. Never a modal, never a full-panel error state. |
| Feature-off | turn route 404 | The shell renders nothing at all — no frame, no spinner, no error. Telemetry only. |
| Success | claims present | Claims, suggested questions, ask box, and **no status row**. Silence is the success state; a green "loaded" banner would be chrome. |

Ask mode reuses the shipped conversation states (pending, answered, error). Its one addition: when an answer would need data outside the bundle, it says so in a plain sentence rather than restating the briefing.
**Claim form.** A claim is an unpadded row separated from the next by a hairline (`{colors.border}` at low emphasis), with no border, no background, and no card container. Twenty claims must read as one briefing, not twenty boxes. The claim sentence carries the voice at body size; the source tag and any cited value sit in `{mono}` so numbers stay scannable. This deliberately avoids the shared `Card` primitive: a card mosaic is the named slop pattern for exactly this kind of surface, and it would also make a full collection briefing three screens long.

**Severity discipline.** Severity is a small marker plus type weight on the claim text. `{colors.destructive}` is used on the marker for `critical` only, `{colors.warning}` on the marker for `warning` only, and `info` carries no colour at all. No row tint, no coloured left border, no background wash. `{colors.primary}` (teal) stays reserved for interactive affordances and focus, per `DESIGN.md`. The test: on a page with six findings, the reader should be able to count the criticals at a glance precisely because nothing else is coloured.
**Accessibility and viewport.** Severity is never colour-only: every marker carries an accessible name ("critical", "warning", "information") so a screen reader and a colour-blind reader get the same information, and the claim's severity leads its announcement. Claim rows, source tags, and suggested-question rows are all interactive and must meet a 44px minimum touch target — they are the primary controls in the below-`xl` drawer. `{colors.muted-foreground}` on the panel surface must hold the project's 4.5:1 minimum at body size. Section headings are real headings so the panel is navigable by heading, and the existing `Announcer` carries state changes (empty, partial, denied, error) rather than relying on a visual row alone. **Evidence reveal is viewport-independent on the nine new pages**: `pinEvidence` targets a DOM anchor that only `/leads` publishes, so everywhere else `activate()` falls through to the inline detail region, which works at every width. The `xl`-only constraint documented for the shipped lead panel does not extend to these pages.

**Design-system entries.** The claim row and the inline status row are new patterns and both get named entries in `DESIGN.md`'s Components section with their tokens, per the rule at `DESIGN.md:288`. The source tag and severity marker compose the existing `badge` primitive with `success`/`warning`/`destructive`/`muted` tokens rather than using its generic variants, as that entry already instructs.

## Open Questions

1. **Should collection briefings inherit the page's active filters?** Deferred for v1 (§5). A briefing describing a different list than the one rendered is worse than no briefing, so this is the first follow-up, not a v1 feature.
2. **Does "what I'd inspect next" click through?** **Resolved: yes.** Every attention item carries a primary action. Where the page has a record surface the action opens the record (on `/leads` this sets `scope = { leadId }` and swaps the briefing to record mode); where it does not — the other nine pages in v1 — the action reveals the cited evidence instead. Both are read-only, so the constraint holds. A finding the reader cannot act on is a report, not a tool, and the journey's intent peaks at exactly this step.
3. **`/analytics` tabs: one descriptor or six?** One descriptor with `scope.tab` and per-source `when` (§4), because the tabs share a shape and six descriptors would be six copies of the same rules.
4. **Do we migrate `leadEvidenceId` onto `pageEvidenceId`?** Not in this change. The leads drift test passes and the migration buys nothing until a page publishes anchors.
5. **How large do flight and hotel booking histories get in practice?** Determines whether `limit` alone is enough or the descriptors need a date-window scope too. `maxFetchRows` and `maxFetchBytes` protect correctness either way — a source over either cap is marked unavailable rather than reported from a partial fetch.

## Success Criteria

- Every enabled page key returns a deterministic briefing with at least one grounded insight on non-empty data.
- **An empty collection renders as an empty state, never as no-access.** No-access requires every attempted source to be denied.
- **Source denial and source outage are visible.** A `403`/`404` on one source shows a named denied state while sibling sources still render; a `5xx`/timeout shows a named partial state. Neither is silently swallowed, and neither crashes the page.
- 100% of rendered claims cite an evidence id present in that turn's bundle, and every such id resolves to a working evidence action — record fields, aggregates, and source baselines alike.
- **Extensibility metric:** adding an eleventh page touches exactly **four** files — one descriptor, the registry, the `ManagementPageKeys` enum in `@travel-crm/contracts` (the wire request is keyed off `z.enum(ManagementPageKeys)`), and one client mount — plus one environment allowlist entry.
- Every page remains interactive throughout: deterministic phase visible within ~1s of scope stability, model phase appended, page never blocked or dimmed. The two phases carry separate per-source budgets — the deterministic phase's short budget is what keeps the 1s target true, and a source that misses it renders as a named partial rather than delaying the paint.

## Design decisions (added by /plan-design-review)

- **Section order is scope-dependent.** Collection scopes lead with `attention` (a list is scanned for problems); record scope keeps the `current_state`-first narrative order (a record is read). Specified in §6.
- **Claim form:** unpadded hairline rows, no card container, body-size text with `{mono}` for cited values. Chosen against the shared `Card` primitive, which at twenty claims is the stacked-cards slop pattern.
- **Severity discipline:** marker plus type weight; `{colors.destructive}` on `critical` markers only, `{colors.warning}` on `warning` markers only, `info` uncoloured; no row tints or left borders; teal stays reserved for interaction.
- **Full state contract (§6a):** nine reachable states, each with copy and treatment. The empty state is a feature — real count in `{mono}` plus a primary action — not "No items found." Partial and denied are deliberately different treatments, because a permission boundary is not a fault.
- **Attention items carry a primary action:** open the record where a record surface exists, otherwise reveal the cited evidence. Both read-only. Resolves the eng-review open question.
- **Auto-open:** once per page key per operator, then honour the persisted collapsed state. The record-scope rule fires once because a record has a first visit; a collection does not, so extending it literally would open the panel on every page load across ten pages.
- **Two new primitives get DESIGN.md entries** (`DESIGN.md:288` requires it): the claim row and the inline status row. Source tag and severity marker compose `badge` with semantic tokens.

### Design "NOT in scope"
