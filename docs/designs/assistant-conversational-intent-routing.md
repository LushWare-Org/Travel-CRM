## Problem Statement

Before PR1, the shipped site-wide assistant had two legal outcomes: `navigate` and `answer_faq_policy`. `Services/assistant-service/src/ai/prompts/assistantTurn.v1.js` explicitly routed every message matching neither capability into `answer_faq_policy`. Greetings, thanks, conversational repair, safe general travel questions, and unrelated requests therefore fell into policy retrieval and often received `FALLBACK_POLICY_MESSAGE`. Visitors experienced a broken or unfriendly chatbot even though the model understood the message.

The product boundary is a friendly travel concierge, not an open-domain assistant: handle social turns and low-risk travel planning naturally, keep company-specific and sensitive claims grounded, and redirect unrelated requests with a warm explanation plus useful next actions.

## Demand Evidence

The user reported observing this failure in real visitor sessions and rejected the current response tone. Exact sanitized messages were not supplied in this session, so intent frequency, confusion rates, and transcript-level demand remain unmeasured. The code path independently proves the failure is reachable for every unmatched message; the assignment below closes the evidence gap before thresholds are frozen.

## Status Quo

1. The client sends a sliding conversation window and its current route allowlist to `POST /api/v1/assistant/turn`.
2. `assistant.controller.js` fetches policy documents before every model call, even for greetings and navigation.
3. One Gemini structured-output call must choose `navigate` or `answer_faq_policy`.
4. The controller validates routes against the client allowlist and policy snippet IDs against server-retrieved candidates.
5. Anything outside those two tools is forced through the policy no-match fallback.

## Target User & Narrowest Wedge

Anonymous visitors using the existing floating assistant on public browsing pages. The narrowest complete change is:

- friendly greetings, thanks, farewells, and conversational repair;
- short, low-risk travel planning guidance;
- warm redirection for clearly unrelated requests;
- unchanged deterministic handling for navigation and company policy;
- escalation instead of generation for price, booking, visa, health, and safety claims that lack an approved source.

No new screen, conversation store, service, or open-domain answer engine is included.

## Constraints

- Keep `assistant-service` stateless and preserve the existing request/response envelope.
- Keep navigation client-side and executable only from the request's `availableRoutes` allowlist.
- Keep company policy quotes server-retrieved and server-verified. The model may select snippet IDs, never author the quoted policy.
- The fast path must never answer company policy, prices, bookings, visa, health, safety, legal, emergency, or other high-consequence claims.
- Production logs and telemetry must not contain raw visitor messages or personal data. Sanitized examples enter the evaluation corpus only through deliberate human review.
- Stage-one failure or uncertainty fails open to the upgraded safe resolver, not to a user-visible error and not to today's two-tool fallback.
- No new agent framework. Reuse `generateStructured`, prompt versioning, Zod enforcement, pino/request IDs, and the current controller boundary.
- The exact small Gemini model must be a pinned model confirmed through Google's live Models API and benchmarked on this evaluation set. Add a separate `GEMINI_ROUTER_MODEL` configuration; do not assume or invent a model ID. If unset, use the current configured model rather than silently selecting an unverified cheaper model.

## Premises

1. The user explicitly requires two-stage routing now, rather than waiting for a larger labeled corpus.
2. Stage one is a confidence-gated intent gate. It directly handles only safe, confident fast paths and abstains on ambiguity, mixed requests, protected topics, or model failure.
3. Abstention routes to an upgraded stage two containing conversational and off-topic outcomes. Sending abstentions to today's `navigate`/`answer_faq_policy` handler would preserve the bug.
4. Numeric model confidence is a routing signal, not calibrated probability. The commit threshold is selected against held-out labeled examples and may be disabled if hard safety targets cannot be met.
5. General travel guidance is limited to low-risk planning and inspiration. Current conditions, availability, prices, bookings, entry requirements, visas, health, safety, legal rights, and emergencies require approved sources or human escalation.
6. Friendly off-topic handling means: acknowledge the request, state the travel-assistant boundary without blaming the visitor, then offer two or three supported next actions.

## Landscape Findings

- **Tried and true:** task-oriented systems use an intent classifier with confidence and ambiguity thresholds, then fall back or hand off instead of forcing a low-confidence intent. Rasa documents this threshold-and-handoff pattern.
- **Current implementations:** semantic routers embed example utterances, choose a route by similarity, and return no route below a tuned threshold. Aurelio Labs' Semantic Router exposes this exact route/no-route behavior and threshold optimization.
- **Current research:** Zaera et al. combine an efficient classifier, an uncertainty score, and an LLM only for uncertain inputs. Their 2025 system reports state-of-the-art out-of-scope results on public benchmarks and a production dataset, but depends on thousands of labeled utterances and calibrated routing thresholds.
- **Project-specific conclusion:** the research validates the user's requested cascade, but not an uncalibrated hard router. With no supplied labeled corpus, the safe initial implementation is a small structured model gate with narrow direct-response classes and aggressive abstention. The same contract can later be backed by a trained uncertainty model without changing the public API.

## Cross-Model Perspective

Codex agreed that the assistant needs a first-class social/conversational outcome rather than a friendlier policy fallback. It challenged the original abstain wording: today's stage-two handler cannot receive abstentions safely because it still forces unmatched turns into `answer_faq_policy`. The premise was revised so stage two is upgraded first.

Its 48-hour proposal was a small structured intent gate with explicit `defer`, a new stage-two concierge outcome, a sanitized golden evaluation set, and telemetry for stage-one intent/confidence, final tool, deferral reason, latency, and fallback use. It recommended skipping embeddings and trained-classifier infrastructure until real labeled traffic exists.

One correction to the proposal: a model's self-reported `confidence` is not calibrated probability. This design therefore derives the commit threshold from held-out examples and treats failure to satisfy safety targets as a reason to abstain more, not to lower the bar.

## Approaches Considered

- **Small-model intent gate plus upgraded resolver, chosen.** Structured classifier call; safe confident social/off-topic fast paths; every other class and every uncertainty goes to upgraded stage two. Reuses current Gemini and controller seams and can later swap router implementations.
- **Trained uncertainty router plus LLM refiner, deferred.** Closest to the strongest research and best long-term cost/latency at scale, but currently blocked by the absence of a labeled production corpus and would add training, serving, versioning, and drift ownership.
- **Semantic example router plus LLM refiner, rejected for now.** Easier to update than a trained model and naturally supports no-match, but adds embeddings, thresholds, and runtime dependencies without trained-model accuracy.

## Recommended Approach

### 1. Stage-one contract

Add a versioned router prompt/schema beside `assistantTurn.v1.js`. It returns classification metadata only:

```json
{
  "intent": "social | off_topic | navigation | company_policy | travel_general | sensitive | ambiguous",
  "confidence": 0.0,
  "hasActionableClause": false,
  "socialSubtype": "greeting | thanks | farewell | repair | none",
  "reasonCode": "single_social | unrelated | site_action | grounded_claim | low_risk_travel | protected_topic | mixed_or_unclear"
}
```

Rules:

- `social`: greeting, thanks, farewell, or conversational repair with no actionable request.
- `off_topic`: clearly unrelated to travel or this site, with no protected or actionable clause.
- `navigation`: asks to reach a page or site feature.
- `company_policy`: asks about LushWare policy, prices, availability, booking state, cancellation, refund, baggage, or company commitments.
- `travel_general`: low-risk inspiration or planning advice that does not depend on current conditions or company facts.
- `sensitive`: visa/entry, health, safety, legal, emergency, financial, or other high-consequence guidance.
- `ambiguous`: mixed intents, unclear referents, conflicting clauses, or anything the router cannot classify confidently.

`hasActionableClause=true`, `sensitive`, `ambiguous`, schema failure, timeout, or AI unavailability forces abstention. A greeting with a trailing question such as “Hi, can I cancel tomorrow?” is not a social fast path.

### 2. Commit/abstain policy

Stage one never answers a factual question. Its direct outcomes are reviewed server-owned copy, so a classifier mistake can cause an unhelpful redirect but cannot fabricate policy, price, booking, visa, health, or safety information.

The server may commit directly only when all conditions hold:

- intent is `social` or `off_topic`;
- `hasActionableClause` is false;
- the response passes schema validation;
- confidence meets the threshold selected by the evaluation procedure below;
- the selected fast-path class is enabled for the detected language.

Every other result proceeds to stage two. Both direct-response classes start disabled. A class may be enabled only after at least 50 sanitized real visitor examples of that class are available. Model/threshold selection uses nested stratified five-fold cross-validation: each outer fold remains untouched while its threshold is selected on inner folds. Report pooled outer-fold point estimates plus 95% confidence intervals. The class needs at least 95% observed precision, a 95% confidence lower bound of at least 90%, and zero protected-topic or actionable mixed turns committed directly. Synthetic adversarial cases remain release-blocking safety tests but do not count toward real-example support or precision. If a class misses any gate, it remains stage-two-only. Threshold changes require the same replay procedure.

This is intentionally abstain-heavy. A self-reported `confidence` value is not probability and cannot override the class enablement, mixed-intent, or protected-topic rules.

### 3. Friendly fast-path responses

Stage one classifies; server code owns direct responses.

- `social`: choose stable reviewed copy by explicit `socialSubtype`, with a neutral fallback such as “Hi! I can help with destinations, packages, trip planning, and LushWare questions. What are you planning?”
- `off_topic`: return a fixed warm redirect that acknowledges briefly, states scope, and offers supported actions. Example: “I’m here to help with travel and LushWare trips. I can help you explore destinations, find packages, plan a trip, or answer a company-policy question.”

Do not reuse `FALLBACK_POLICY_MESSAGE` for either path. Do not randomize copy; stable output is easier to test, localize, and measure.

### 4. Upgraded stage-two resolver

Replace the two-outcome vocabulary with four explicit outcomes:

- `navigate`: unchanged route selection and client allowlist validation.
- `answer_faq_policy`: unchanged server-selected candidate verification and fixed no-match fallback.
- `respond_conversationally`: `mode = social | travel_general`; permits a short model-authored social response, clarification question, destination inspiration, or generic planning suggestion.
- `redirect_off_topic`: server ignores model-authored answer text and returns the reviewed deterministic redirect copy.

Stage two receives the stage-one intent as an untrusted hint, not an instruction. Gemini generation keeps the repository's proven flat merged JSON Schema. The server first validates the recognized tool enum, then canonicalizes only that tool's allowlisted fields into a safe internal shape; missing or invalid fields map to the tool's existing decline/fallback. A strict discriminated union validates the canonical result before dispatch. `respond_conversationally` with model-authored text is accepted only when the stage-one class is `social` or `travel_general`; otherwise the controller replaces it with fixed server-owned social, escalation, or redirect copy. The controller strips HTML, rejects executable URLs, and retains the existing non-empty and 2,000-character limits. These checks do not make factual prose “verified”: the stage-two prompt and evaluation corpus constrain `travel_general` to low-risk inspiration and planning. Company policy, pricing, availability, booking, visa, health, safety, legal, emergency, and financial answers still require a grounded tool or fixed escalation.

For `sensitive`, stage two returns a fixed escalation response and supported contact/navigation options rather than model-authored advice.

### 5. Client and wire contract

Both fast paths and all stage-two outcomes keep the existing `{ success: true, data: { toolCall, serverResult, message } }` envelope. The server returns:

- `respond_conversationally`: `serverResult = { mode: "social" | "travel_general", source: "router" | "resolver" }`;
- `redirect_off_topic`: `serverResult = { redirected: true, source: "router" | "resolver" }`.

The client changes are in scope and atomic with the server vocabulary change:

- expand `AssistantTurnTool` in `Client/src/services/api/assistantTurn.ts`;
- add conversational and redirect variants to `AssistantTurnData`;
- make `deriveTurnData` branch explicitly on all four tools instead of treating every non-navigation result as FAQ;
- render no extra quote/navigation panel for conversational and redirect turns; the assistant bubble already contains the complete response;
- expand `AssistantEventTool`, backend `recordEventSchema`, and related tests;
- keep navigation chips derived only from server-resolved `serverResult`, never model args.

No server tool value may ship before the client parser and renderer accept it; otherwise Zod rejection turns every new response into `ASSISTANT_ERROR_MESSAGE`.

### 6. Policy retrieval

The current 60-second cache makes policy retrieval cheap after the first successful fetch, while omitting candidates from an abstained mixed turn can reproduce the policy fallback bug. Therefore every stage-two turn fetches/retrieves candidate snippets before the resolver call, exactly as today. Only stage-one direct `social` and `off_topic` responses skip retrieval. There is no grounded retry and no third model call.

This keeps the correctness boundary simple: whenever stage two selects `answer_faq_policy`, it already has the candidates required for server verification. A failed retrieval still produces the existing verified no-answer fallback.

### 7. Evaluation corpus and replay

Create a versioned, sanitized test corpus with at least:

- 50 sanitized real social turns, split across greeting, thanks, farewell, and repair;
- 50 sanitized real clearly off-topic turns;
- 20 navigation requests;
- 20 grounded company-policy requests;
- 20 low-risk travel-general requests;
- 20 protected/sensitive requests;
- 30 adversarial mixed turns, including greeting + policy, prompt injection, quoted unrelated text, negation, typos, and multi-intent requests.

Each direct-response class needs its own 50 real visitor examples before enablement. Synthetic rows fill adversarial and rare edge cases but do not count toward class support or precision. Each row records expected stage-one class, social subtype, whether direct response is permitted, and allowed final stage-two outcomes. Keep personal data out of fixtures.

The replay report includes per-class precision/recall, confusion matrix, abstain rate, fast-path coverage, protected-topic/actionable false commits, stage-one/stage-two disagreement, and final-tool mismatch. Nested cross-validation reports outer-fold sample counts and pooled 95% confidence intervals; threshold selection never sees its outer evaluation fold.

### 8. Latency, retries, and failure behavior

The client currently has a 15-second default timeout, while `generateStructured` can retry three 30-second attempts. Two-stage routing cannot fit that contract without explicit budgets.

- Add an optional `maxAttempts` parameter to `generateStructured`, defaulting to today's `3` so existing callers do not change.
- Give the assistant turn controller a 27-second monotonic server deadline and pass the remaining budget into each external call.
- Router call: `maxAttempts=1`, `timeoutMs=min(1500, remainingBudget)`, and no retry/backoff. Failure immediately abstains.
- Policy retrieval remains serial after the router and already has a 3-second timeout.
- Resolver call for this endpoint: `maxAttempts=1`, `timeoutMs=min(20000, remainingBudget)`.
- Give `sendAssistantTurn` an endpoint-specific 30-second client timeout with `retry:false`. The 27-second server deadline reserves at least three seconds for controller work, gateway transit, serialization, and network overhead.
- Record server-deadline exhaustion separately from provider 429/503. Abort rather than start or sleep through work that cannot finish within the remaining deadline.

Other failure rules:

- Stage-one invalid JSON, timeout, 429, 503, or unavailable model: continue to upgraded stage two when the request budget permits and record the failure category.
- Stage-two failure: retain the existing client error path and previously rendered navigation chips.
- Stage-one/stage-two disagreement: stage two wins; record a mismatch counter for later router improvement.
- Unsupported or sensitive request: fixed friendly escalation, never fabricated guidance.
- Empty or oversized model message: retain the existing non-empty and 2,000-character server enforcement.

### 9. Telemetry and privacy

Add one nullable `metadata Json?` column to `AssistantEvent` through a Prisma migration rather than adding many sparse columns. The existing client event endpoint remains for client-observable events. It does not receive router internals.

`assistant.controller.js` writes one best-effort server-owned `resolution` event per completed or failed turn, correlated by `sessionId` and the latest user-message ID as `turnId`, with the final tool/route and metadata. A shared internal telemetry helper validates the server-built metadata against a `.strict()` Zod object with bounded strings/numbers before `prisma.assistantEvent.create`; telemetry failure never changes the turn response. The allowlisted fields are:

- router version and configured model identifier;
- predicted intent, social subtype, and confidence bucket;
- committed versus abstained and reason code;
- final stage-two tool;
- stage-one and stage-two latency;
- fallback/escalation used;
- model/schema/timeout failure category.

Expand the client `AssistantEventTool` and backend external `recordEventSchema` tool enums in the same cutover, but do not send server-only metadata through the browser. Both the internal metadata schema and the external event schema use `.strict()` so unknown keys are rejected rather than silently stripped. Never log or persist messages, prompt text, policy snippets, contact details, or model responses. A separate human-reviewed workflow may add externally supplied, already-sanitized examples to the corpus.

Keep the client's existing `response` event because it proves the browser received and rendered a result. The server-owned `resolution` event records model/router completion. Their distinct names prevent double-counting, and `turnId` supports exact joins when both facts are needed.

## Open Questions

- Exact pinned `GEMINI_ROUTER_MODEL`: resolve through live model availability plus the routing benchmark; production must not use a floating `-latest` alias.
- Exact reviewed social and off-topic copy: use the examples above as behavioral requirements, then approve final brand wording during implementation review.
- Which supported languages need independent threshold validation. Multilingual greetings belong in the corpus; production fast-path enablement is per language if performance differs materially.

## Success Criteria

- Zero policy-fallback responses for held-out pure greetings, thanks, farewells, and clearly off-topic turns.
- Zero direct fast-path responses for protected/sensitive or mixed actionable turns in the held-out corpus.
- Each enabled direct-response class meets its minimum support and precision/confidence gates from the Commit/abstain policy; classes remain disabled by default until they do.
- One hundred percent of executable navigation targets still trace to the request's `availableRoutes` allowlist.
- One hundred percent of company policy quotes still trace to server-retrieved candidate snippets.
- Stage-one failures degrade to stage two without creating a user-visible failure by themselves.
- Every new tool value parses and renders through the client without an error banner or empty extras panel.
- The endpoint completes inside its explicit 30-second client deadline; fast-path and two-stage p50/p95 latency and per-turn model cost are recorded before rollout.
- Telemetry contains no raw visitor text or personal data, and rejects unknown metadata keys.

## Dependencies

- Existing `generateStructured` model seam and Gemini SDK in `assistant-service`, extended with a backward-compatible `maxAttempts` option.
- Existing Zod/JSON schemas, controller dispatcher, policy retrieval package, route allowlist, telemetry endpoint, and response envelope.
- Client parser, `AssistantTurnData`/`deriveTurnData`, widget extras, event tool enum, and related tests updated atomically with the server tool vocabulary.
- Nullable `AssistantEvent.turnId` and `AssistantEvent.metadata` fields, a composite session/turn index, Prisma migration, strict event validation, and matching client payload support.
- A separately pinned router model configuration and deployment env wiring.
- At least 50 team-supplied, already-sanitized real visitor examples for each direct-response class before that class can be enabled; the assistant service itself does not retain transcripts.
- Existing CI/CD and Cloud Run deployment cover distribution; no new service or package is introduced.

## The Assignment

Before either direct-response class is enabled, the user or product team must supply at least 50 already-sanitized real visitor messages of that class from the external session-review source where this issue was observed: 50 `social` examples for the social fast path and 50 `off_topic` examples for the off-topic fast path. The assistant service has no transcript store and this design does not add one. Label all supplied messages across the full intent vocabulary, mark whether a direct response would have been safe, and record the reply the visitor should have received. Remove names, emails, phone numbers, booking references, and other personal data before examples enter the repository. Implementation may proceed with PR1 and synthetic regression cases while data is collected; each class remains disabled independently until its own real-data and nested-evaluation gates pass.

## What I Noticed

- You drew a product boundary in one sentence: “general messages also, not too general.” You rejected both a greeting-only patch and an open-domain chatbot.
- You pushed back on the initial single-call recommendation and explicitly required two-stage classification. The design keeps that decision while adding the uncertainty gate the research says it needs.
- You identified tone as product behavior, not cosmetic copy: an irrelevant message should receive a helpful redirect, not a technically correct refusal.

## Engineering Review Addendum

### Accepted implementation sequence

The implementation is split into two independently releasable PRs.

```text
PR1: safe resolver and delivery contract
  client accepts four tools behind disabled server flag
      -> deploy client
      -> verify cached-bundle propagation
      -> deploy resolver + canonical schemas + bounded deadline
      -> enable new outcomes
      -> keep flag through one rollback window
      -> remove temporary flag

PR2: measured routing optimization
  receive sanitized real examples
      -> build router + replay harness
      -> nested cross-validation
      -> add resolution telemetry migration
      -> deploy with direct classes disabled
      -> enable each class only after its gate passes
```

PR1 delivers the safe visitor-facing core without depending on an uncalibrated factual-response classifier: greetings and clearly off-topic turns receive fixed server-owned copy. Model-authored `travel_general` remains disabled until PR2 supplies an independent stage-one gate and live evaluation.

### PR1 scope: resolver, wire contract, and bounded delivery

1. Verify the existing assistant-service to user-service Cloud Run authorization before rollout. Inspect the real call path/logs; add the missing `run.invoker` binding only if the recorded P1 risk in `TODOS.md` is confirmed.

4. Update the client Zod enum, `AssistantTurnData`, `deriveTurnData`, widget extras, and event tool enum before enabling server responses. Conversational/redirect turns render the bubble only.
5. Add a temporary server feature flag for the new outcomes. Client-first deployment is mandatory. Keep the flag through one tested rollback window, then delete it rather than creating permanent compatibility code.
6. Move deadline ownership into PR1: endpoint-specific 30-second client timeout, 27-second controller deadline, backward-compatible `maxAttempts`, one resolver attempt capped at the remaining budget.
7. Preserve existing client `response` telemetry in PR1.

### PR2 scope: router, evidence, and resolution telemetry

1. Accept only team-supplied, already-sanitized real messages; do not add transcript persistence. Require 50 real examples per direct-response class before that class can be enabled.
2. Add the router prompt/schema, evaluation corpus, live replay command, nested stratified five-fold evaluation, and class enablement configuration.
3. Reserve 1.5 seconds of the existing 27-second server deadline for one router attempt. Abstention or failure proceeds to the resolver with the remaining budget.
4. Add nullable `AssistantEvent.turnId` and `metadata`, a composite session/turn index, strict internal/external validation, `turnId` in browser response events, and server-owned `resolution` events keyed to the same triggering user-message ID.
5. Enable model-authored `travel_general` only when stage one independently returns `travel_general` and stage two agrees. Deploy with both direct fixed-response classes disabled; enable `social` and `off_topic` independently only after their data, precision, confidence, and zero-leak gates pass.

- `Services/e2e-tests` already provides the real gateway/service integration harness.

### NOT in scope

- Trained intent classifier or embedding router: deferred until substantially more labeled traffic exists.
- Transcript storage or raw-message telemetry: prohibited by the privacy boundary; examples arrive sanitized from the external review source.
- Open-domain answers, live travel conditions, prices, availability, booking state, visa, health, safety, legal, emergency, or financial guidance without an approved source.
- New conversation service, agent framework, vector database, or client-side navigation authority.
- Broad telemetry retention/sampling redesign: remains the existing P3 TODO; PR2 adds bounded metadata but does not solve table lifecycle.
- CGNAT/rate-limit redesign, fallback contact parity, and unrelated widget impression fixes: existing TODOs, not prerequisites for this behavior.
- Policy-fetch negative caching: existing P3 performance work; the 27-second request deadline prevents unbounded turn work, while cache behavior remains unchanged.
