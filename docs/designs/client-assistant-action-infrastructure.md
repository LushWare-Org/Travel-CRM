## Problem Statement

The site-wide client assistant shipped phase 1 with four recognized outcomes and exactly one client-executed capability: `navigate(route)`, which carries a route name and nothing else. It can take a visitor to `/packages`. It cannot express "Dubai packages under $1000", because the packages page reads destination, state, country and category from the URL but keeps price range, duration, min rating, sort and view mode in local `useState` (`Client/src/features/packages/PackagesContainer.tsx:39-44`), and nothing outside the component can write that state. It cannot touch any form, anywhere. And the model has no way to learn that a page has filters at all, so "what filters under $1000" is not merely unanswered, it is unanswerable.

The ask: give the assistant a real action surface over the site, where the frontend supplies the tools rather than only exposing whole pages.

## What Makes This Cool

The assistant stops being a help widget that describes the site and becomes a co-pilot that operates it.

- "Dubai under a thousand" becomes one turn and one shareable URL, not a description of where to click.
- A visitor on the packages page can ask "and what if we sort by price" and watch the page change under them.
- Half-typed forms become filled forms, with the visitor keeping the button.
- Everything the assistant says about what is on screen is true by construction, because the page reports its own state instead of the server guessing at it.

## Constraints

- Extends the shipped phase-1 surface (`assistant-service`, `AssistantWidget`, `availableRoutes`). One assistant, one vocabulary, growing.
- No new AI framework, and no new contract package. `Services/shared/contracts` already exists and is consumed as `@travel-crm/contracts`; this design adds a domain module to it.
- The model never authors an executed action. It names one action from a fixed union, supplies arguments, and both the server and the client validate before anything runs.
- **The client-sent manifest is untrusted input, not just a validation input.** `/api/v1/assistant/turn` is public and unauthenticated. `capabilities` and `currentView` are strings written by the caller and pasted into the model's prompt, so the server must treat them as data throughout: strict patterns on every identifier, a hard size cap, and the same explicit data-not-instructions labelling (spotlighting) the phase-1 doc already requires for package descriptions. Schema validation constrains what the model may say back; it does not constrain what an attacker may put into the prompt.
- The assistant never dispatches a form submit. Not on contact, not on review, not on booking.
- Inherited exclusions: the widget does not mount on `/planner`, `/package/:id/customize`, `/login`, `/my-account` (`Client/src/config/assistantRoutes.ts`). This design adds `/reset-password/:token`, since a prefilled credential field is a path it deliberately does not open.
- Gateway stays the single public entry point. `/api/v1/assistant/turn` continues to reuse `itineraryChatLimiter`.
- **The rollout flag must not gate the new actions.** `ASSISTANT_CONVERSATIONAL_OUTCOMES_ENABLED` is hard-set to `"false"` for deployment (`infra/terraform/modules/deployment/locals.tf:172`), and `canonicalizeAssistantTurnResponse` rewrites any tool outside `LEGACY_ASSISTANT_TOOLS` into an `answer_faq_policy` fallback when it is off (`assistantTurn.v1.js:70-76`). Client actions go on an always-enabled core set; the conversational pair stays behind the flag.
- **The controller dispatch must learn the new outcomes.** `assistant.controller.js:212-213` ends its switch with `default: throw new AppError('AI returned an unrecognized tool', BAD_GATEWAY)`, so a turn resolving to a new action returns 502 until explicit cases exist.
- **The turn envelope is not shared today.** `Client/src/services/api/assistantTurn.ts` is a hand-maintained mirror, it parses the outgoing payload before posting, zod strips unknown keys, and its tool enum is a closed four-value list. Any new request field or outcome must be added here or it dies silently in either direction.
- **Compatibility is additive in both directions.** The client is a static bundle and a browser can hold an old one across a deploy or a rollback. Every new request field is optional with a default; every new response field is optional on the client with a safe default (`params` defaults to `{}`); an unrecognised outcome renders the existing generic bubble rather than failing the parse. Deploy order: server first, then client. A new server with an old client is inert; a new client against an old server must still navigate.
- Gemini flat-schema constraint. `assistantTurn.v1.js` records that nested and conditional object schemas produced `args: {}` in live structured-output calls. Every argument travels as a flat optional scalar key, and per-action narrowing happens after generation.
- **Price is a numeric budget, not a bucket identity.** `priceMax` is a number in the deployment's display currency, and the sidebar's bucket buttons write their own bounds into the same parameter. Bucket ids are removed entirely: a thousand-wide bucket cannot express "under $1500", and a bucket id derived from a label reintroduces the currency coupling the encoding exists to avoid.
- **Catalogue size is a correctness input, and this branch fixes it.** `PackagesContainer.tsx:65` fetches `{ limit: 100 }` and filters client-side, so filtering, sorting and the destination list were all computed over a truncated set. This branch moves filtering and sorting to package-service (see step 1), which removes the ceiling rather than qualifying it.

## Premises

1. This extends the shipped phase-1 assistant rather than adding a second chat surface.
2. The client owns the permission boundary; the server owns the implementation. Server-executed tools return facts, are implemented in the server registry, and are allowlisted per page by that page's adapter (`billing.adapter.js:80`, `toolRegistry.js:253`). Client-executed capabilities mutate UI state and are reachable only if the browser said so this turn. The server never keeps a duplicate of the client's action vocabulary.
3. URL parameters own addressable state: the packages filters (price, duration, rating, sort), pagination, view mode, and the `destination`, `state`, `country` and `category` params the page already reads. `state` and `country` are aliases of `destination`, not separate dimensions. Imperative actions own only state with no address: opening a panel, staging form values.
4. The assistant never submits. It stages values and marks them as assistant-written. The button stays a human action on every form, booking included.
5. Any number the assistant states about the current view comes from the page's own reported state, relayed unchanged and composed server-side. A bounded server-side search tool arrives later and never overrides the page for an on-screen claim.
6. Capability vocabulary splits three ways by ownership. Argument schemas, constant value sets and form field schemas live in the shared contract. The set of capabilities reachable this turn and the catalogue-derived value sets are registered at runtime and sent with the request. Where a value set is neither, the value is shape-validated and the target page degrades gracefully rather than the turn being rejected.
7. Hardening starts at commit one. Model output never becomes a raw URL, never writes outside a capability registered this turn, and every supplied value is validated against the shared schema before dispatch, plus against a reported value set whenever one exists.

Premise 2 was revised mid-session; the first draft claimed the client owns the whole vocabulary, which the repo already contradicts.

## Action contract

One discriminated union of client-executed actions, each a new top-level member of the model's response union. Structured arguments travel as prefixed flat scalar keys and are un-nested during canonicalization.

- `navigate` — args `{ route, message, param_<name>… }`. Canonicalized to `{ route, params }`. `serverResult` becomes `{ route, path, params }`.
- `open_panel` — args `{ panel, message }`. Canonicalized to `{ panel }`. `serverResult` is `{ panel }`.
- `prefill_form` — args `{ form, message, field_<name>… }`. Canonicalized to `{ form, fields }`, narrowed to the chosen form's writable fields. `serverResult` is `{ form, fields }`. No member's effect is submission.

Plus one new **answer** outcome:

- `answer_current_view` — the model selects it when the visitor asks about what is currently on screen. The server composes the sentence from the reported `currentView` using server-owned copy; the model supplies no numbers. This outcome is what gives the page-state channel a consumer: with the conversational flag off, `answer_faq_policy` is the only other non-mutating outcome and it falls back to policy copy when retrieval matches nothing, so a count question currently has nowhere to land.

`message` stays a model-authored argument on the action members. When it is empty the controller supplies a per-action server-owned fallback rather than the generic one, because a bare `NO_MESSAGE_FALLBACK` on a successful action reads as a failure.

**URL mutation semantics.** Same route: supplied parameters patch the current URL, so "and sort by price" keeps the destination and price filters. Different route: the supplied set replaces, since another page's filters are meaningless. Clearing uses an explicit sentinel per parameter (`any` for a filter, `all` for destination). Pagination resets to page 1 whenever a filter parameter changes, unless the turn sets `page` itself, matching what the page already does when a human clicks a filter.

**Per-turn schema builder.** `assistantTurnResponseJsonSchema` becomes `buildAssistantTurnResponseJsonSchema({ routes, forms, flags })`, built each turn from the offered routes' param schemas and the registered forms' field schemas, emitting flat optional scalar properties only.

**Vocabulary lists.** Seven closed lists hardcode the same values and must be derived from the shared contract or extended: `ASSISTANT_TOOLS` and `assistantTurnResponseSchema` (`assistantTurn.v1.js`), `AssistantTurnTool` (`Client/src/services/api/assistantTurn.ts`), `recordEventSchema.tool` (`validators/assistant.schema.js`), `assistantResolutionEventSchema.tool` (`telemetry/assistantEvents.js:28`), `AssistantEventTool` (`Client/src/services/api/assistantEvents.ts`), `allowedFinalTools` (`evaluation/routerEvaluation.js`). The telemetry one is `.strict()`, so a resolution event carrying a new outcome currently fails to parse and is dropped with a logged error.

**Client view union.** `AssistantTurnData` is derived from the shared action union rather than hand-written, and `deriveTurnData` is exhaustive over it, so a contract addition without a view variant fails to compile.

## Argument encodings

- `destination` — catalog-derived, resolved in the slug space the page matches (`slug`, `nameSlug`, `countrySlug`, `id`). `state` and `country` are aliases. The page reports the values it resolved.
- `priceMin` / `priceMax` — numbers in the deployment's display currency. No bucket ids.
- `durationMin` / `durationMax` — numbers of days.
- `rating` — one of `5`, `4`, `3`.
- `sort` — one of `popularity`, `price-low`, `price-high`, `duration`.
- `page` — a positive integer.
- `view` — `grid` or `list`.

**Built as (step 1, 2026-09-12).** Two things landed differently from the sketch above, both simpler. Price and duration are plain numeric bounds rather than band ids, so a link carries `priceMax=1500` and the sidebar's bands write their own `min`/`max`; an unknown or non-numeric bound degrades to no filter rather than reaching the server. And `sellPrice` is now a database-generated column on `Package`. It had to be: the page's price is cost plus a per-package margin computed at read time, so there was nothing for the server to filter on, and the only price filter that existed filtered `basePrice` while the cards rendered `sellPrice` — a defect that was invisible only because `defaultMarginInput` defaults to 0. Repointing it fixed the planner wizard's budget too.

**Writable field types.** A field is prefillable only if its registered type is one of `text`, `email`, `tel`, `textarea`, `date`, `number`, `select`. File inputs, consent and agreement checkboxes, and credentials are non-prefillable, and the registry refuses to register them rather than relying on each form to omit them. Concretely: `ApplicationForm.tsx:181` (`type="file"` resume) and `:214` (required `agreeTerms`) are outside the protocol by construction.

## Per-turn wire changes

The request gains two fields beside `availableRoutes`:

- `capabilities` — trimmed to what the contract cannot know: `version`, `route`, `panels`, `revision`, and `optionSets` (`destination`, `category`). Form field schemas and constant value sets come from the shared contract keyed by route, so this block does not restate them every turn. `revision` is computed by the client from the mounted capability set and the target identities it depends on.
- `currentView` — `{ path, params, filteredCount, renderedCount, catalogueTotal }`. With step 1 moving filtering server-side, these are read from the server's own response rather than from a locally filtered array.

**Stale actions.** The server echoes the request's `revision` on any client-executed action; the runner refuses a response whose revision no longer matches the mounted page, surfacing "the page changed, ask me again". This is what stops package A's traveller details being written into package B's booking form when the visitor reopens a modal mid-turn. The in-flight turn is additionally aborted on route change as a cheap first line.

## UI Design Decisions

From `/plan-design-review` (seven passes; text-based, because the designer binary is installed but has no OpenAI credential and the probe returned `No OpenAI API key found.`).

**Attention and announcement (Pass 1).** Whenever the assistant changes the page, the change is announced in the transcript as a short present-tense line naming what changed. The widget never steals focus and never moves the viewport. The form carries the markers; the transcript carries the narration.

**The assistant-written marker (Pass 5, Pass 6).** Colour plus a non-colour signal: a tinted field with a short adjacent label or an icon carrying an accessible name, so it survives colour blindness, high-contrast mode and monochrome. Staging fields fires a polite live-region announcement naming how many fields were filled. The marker must not read as a validation error, and it must not be implemented as a coloured left border on a rounded card.

**The confirm chip (Pass 6).** Minimum 44px touch target, operable and dismissible by keyboard, rendered inside the assistant bubble rather than as a modal.

**The count answer (Pass 7).** A distinct, quieter view-summary block: the number large enough to read at a glance, the active filters shown as the existing rounded chips, and a one-line qualifier when the number is partial. Visually distinct from both a policy answer and an action announcement.

**Component reuse (Pass 5).** A design system already exists: `Client/DESIGN.md`, which the `index.css` token block already cites. An earlier finding of "no design system" was wrong, because it checked the repository root rather than `Client/`. This review extended that system rather than replacing it: a new **Assistant Affordances** section documents the field marker (`bg-brand-50` with a `border-brand-200` hairline and an outline badge, never gold and never `red-600`), the confirm chip, the action announcement, the view-summary block, and a new `z-floating-assistant` (110) token for the panel above an open dialog. The marker uses `Client/src/components/ui/badge`; the chip and announcement reuse the widget's existing `CHIP_CLASS` and fallback bubble; layering stays inside the named `z-` scale.

### Interaction state table (Pass 2)

| Feature | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| Assistant-written marker | field not yet staged | no fields staged | field refused as non-prefillable, stated in the transcript | field marked, label present | some fields staged, refused ones named |
| Confirm chip | turn in flight | no collision | chip stale because the page changed, dismissed with a note | applied, marker updates | some fields applied, others held |
| Action announcement | turn in flight | no action this turn | action failed, reason in the transcript | one line naming what changed | applied with a qualification, e.g. an unknown destination |
| Filtered view change | route transitioning | filter produced zero results, with a way to clear | turn failed, prior view intact | URL, chips and result set agree | count qualified because the catalogue total exceeds what was loaded |
| Count answer | turn in flight | no view reported | assistant says it has no view rather than guessing | number matches the rendered set | partial, with the qualifier line |

## Prioritized build order


1. **Server-side packages filtering plus the URL refactor.** Move filtering and sorting from `PackagesContainer` into package-service (the API already computes and returns a true `total` that `fetchPackages` discards), and move price, duration, rating, sort, view mode and page out of local `useState` into `searchParams`, with the sidebar's budget buttons writing `priceMax`. Keep `showFilters` out of the URL; fix its resize listener (`PackagesContainer.tsx:55-58`) so an explicit open intent survives a resize. Test the URL round-trip, an unknown budget degrading to no filter, and a filter change resetting pagination.
2. **Extract the wire module.** Move `assistantTurnResponseJsonSchema` and `canonicalizeAssistantTurnResponse` out of `ai/prompts/` into a contract-facing module that imports the shared contract. Do this first, before expanding either, so the prompt file ends up owning prompt text only.
3. **Shared contract.** Add the action union (including `answer_current_view`), per-route param schemas, the encodings above, the writable-type allowlist and the four forms' field schemas to `Services/shared/contracts` as a domain module re-exported from `src/index.js`.
4. **Wire plumbing, both directions.** In `assistantTurn.v1.js`: `CORE_TOOLS`, the response union, the per-turn schema builder, canonicalization, and `buildAssistantTurnPrompt` accepting `capabilities` and `currentView`. In `assistant.controller.js`: the `req.body` destructure, explicit dispatch cases for every new outcome (without which they 502), and `answer_current_view`'s server-composed copy. In `assistant.schema.js`: `assistantTurnSchema`, the manifest patterns and size caps, the telemetry enums, and the `metadata` pass-through. In `assistantEvents.js`, `assistantEvents.ts` and `routerEvaluation.js`: the three remaining tool lists. In `useAssistantChat.ts`: the derived view union and `deriveTurnData`. In `AssistantWidget.tsx`: the render branches.
5. **Client mirror and page mapping.** Convert `Client/src/services/api/assistantTurn.ts` to import the shared contract, with every new field optional and `params` defaulting to `{}`. Add `pageCapabilities.ts` mapping route names to shared param schemas and option-set reporters.
6. **Capability registry.** A React context plus `useAssistantCapability()`, the revision computation, and completeness tests: every registered capability has a shared schema, a piece of state is claimed by exactly one mechanism, and the wire union's member list equals a frozen literal.
7. **Client action runner.** Dispatch after validation, revision check, push history for assistant-initiated URL changes, and inline failure messaging plus a recorded event.
8. **Form prefill.** The registered handler contract, writable-type enforcement, provenance tracking, dirty tracking, and the collision flow: non-colliding fields apply immediately, colliding fields are held and rendered as an inline confirm chip in the assistant bubble (a client-side control, not a server turn), with discard keeping the visitor's original text. Modal-hosted forms (review at `z-modal: 100` versus the widget's `z-floating-action: 70`) get an explicit integration: the widget raises above an open modal and takes focus, with Escape and focus-trap behaviour stated between widget and dialog.
9. **Page-state channel.** The page reports `currentView`; step 4's `answer_current_view` consumes it; the prompt is instructed never to state a count it was not given.
10. **Failure semantics and telemetry.** Server-side rejection degrades to the existing repair copy and records a rejection event. Client-side rejection shows an inline message and records the same. Needs an event type that does not exist, plus `action` and `reason` carried in `metadata`: `AssistantEvent` already has a `metadata Json?` column (`prisma/schema.prisma:33`), but `recordEventSchema` is strict and has no `metadata` field and `events.controller.js:12-14` hardcodes `metadata: null`. No migration needed.
11. **CI coverage.** Add a Client unit-test job and a `Services/e2e-tests` job to `microservices-ci.yml`. Today the four `npm test` invocations cover shared/contracts, the backend service matrix, Management and package-service; Client is only built in `deploy.yml`, and neither `Services/e2e-tests/` nor Management's Playwright suite is referenced by any workflow. Roughly two thirds of this branch's diff is Client.

### Deferred, not in this branch

A bounded server-side `search_packages` tool, in the registry with a per-page `tools:` declaration like Management. Gate: this design's success criteria plus the phase-1 go/no-go bar.

**REGRESSION (mandatory).** The `navigate` response gains `params` and the outcome union grows, both of which change the shape existing callers parse. The client mirror test above is the regression guard and is required, not optional.

## Success Criteria

- "Dubai under $1000" completes in one turn from the packages page with the right parameters and the right rendered set, computed over the true catalogue rather than a capped page.
- From `/` it completes in one turn too, with the destination checked when a value set is available and passed through as a slug otherwise; an unrecognised slug lands on an unfiltered page, never a broken one.
- Any budget the visitor names works, not just the ones that happen to match a sidebar bucket.
- "And sort by price" preserves the filters already applied.
- The URL is shareable, and the back button returns the previous filter state.
- Asking "how many are under $1000" on a filtered page returns the matching total via `answer_current_view`, not a refusal and not the rendered page size.
- No assistant-triggered form submits. The invariant is that the action union declares no member whose effect is submission and the runner references no form submission API; checked by the frozen-union test plus a grep for `requestSubmit` and `submit()`.
- An action chosen against a stale page never executes.
- No assistant link is unshareable, and no piece of state is reachable only through the imperative path.

## Open Questions

- Registry completeness as a runtime assertion or a test-time one. Test-time is cheaper; runtime catches a lazily mounted form the test never rendered.
- Whether `currentView` is sent every turn or only when it changes.
- Which UI treatment marks an assistant-written field across four different forms without reading as an error state.
