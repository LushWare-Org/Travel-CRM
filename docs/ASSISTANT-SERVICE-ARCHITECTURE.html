0Scope & method

This document describes the service as it exists in the working tree. Every number is quoted from source; every claim names its file. The goal is the opposite of a design doc: it is the runtime contract — what actually happens between an HTTP request arriving and a JSON body leaving, plus the hard ceilings that no amount of prompt engineering can move.

Reading the badges

PHYSICAL a ceiling enforced by infrastructure (Cloud Run, Node, the provider, the network). Logic cannot route around it.   ARCHITECTURAL a deliberate design constraint — movable, at a cost.   PRODUCT not built yet.   SHIPPED present and working.

Three findings worth reading first

  1. Two assistants share one service. A public, anonymous conversation loop (/assistant/turn) and an authenticated, evidence-grounded operator copilot (/assistant/management/*). They share a Gemini client and a Postgres schema and nothing else.
  2. Only one of them has a tool-calling loop. The site-wide assistant is a single structured call that picks one of seven outcomes. The operator copilot runs a bounded 4-call agent loop over a fixed tool registry.
  3. The binding constraints are time budgets, not prompt logic. Four independent deadlines (30s client → 27s server → 20s model → 1.5s router) plus a 17s copilot budget, a 4-tool-call cap, and a max_instances = 10, min_instances = 0 deployment. Capability work that ignores them will pass tests and fail in production.

3Site-wide turn flow SHIPPED

File: src/controllers/assistant.controller.js · prompt src/ai/prompts/assistantTurn.v1.js · router src/ai/assistantRouter.js

Per-call loop

  1. Validate. validateBody(assistantTurnSchema) → sessionId ≤255, messages 1..20 (each content ≤2000, at ISO datetime), availableRoutes ≤100. Zod strips unknown keys.
  2. Stage 1 — optional classifier. Only when ASSISTANT_CONVERSATIONAL_OUTCOMES_ENABLED=true: one structured call, temperature 0, maxOutputTokens 256, timeout min(1.5s, remaining), maxAttempts 1. Returns one of 7 intents + confidence + hasActionableClause.
  3. Stage 1 short-circuit. Commit only if the class is enabled, confidence ≥ threshold (default 0.95), and intent is social or off_topic with no actionable clause. Then the server returns reviewed copy with no second model call, records telemetry, and exits.
  4. Policy retrieval. fetchPolicyDocuments() → GET user-service /api/v1/admin/internal/policy-documents with x-internal-token; 3s abort; 60s in-process TTL cache; on failure serves stale cache, else []. Then retrieveSnippets(): keyword overlap over blank-line sections (tokens length ≥4, stopword-filtered), maxSnippets 2, minScore 1. No embeddings, no vector store.
  5. Stage 2 — the resolver. One structured call, maxOutputTokens 1024, temperature 0.7, timeout min(20s, remaining), maxAttempts 1. Emits a flat { tool, args }.
  6. Canonicalize + parse. Flat payload → strict 6-way discriminated union. Parse failure → 502 AI response did not match the tool contract.
  7. Deterministic dispatch. A server-side switch, not the model, decides what the user sees (see below).
  8. Message guard. Empty → reviewed fallback string; longer than 2000 → sliced. A response can never be empty, because an empty assistant bubble would poison every later turn's resent window.
  9. Telemetry (awaited). One validated AssistantEvent row: tool, route, router metadata, per-stage latency, fallbackUsed, failureCategory.

The 27s deadline is bookkeeping, not a watchdog. It is checked before the router and before stage 2; nothing aborts an in-flight provider call when it expires, and there is no setTimeout that cancels the request. Node's own server.requestTimeout (default 300s) is the only hard backstop — so an abandoned turn can keep a Cloud Run instance and a billed generation alive long after the visitor's browser gave up at 30s.

5The tool-calling loop ARCHITECTURAL

File: src/ai/agentRunner.js · registry src/tools/toolRegistry.js

Mechanics, verbatim

MAX_TOOL_CALLS        = 4
MIN_CALL_TIMEOUT_MS   = 1_000
budget                = MANAGEMENT_GENERATION_DEADLINE_MS = 17_000   // whole ask

if (resolveTools(names).length === 0)  → single-shot schema {claims} , no tool block
                                       → maxAttempts 1, timeoutMs = 17_000

deadline = Date.now() + 17_000
for (call = 0; call < 4; call++) {
  remainingMs = deadline - Date.now()
  if (remainingMs < 1_000) return { answerBlocks: [], toolEvidence: history }   // stop, don't spend
  raw = generateStructured({ ..., timeoutMs: remainingMs, maxAttempts: 1, temperature: 0.2 })
  if (raw.tool === 'final_answer') return { answerBlocks: raw.args.claims, toolEvidence }
  result = executeTool(tool, args, ctx, allowedNames,
                       AbortSignal.timeout(max(deadline - Date.now(), 1_000)))
  history.push({ tool, result })
}
return { answerBlocks: [], toolEvidence }

Three properties that matter for extension:

  • One budget, not one per call. Each iteration's timeout is what remains of the single 17s, so unused time rolls forward and the total can never outrun the budget. Four slow steps cannot bill four full generations.
  • The budget covers tool I/O. Every tool read receives the remaining budget as an AbortSignal, so a stalled domain service cannot outlive the ask.
  • Exhaustion is answer-shaped. A loop that runs out returns answerBlocks: [] plus whatever tool evidence it gathered — never a briefing payload, never a phantom claim.
Physical consequence: because each iteration re-sends the entire history, prompt bytes grow across the loop. With the 64 KB per-list-result budget, a worst-case 4-step ask serializes roughly 0 + 64 + 128 + 192 ≈ 384 KB of tool results cumulatively, on top of the evidence bundle, for one 17-second request on 1 vCPU. There is a per-result byte cap and no aggregate prompt cap.

Execution semantics (executeTool)

if (!allowedNames.includes(name))      → { error: "unknown tool '…'" }   // caller-resolved vocabulary only
const parsed = tool.argsSchema.safeParse(args)                            // strict Zod
if (!parsed.success)                    → { error: "invalid args for …" } // fed back to the model
try { return await tool.execute(ctx, parsed.data, signal) }
catch { return { unavailable: true } }                                    // never throws out of the loop

Three result shapes are possible and all are model-visible data, not exceptions: {data}, {notAuthorized:true} (403/404 from the domain service, propagated verbatim — the copilot never pre-checks ownership because the ownership model has carve-outs), and {unavailable:true} (network, 5xx, abort). The model can name a tool the page did not declare and gets an error string, never an execution.

6The model layer — the single AI seam

Call construction

  • Model pin: GEMINI_MODEL || 'gemini-3.5-flash' — deliberately not a -latest alias. The file's own comment records the reason: the alias resolved to a preview build with a 20-request/day free-tier quota that returned 503s.

7Grounding & safety envelope

Two different strategies

Public turn — grounded by construction

No post-hoc validator runs. Instead the model is structurally unable to invent facts: it may only select server-retrieved snippet ids, and the server owns every quotation and every fallback string. Navigation is checked against a client-supplied allowlist; a route not offered in this request cannot be reached.

Copilot — grounded by validation

groundingValidator.js runs deterministic post-generation checks with no model judgment: a fact is grounded iff its normalized value appears inside the normalized serialization of a cited evidence item. Claims citing unknown ids, or carrying unsupported numbers/dates/amounts, are pruned. Residual value tokens in prose are rejected outright — deliberately over-rejecting, because zero unsupported values is the success criterion, not maximum claim count.

Safety properties worth preserving in any extension

  • Client-owned route allowlist. The server holds no route table; the browser sends the enabled routes per request and the server only validates the model's pick against them.
  • Sensitive-topic override. Visa/health/safety/legal/emergency/financial intents are forced to a refusal message before the model's answer is used.
  • Server-owned sources. buildSources builds the source list from accepted evidence ids — never from model-authored labels or URLs.
  • Message sanitization. Model prose is HTML-stripped, and any message containing a URL is discarded in favour of reviewed copy.
  • Prompt-injection posture. The router prompt wraps the visitor message in <visitor_message> and instructs the model never to follow instructions inside it; a mixed/unclear/injection case is classified ambiguous and routed to the resolver rather than blindly committed.
  • Identity forwarding, not escalation. The service acts as the caller to every domain service; a 403/404 is surfaced as notAuthorized, never retried with different credentials.

Rate limiting — and why it is weaker than it looks

  • globalLimiter: 300 / 15 min / IP, applied to everything.
  • itineraryChatLimiter: 30 / 15 min / IP, applied to /assistant/turn — shared with wizard-turn, itinerary-chat, generate-day-preview and generate-days-preview.
  • The store is in-memory per gateway instance. Counters reset on cold start and do not coordinate across instances, so the effective global ceiling scales with gateway instance count rather than being a true cap.
  • Carrier-grade NAT means many real visitors can share one IP and collectively exhaust the shared 30-request bucket; the client shows a generic "failed to reach the assistant" banner with no rate-limit-specific message (known issue, TODOS.md P3).

The three ceilings most likely to bite capability work:
  1. 1 vCPU, 512 Mi, 10 instances. Parallel fan-out, larger evidence bundles and bigger prompts all compete for the same fixed compute.
  2. Single-shot, non-streaming, 17 s / 27 s budgets. Any feature whose perceived value depends on feeling immediate (proactive review, long investigation) must fit inside these or change the transport.
  3. No aggregate prompt budget. The tool loop bounds each result but not the sum, so adding tools multiplies the worst-case prompt rather than adding to it linearly.

10Limitations, by layer

Ordered from least movable to most movable. Work on the top layers is wasted if the bottom ones are saturated.

L1 — Physical / infrastructure PHYSICAL

  • 512 Mi / 1 vCPU / 10 instances; scale-to-zero cold starts with no startup probe.
  • No declared Cloud Run timeout or concurrency; only Node's 300 s request backstop ends an abandoned turn.
  • Non-streaming transport end to end.
  • In-memory, per-instance rate limiting shared with unrelated AI routes.
  • Provider quota, per-attempt timeouts and a 65 536-token output ceiling.
  • Keyword retrieval with a per-instance 60 s cache; no vector store.
  • Unbounded telemetry table on a shared pooled database.

L2 — Architectural ARCHITECTURAL

  • Conversation state is server-side now. The turn reads and writes AssistantSession/AssistantMessage, and the client's resent window is used only when the store cannot be read. A device switch keeps the thread only if the same sessionId travels, which it does not — the id lives in that browser's localStorage.
  • Retries effectively disabled on the public path (maxAttempts: 1) — transient provider failures are user-visible failures.
  • Deadlines are arithmetic, not watchdogs — expiry is checked at two points and nothing aborts in-flight work.
  • Evidence preload sits outside the model budget for the copilot, so a slow domain service delays the response without consuming the 17 s.
  • No aggregate prompt budget in the tool loop; growth is per-result only.
  • Grounding over-rejects by construction (any numeric-shaped prose is suspect), so richer prose styles trade directly against claim survival.
  • Six outcomes hard-coded into one union shared by prompt, canonicalizer, controller, wire schema, client enum and telemetry enum — extending the public vocabulary is a six-file, versioned change.
  • Telemetry insert awaited on the public turn's critical path.
  • Feature-gated dark launch: copilot routes 404 unless two env vars and a client build flag agree.

L3 — Product / not built PRODUCT

  • No write actions of any kind; no confirmation-and-apply flow.
  • Five of eight planned tools unregistered; scope filters on collection pages deferred (blocked on a real schema for the collection branch).
  • No proactive review queue; no interrogable-briefing entry point; no cross-page working memory.
  • Copilot drawer is modal below xl, so the evidence-reveal interaction degrades on tablet/phone.
  • Public assistant has no contact-details parity on policy miss (no orgSettings fetch).
  • Impression telemetry fires once per mount keyed on the first pathname, skewing the design's own go/no-go denominator.

13Recommended sequencing

Ordered so that each step makes the next one measurable. Steps 1–3 are infrastructure work that unblocks everything above it; steps 4–6 are the capability work.

  1. Make the failure envelope observable before changing capability. AssistantEvent.metadata already stores failureCategory, per-stage latency, fallbackUsed and routerVersion. Query it over a week to get the real distribution of provider vs timeout vs schema failures and the true p95 of each stage. Nothing else can be prioritised honestly without this.
  2. Fix the physical resilience the budgets already assume: re-enable retries on the public turn (a bounded second attempt inside the existing 27 s, the way the briefing does it), declare the Cloud Run request timeout and concurrency so a stuck request cannot run 300 s, and stop awaiting telemetry on the turn's critical path. These three are pure wins with no capability change.
  3. Fix resource governance: give /assistant/turn its own limiter instead of sharing the wizard bucket; add a retention or sampling policy for AssistantEvent; stamp the policy-document cache on failure so an outage does not pay a 3 s fetch per turn.
  4. Widen the copilot's reach with the seams that already exist — register the five declared tools behind their IAM grants, one per page, each with its projection/rowCap/byte budget. This is additive, reviewed per page, and needs no new transport.
  5. Then add aggregate prompt budgeting to the loop (a total byte cap across history, not just per result) before adding more tools, or tool count becomes a latency cliff instead of a cost curve.
  6. Only after that, consider new public-assistant outcomes or cross-page memory — both require contract versioning across six surfaces, and both are bounded by the 1 024-token / single-shot envelope. If the product genuinely needs long, investigative answers, that is a streaming re-platform decision, not a prompt change.
The one-line version: the service's ceiling today is set by four numbers — max_instances = 10, 1 vCPU, 17 s and 1024 output tokens. Instruments first, then resilience, then tools, then new outcomes. Any capability added before the retry/timeout/telemetry issues are settled will be measured through a noisy, unrecoverable failure path.
